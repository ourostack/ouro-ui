# The site's parts

How the site under `site/` is put together, with the rules its parts hold to: the docs pages, Spoonjoy's usage map, the Apple section, the voyage pages, the porthole stage and the chapters. Moved out of AGENTS.md, which keeps the rules an agent acts on and links here.

## Site

- `site/`: the home page, the Nautilus's page and the docs site (https://ui.ouroboros.bot/), built with Vite from the root dependencies, not a workspace package. Docs pages render the generated `docs/*.md`, each page loading only its own files before it renders or hydrates (`site/src/docs/content.ts`, through the docs module's `prepare`), and the index lists every page from the summaries `pnpm run docs` writes into `catalog.json` and `pages.json`, so the docs' first load doesn't grow with each page; each registry item's page is `docs/<item name>/`, listed from `site/src/docs/catalog.json` (written by `pnpm run docs`), with the live demo from `site/src/docs/demos/<item name>.demo.tsx` (its default export; `site/src/docs/demos.tsx` finds them by glob).[^a-demos] Demos are site code and ship in no item.[^a-demos-site] `pnpm site:build` writes `site/dist` (prerendered HTML per route, with Open Graph and Twitter tags from `site/src/head.ts`), `pnpm site:dev` serves it. Link previews show storybook cards: `node site/scripts/og-cards.mts` draws them into `site/public/og/` from `CARDS` in `site/src/storybook.ts`, and a page without a card of its own shows the docs card. `site/public/og.png`, the 1200x630 screenshot of the old landing page that previews used before the cards, stays for links shared then; `node site/scripts/og-image.mts` redraws it.[^a-og] The "Agents read the types" examples live in `site/src/agents/examples.ts`; `pnpm site:messages` regenerates their compiler output (`site:build` and `pnpm test:scripts` fail when it is stale), and the `site` Vitest project checks each quoted dev message against the real component.[^a-agent-messages] Each page kind (the voyage module, which renders the home page `/` and the Nautilus's page `/nautilus/`, and the docs) is its own chunk: `site/scripts/prerender.mts` links its stylesheet, `site/src/entry-client.tsx` loads the page's module once the server HTML has painted (so the paint gets the bandwidth) and then hydrates, `App` marks the hydrated page `html[data-site-ready]` (end-to-end specs wait for it before they click), and `site/e2e/catalog.spec.ts` holds each closure to its gzip ceiling (each page kind may grow at most a fixed margin past what CI measured it at; the voyage pages never load the docs' Markdown; Recharts and docs demos are never in one).[^a-chunks] The site is named Ouro UI (the header's brand, the home page's title, `og:site_name`, the web manifest and the footer), a complete kit for agents to build delightful interfaces for people and for other agents; the hero says so in six words.[^a-six-words] Ouro HX, for the screens people use, and Ouro AX, for the tools agents use, are two of the kit's parts: the bar and the footer name both, and the kit row under the hero names its four parts and links each (`KIT` in `site/src/copy.ts`).[^a-ui-halves] The header wears the Ouro HX mark beside the name Ouro UI, and Ouro UI and Ouro AX have no approved mark of their own (`site/public/brand/provenance.json`).[^a-ui-mark] A component's or guide's page keeps its product's name in its title (`Button · Ouro HX`). An old address is a static page that refreshes to the new one, with a canonical link and a plain link (`redirects` in `site/src/routes.ts`, `redirectPage` in `site/src/head.ts`): `/voyage/` goes to `/`.[^a-redirects] A redirect for another kit's name (`/docs/modal/` to Dialog) also says so on its page, from its `note`.[^a-redirect-note]
- `site/src/docs/spoonjoy.json`: where Spoonjoy uses each component, for the docs pages' "In Spoonjoy" section.[^a-spoonjoy] `node site/scripts/spoonjoy.mts` rewrites it from Spoonjoy's public pages, fetched signed out (a page counts only when its HTML holds the component's `data-ouro="<item>"` marker), and its `/ouro-provenance.json` (the files that render it); rerun it when Spoonjoy adopts a component, and update the home page's component count (`site/src/voyage/home.tsx`), which `claims:check` compares with the file.
- The Ouro UI for Apple section (`site/src/apple/`, `/apple/…`) shows what ourostack/ouro-ui-apple has shipped. When an Ouro UI for Apple feature lands on that repository's main branch, update the section in the same wave: its own page if it needs one (`APPLE_PAGES` in `shell.tsx`, `APPLE_PATHS` in `site/src/paths.ts`, `routes.ts`, the island and prerender lists, `catalog.spec.ts`), the overview, the start page and `site/llms.txt`. Say it comes in a later release until a release tag carries it, and give install lines only for a real tag.
- `site/src/pages/voyage.tsx`: the voyage pages ("Mobilis in mobili", `site-design.md`). The home page `/` is the porthole stage, "Two ships, same parts." (two showcases laid out on the page, not in cards: the Nautilus, a story made up to show HX off, and Spoonjoy, a real app, each with an "X-ray it" link and its picture: the Nautilus in profile beside its words, and Spoonjoy's X-ray screenshot across its row under them, which `node registry/ouro/images/images.ts site/showcase --out site/public/showcase --widths 640,960,1280 --base /showcase/` makes from the sources and provenance in `site/showcase/`; much more is built with HX, so the section never reads as the list of its users, and it counts no components), the themes, the agents section and the install steps with what comes with every component (`site/src/voyage/home.tsx`, `home-reference.tsx`); `/nautilus/` is the story's opening, its list of chapters and Chapters I to III (`site/src/voyage/nautilus.tsx`).[^a-two-ships] This home page took over ouroboros.bot/ouro-hx/, which forwards here: pages about Ouro HX, Ouro UI and Ouro AX are written here, not on ouroboros.bot. `?xray` in the address turns X-ray on at load on both, and on every docs page.[^a-xray-address] Its chrome is built from Ouro HX components, and it themes the page with six presets, each a plain shadcn/ui theme in `site/src/themes/<preset>.css` (`:root` and `.dark`, plus `--font-heading`, the `--shadow-*` scale and `--ouro-backdrop-color`, and where a preset's actions differ from its selection, `--ouro-action` and `--ouro-action-foreground`, as Cookbook's do).[^a-presets] `pnpm site:themes` (`site/scripts/themes.mts`) writes `presets.generated.css` (each preset scoped to `[data-theme="<preset>"]`) and `themes.json` (the "Copy theme" and "Copy tokens only" CSS); `--check` (in `site:build`) fails when they are stale, a font's checksum or budget is off, or the synced part of `cookbook.css` was edited.[^a-themes-check] `pnpm site:static-css` (`site/scripts/static-css.mts`) writes `ouro-base.css`, `ouro-theme.css` and each preset as plain stylesheets in `site/public/css/`, for pages without Tailwind (`docs/guides/static-css.md`); `--check` (in `site:build`) fails when one is stale.[^a-static-css] Cookbook is Spoonjoy's own tokens: `node site/scripts/themes.mts sync-cookbook <spoonjoy-v2 checkout>` copies them in from the checkout's `app/styles/sj-tokens.css` and `app/styles/tailwind.css` and records the commit. The fonts are self-hosted Latin subsets in `site/public/fonts/<family>-<version>.woff2`, listed with their package, checksum, licence and changes in `site/src/themes/fonts.json`; only Geist and Geist Mono are preloaded, and a preset's display face loads when it is chosen. The theme a reader picks is stored in `localStorage` (`ouro-site-theme`) and applied before first paint by the inline script `head.ts` puts first in every page (`site/src/themes/prepaint.ts`); a reader who has picked none gets Live, Pearl under their own sky.[^a-prepaint] CI's `theme-install` job (`site/scripts/theme-install-test.sh`) pastes each preset's copied CSS into the clean shadcn app the install test starts from, with Checklist and Dialog, and compares it with the site (`site/theme-install/`).[^a-theme-install] The Ouro HX logo in the headers and the favicon comes from `site/public/brand/`: byte-identical copies of the approved artwork, listed with their checksums and source commit in `provenance.json` and checked by `site/scripts/brand.test.mjs`;[^a-brand] never recolour, re-export or redraw them (`site/src/components/brand.tsx` renders the rich render with its `srcset`).
- The voyage hero's porthole stage (`site/src/voyage/stage/`): `scene.tsx` layers the original drawings in `site/src/nautilus/art/` (coloured from the theme in `stage.css`, so presets repaint it), `stage.tsx` drives it with HX controls, and `copy.ts` holds every word it says, the crew's log lines and `STAGE_CONTROLS`.[^a-stage-copy] Each control in `STAGE_CONTROLS` needs a test named `control: <id>` in `site/e2e/stage.spec.ts` that operates it and asserts what it visibly changes (`site/scripts/stage-census.test.mjs` fails otherwise, for the stage and each chapter: `CENSUSES` in `site/scripts/stage-census.mts`);[^a-stage-census] the same spec holds touch, reduced motion and off-screen rest; `site/e2e/stage.latency.spec.ts` holds each control to its click-to-paint budget in `site/e2e/latency.ts` (4× CPU; of 20 presses after two warm-ups (ten before a run's first control, which warms the browser), p95 within 100 ms for every control and the median within twice the control's CI baseline or 24 ms over it, whichever is more, from `BASELINE_MEDIAN` in the spec; 20 presses more, once, when only the p95 of the first 20 is over budget and all 40 could be within it, and then the same budget judges all 40, never a chosen take; each bound times the runner's factor, which a calibration probe pressed beside the control at the same throttle measures: 1 on a quiet runner, at most 1.5 on a slow one (#798); when the probe reads the runner past 1.5×, the runner is given 10 s and the control measured again, pass or fail, up to three measurements in all, and the last alone is judged, failing as too loaded to judge when its probe is past it too; but when the reads are steady (every one past 1.5×, all within one 8 ms step of each other), the runner is slow, not loaded, so the control is judged at 1.5×, which stretches its bounds less than the runner is slow: a pass there stands, a miss fails as infrastructure, "runner too slow to judge", the job's later controls are measured once and judged the same way (the verdict is kept in the run's output folder, since Playwright starts a new worker after a failed test), and the job summary and a `latency-runner-too-slow` log line count the misses (`steadySlow`, ourostack/ouro-ui#2114); each re-measured control and a count of them go in the job summary, which flags a job where more than 1 in 20 controls needed one[^a-latency-remeasure]; Event Timing reports 8 ms steps, rounding each duration to the nearest, so the p95's bound is rounded to the nearest step too (ties up: 104 ms at 100, 120 at 119; `p95Bound`);[^a-latency-step] every sample printed; other `*.latency.spec.ts` files use the same helper) and runs alone (`pnpm test:latency`, `playwright.latency.config.ts`, CI's `latency` job) so no other test shares the CPU; and `stage.test.tsx` holds the copy to Flesch–Kincaid grade 6 (`site/test/readability.ts`).[^a-stage-latency] Every drawing is listed in `site/src/nautilus/art/manifest.json` (creator, source, licence, checksum, its `subject`, and for any drawing with the Nautilus in it, `"subject": "nautilus"` however small the ship, the Verne passages its shape follows); `node site/scripts/art.mts` (in `site:build`) fails on an unlisted file, a stale checksum, a licence outside the allow-list, public-domain art that is not de Neuville's or Riou's from 1871 or earlier on Commons or Gallica, or art over the hero's 35 KB gzip budget; `--write` refreshes checksums.[^a-art] Draw the Nautilus from Verne's text, never the 1954 film's design. The hero's proof claims are computed at build time from the repository (`site/scripts/proof.mts`, served as `virtual:site-proof`), so each claim is only what its source says, and each links to its evidence; the hero gives a person no command to run: what a person does is choose Ouro UI and hand it to their coding agent, so beside the story on a wide screen, and under the meadow on a narrower one, it shows a look to try and one line to paste to the agent (`HANDOFF` in `site/src/copy.ts`), which sends the agent to `llms.txt`; the commands are in the install section, for agents and the curious, and every public install address there is pinned (`scripts/latest-release.test.mjs`).[^a-proof] The hero's words are `VOYAGE_HERO` in `site/src/copy.ts`; never describe HX as "for shadcn/ui apps": the shadcn CLI is only how it installs.[^a-voyage-copy] The crew's newest line has a strip of its own between the porthole and the console, in flow, with room kept for it (the captain's first order at rest), so it never lies over a control (on a wide Pearl stage it is the head of the console's pane), and the whole log folds behind "Ship's log"; the line is a live region while the log is folded and the log's list reads new lines while it is open, so no line is read twice.[^a-crew-line] On a phone the porthole and that strip stick under the header with a hard lower edge while the console scrolls beneath them, so no press scrolls the page; the porthole is sized (`--porthole` in `stage.css`) so once it sticks, a phone's screen holds the whole porthole, the captain's order and the depth lever under it (`stage.spec.ts` checks the strip covers nothing at rest and after a dive, light and dark).[^a-crew-line-phone] No toast on the voyage pages says what is already in view, and nothing moves the page for a note: a press is said once, by the crew's line or by the control itself (the hand-off's Copy is HX's `CopyButton`, which says "Copied" on itself).[^a-toasts] Every stage payoff (bubbles, the sight glasses filling and the manifold's pipe, the Ready line and Dive's ring, the tanks-full lights, the beam and the creatures it finds, the midnight glow, the bell, its sonar and the creatures it startles) has an opacity- or colour-only form under reduced motion, which `stage.spec.ts` checks by keyframe property;[^a-stage-reduced] every latency press must happen (the browser's interaction count) and produce an Event Timing entry unless it took under 16 ms, the API's floor; a press with neither fails the test, and a press's set-up (filling the tanks before Dive) runs and settles unthrottled, so only the press is measured.[^a-stage-latency] The site specs collect page errors and console warnings through `site/e2e/diagnostics.ts`, which ignores WebKit's unused-preload warning, in WebKit only and for the site's own fonts and chunks (a one-shot timer 3 seconds after load, so it depends on the machine's speed; in Chromium the same warning means a real preload mismatch and fails); a test of a one-off animation records it as it starts (`recordAnimations` in `stage.spec.ts`) instead of looking for it still running, and a test reads the stage, or clicks a popup's option, once it has settled.[^a-diagnostics] To keep presses fast, the porthole's picture follows the console's state from a task after the press's frame has painted (`useAfterPaint` in `stage.tsx`; a deferred render could commit before that paint and lay out the whole drawing in it), the scene animates nothing beside the hull (a moving shape there repaints the hull, beam and glass every frame), the bell's answer (and Chapter I's new, empty form) waits for the press's paint, the organ's tune builds its pipes after it (`playTune` in `organ.ts`), Nemo's museum keeps whether it is open to itself (`Museum` in `chapter-two.tsx`), so opening it renders only its Sheet,[^a-press-cost] and X-ray lives in `site/src/voyage/xray-store.ts`, read only by the header's Switch and the Inspector, which opens two animation frames after the press, once the press has painted. Live docs demos set `data-site-demo-ready` once their handlers are attached; tests wait for it and press once. The `lighthouse` job in CI, which is not a required check, runs `site/lighthouserc.json` against the build served as Pages serves it (`site/scripts/serve-pages.mjs`: HTTP/2, TLS, gzip).[^a-lighthouse] The site's end-to-end specs run against the build served the same way (`playwright.config.ts`, `https://127.0.0.1:4179/`), so they check what people get; under Vite preview's HTTP/1.1 server, WebKit sometimes failed a page's own requests or showed its HTML still compressed.[^a-site-e2e-server] Before any spec, `site/e2e/warm-up.ts` opens the voyage pages once in each site browser, since a fresh runner's first visit to one ran seconds slower than every later visit.[^a-site-e2e-server]
- Chapter I, "Build the ship" (`site/src/voyage/chapters/`): `chapter-one.tsx` holds the shipyard (Reorderable sets the order of work, Checklist ticks the jobs in that order, the engraved plan `nautilus-blueprint.svg` draws each part as its job is ticked, Progress fills, Launch floats the ship, and an HX Link under the plan leads on to Chapter II) and the ship's articles (an HX Form signs you on to the crew list, then steps aside for a line that you are aboard and the same link until you leave), each one framed application with a Code sheet that lists what is HX's and what is the site's; `copy.ts` holds every word (grade 6 or under, `chapter-one.test.tsx`) and `CHAPTER_ONE_CONTROLS`, each of which needs a `control: <id>` test in `site/e2e/chapter-one.spec.ts` and a latency test in `chapter-one.latency.spec.ts` (the same `latency.ts` budget, with the chapter's own `BASELINE_MEDIAN`).[^a-chapter-one] The chapter is an island (`island.tsx`): the server renders it whole, and in the browser its chunk loads only as it nears the screen, then React hydrates the server HTML; it marks `#chapter-one[data-chapter-ready]` once hydrated, which specs wait for before they press. `catalog.spec.ts` holds what the island adds to 60 KB gzip and keeps it out of the voyage's first load.[^a-island] A chunk that fails to load shows the island's fallback (`ISLAND_FALLBACK` in `site/src/voyage/copy.ts`, in a section with the island's id, with a link to reload) while the rest of the page hydrates, answers and still sets `html[data-site-ready]`; it is not retried in place, since the browser keeps a failed module fetch for the page's life.[^a-island-fails] Its styles come in two parts: `chapters.css`, how the server draws it (the plan and the rail's picture at rest; layout is utilities), loaded with the page's stylesheet so the server HTML is styled; and `chapter-one.css`, everything that changes once it answers (parts drawn in, the launch's slide, wake, bubbles and lantern flash, the yard growing, the crew's cheer, a pencilled-in signing, the Code sheet's wrapped lines), imported `?inline` into the island and put in the page as it hydrates, so it costs the first paint and the voyage's initial CSS budget nothing.[^a-chapter-styles] The voyage has a Tailwind build of its own (`site/src/voyage/voyage-tailwind.css`): the site's stylesheet less every registry component, every source file of a component it renders, and every site file that the voyage's import graph never reaches, islands included, a list `node site/scripts/page-css.mts` writes and `site:build` checks, so a new component, or a new part of one the voyage renders, adds nothing to the voyage's CSS until the voyage imports it.[^a-page-css] The docs split the same way: the docs' shared shell (`site/src/docs/shell.css`) links once and is cached across the docs, and a component's page inlines in its head only the classes its own demo adds (`site/scripts/docs-css.mts`), while the components index and the live demo page link the whole build; `site/e2e/catalog.spec.ts` holds each page to its budget.[^a-docs-css] The rail beside the chapter (held in view on a wide screen tall enough for it, 56rem) shows the chapter's picture and how the voyage stands; the shipyard and the articles write that state to a small store the rail reads, from the deferred plan, so a press never waits on it.[^a-rail] Each chapter's picture is a frosted-glass scene from ourostack/.github's `brand/` (`nautilus-shipyard`, `nautilus-library` and `nautilus-squid` in `site/src/storybook.ts`), the whole 3:2 frame with its night twin, in the rail on a wide screen and full width above the chapter on a phone (`ChapterPicture` in `frame.tsx`); the page opens on the `nautilus` scene, full width above its title, like the home page's hero.[^a-chapter-pictures] At the launch the plan becomes a painting of her afloat: the `nautilus` scene cropped to the plan's 3:1 by `site/scripts/plan-ship.mts`, which writes the files and a manifest of their sources into `site/public/plan-ship/`; `plan-ship.test.mjs` makes the crop again and compares.[^a-plan-ship] The crew's avatars show their faces from the same world, square crops of figures in those scenes (`crew-faces.ts`), which `node site/scripts/crew-portraits.mts --write` cuts into `site/public/crew/` with a manifest of each scene's checksum and box; the script test fails when a face is not its scene cut at its box, and a person you sign on keeps their initials.[^a-crew-faces] The ship that sails by when someone types "nemo" is a painting too: `node site/scripts/nemo-ship.mts --write` cuts the Nautilus, by day and by night, out of the `nautilus-shipyard-afloat` scene along a hand-traced mask, feathered inward, into `site/public/eggs/` with a manifest of each scene's checksum and mask, and the script test cuts her again and compares.[^a-nemo-ship] The articles refuse in Conseil's voice, and pencil you in, until the trade and the oath are given, with the browser's own messages under the fields; focus stays put: after Sign on your row's Leave, after Leave on the name field, after "Build her again" on the first job. The plan's and the vignette's manifest entries name `"chapter": "I"`, so they count against the chapter's 50 KB art budget, not the hero's.[^a-chapter-art]
- Chapters II, "Plan the voyage", and III, "Face the squid" (`site/src/voyage/chapters/`), are islands like Chapter I, each with its own chunk, `CHAPTER_TWO_CONTROLS` or `CHAPTER_THREE_CONTROLS` (a `control: <id>` test and a latency baseline for each), copy at grade 6 or under, and a Code sheet per composition.[^a-chapters-two-three-controls] Chapter II holds the chart room, the specimen book and the ship's radio (`chapter-two-radio.tsx`: ConversationList, Avatar with presence, MessageList and Message, ReactionBar and Composer), whose replies come from a script in `radioReply` (`chapter-two-copy.ts`), with no network and no AI; Chapter III holds the squid and the organ, whose tunes play through Web Audio only when the reader presses Play.[^a-chapters-two-three-radio] Every composition is an application's window (`Composition` in `frame.tsx`, drawn by Ouro HX's `AppWindow`, so apps get the same frame): its file and Code button in a title bar, and the Ouro HX components it is built from along its foot, from each Code sheet's `uses`.[^a-chapter-window] The voyage ends on the home page's hand-off to a coding agent (`HandOff`, `site/src/voyage/handoff.tsx`), not an install button, and the saloon's log holds only what has happened.[^a-voyage-end] The words stay friendly for readers who never read Verne: each crew member is named with their role (`ROLES` in `frame.tsx`), and the squid is coaxed off the propeller with a lamp, not fought; their voice is dry and warm, with no nursery words, no emoji and at most one exclamation a chapter (`voice` in `site/test/readability.ts`).[^a-chapters-two-three-roles] `catalog.spec.ts` holds each island to 60 KB gzip of its own code, not counting shared HX chunks (an HX component's chunk with the Base UI it is built on, `HX_MODULES`); none of them loads Recharts.[^a-chapters-two-three]
