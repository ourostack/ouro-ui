# Registry, install test, Pages and releases

How the registry is generated, what the install test proves, how Pages publishes the site and how a release is cut, pinned and recovered. Moved out of AGENTS.md, which keeps the rules an agent acts on and links here.

## Registry

- `scripts/registry.mts` derives everything from the layout.[^a-registry] Each component is two items.[^a-two-items] `<name>` ships the runtime source only: `<stem>.tsx`, `<stem>-parts.tsx` and `<stem>-styles.ts` (`registry:ui`), targeted at `@components/ouro/<folder>/`. The opt-in `<name>-tests` ships its tests and type tests (`registry:component`), stories and `e2e/ouro/<stem>.spec.ts` (`registry:file`, to `~/e2e/ouro/`), depends on `<name>`, `ouro-testing` and the `-tests` item of everything `<name>` installs, and names the Storybook, Vitest and Playwright devDependencies.[^a-tests-item] Each helper in `lib/ouro` is its own item, `lib-<stem>`, with `lib-<stem>-tests` for its tests, so a component installs only the helpers it imports (and `OuroProvider`, which only the app imports, comes with every component that renders links, through `lib-router-link`, and with `tooltip`, whose tooltips it groups; any other app adds `lib-ouro-provider` by name, which the README's Next.js steps do); `ouro-lib` and `ouro-lib-tests` depend on all of them, and `ouro-tests` depends on every `-tests` item.[^a-lib-items] A runtime item that needs a devDependency fails the generator. `registryDependencies` come from the `@/registry/...` imports, as full unpinned addresses (`ourostack/ouro-ui/<item>`; release tags pin them, see Pages and releases); npm `dependencies` come from the imports, at the caret range in this repository's `package.json`. `devDependencies` carry no version, because the CLI hands a versioned one to the package manager on every add, which would move a version the app pinned; the minimum each tool needs is in the item's `meta.requires` and in `docs/guides/testing.md`.[^a-dev-deps] No item depends on `ouro-base` or `ouro-theme`: an item with `css` or `cssVars` in its tree makes the CLI rewrite the app's stylesheet, so the app adds `ouro-base` once and no later add touches its CSS (`scripts/registry.test.mjs` holds both rules).[^a-ouro-base-only] The theme items' `cssVars` and `css` come from `registry/ouro/theme/*.css`; a theme file may hold only `:root`, `.dark`, `@theme inline`, `@utility` and `@keyframes`. Descriptions and docs messages come from `docs/<Component>.md`.
- The components come from each folder's `component.json` (`scripts/components.mts`): `{ "order": 70, "components": ["text-field", "text-area"] }` lists the folder's component file stems (item name `<stem>`, export name the stem in PascalCase, or the manifest's `titles` entry where an initialism keeps its capitals: `"titles": { "snap-pip": "SnapPiP" }`), and `order` places the folder in `registry.json` (equal orders sort by folder name).[^a-component-json] The manifest ships in no item.[^a-ships-once] A registry file no item ships fails the generator unless it is in `repoOnly`.[^a-ships-once] `pnpm registry` also writes `site/public/llms.txt`, the hand-written `site/llms.txt` with its `## Items` list filled in; edit `site/llms.txt`: `pnpm registry` overwrites the output.

## Install test

- The install test (`scripts/install-test.sh <shadcn|ouro|github|current|namespace|next|upgrade> <dir>`) runs locally too. Every variant adds `ouro-base` first and then checks that no later add changes the stylesheet by a byte.[^a-install-byte] The `shadcn` variant first strips `--input` and `--radius` from the preset's theme, so the shipped field spec proves `ouro-base` alone gives a field its border. With the test tools pinned to this repository's versions and a rule of its own in the stylesheet, it adds `sheet` and `button-tests` and compares the stylesheet and `package.json` byte for byte. It installs the runtime items into the bare fixture first and checks that they added no test, story, spec, test kit or test tooling, and that `npx vitest run` finds no tests;[^a-runtime-install] then it copies in `test/install-fixture-tests/`, adds `ouro-tests` and runs the shipped tests and specs. In the check job, the `shadcn` variant then adds the Node-only tools with the CLI (Ouro check, Ouro images and the Ouro AX kit with its tests) and checks that a strict tsconfig with no Node types passes with them where they land, that each Ouro AX file installed once, and that the kit's tests and `check.ts --help` run.[^a-node-tools] The `ouro` variant adds `ouro-theme` from GitHub at the ref when that commit has a `registry.json` (a release commit; push first), and otherwise from the locally built registry. Refs are not inherited by `registryDependencies`, so the script installs from a locally built copy of the registry whose dependencies point at the built item files (`--deps <dir>/{name}.json`). The `namespace` variant builds the namespace as Pages does, from the newest release tag (`scripts/namespace.sh`), serves it on localhost, registers `@ouro` in the app's `components.json` and installs `@ouro/dialog`, checking that every dependency came through the namespace, that no test item came with it, that each served item names that release and that every installed file equals the tag's source.[^a-install-namespace] The `next` variant creates a Next.js App Router app with `create-next-app` (TypeScript, Tailwind CSS v4, `src/`), runs `shadcn init` (which writes `"rsc": true`), adds every runtime item (the `registry:ui` items in `registry.json`, as every variant installs), renders each component from a Server Component page (ConfirmDialog's `onConfirm` is a server action) and runs `next build`.[^a-install-next] Each component has its own section, `test/install-fixture-next/src/app/sections/<item>.tsx`, whose `// expect: <pattern>` lines say what the prerendered page must hold; the script writes `sections/index.ts` from the files, and fails when a component has no section.[^a-next-sections] The `upgrade` variant installs `dialog` at `#v0.1.0` from GitHub (which brings `button` and `sheet`) into an app with the v0.1.0 test setup and a test of its own (`test/install-fixture-upgrade/`), then runs the commands in `UPGRADING.md` against this commit's registry, in two layouts.[^a-install-upgrade] In an `app/` layout with `~/*` aliases on `./app/*`, step 1 on an app with no Ouro component must stop without adding anything, then steps 1 to 3 run.[^a-install-upgrade] In the `src/` layout, steps 1 and 2 run, and separately steps 1 to 3.[^a-install-upgrade] Each app must type check, build, run its own test with its own config, keep the same components and have no self-referential token.[^a-install-upgrade] The note's commands find the app's folders with `npx shadcn info --json` (`resolvedPaths`), never a hard-coded `src/`; `scripts/upgrade-note.test.mjs` also runs them with a stand-in `npx` in bash and zsh.[^a-note-paths] The `current` variant installs ouro-base and every component of the newest release from GitHub at its tag, writes the install record a product keeps, and updates the app to this commit with Ouro Current exactly as a product is updated: `scripts/current/local-update.mjs` runs `keepRepo` against a GitHub in memory holding the app (`scripts/current/fake-github.mjs`, which the Current tests use too) and writes its pull request's change back.[^a-install-current] The stylesheet must then hold everything this commit's `ouro-base` adds (`install-check.mjs --theme-item`), every installed file must equal this commit's source, and an app already on this commit whose stylesheet is still the release's must get the same stylesheet; then the type check, the build and the shipped tests that compare a component's corners with Ouro's radius steps (`rounded-ouro-*`, `--radius-ouro-*`).[^a-install-current] A change to Ouro Current or to `ouro-base` that would leave products behind fails here before it ships. The `github` variant installs every component in the newest release from GitHub at its tag (`ourostack/ouro-ui/<item>#<tag>`), as a user does; CI runs it (job `install-github`) after each push to main.[^a-install-github]

## Pages and releases

- The site's host is https://ui.ouroboros.bot/, and new links use it. GitHub Pages builds the site and holds it at https://ourostack.github.io/ouro-ui/, with no custom domain; the `ouro-ui-host` Worker in `site/host/` serves it on the route `ui.ouroboros.bot/*`, fetching each path and query from Pages and keeping Pages' redirects on ui.ouroboros.bot; it sends plain HTTP to the same path and query on https with a 301, and every response carries HSTS.[^a-host] Deploy it with `npx wrangler deploy` from `site/host/`. The old host, ui.ouro.bot, forwards to the same path here from the `ouro-apex` Worker in ourostack/ouro-apps-site.
- `pages.yml` publishes https://ui.ouroboros.bot/ on every push to main, from that commit and without waiting for main's CI, which still runs (also runnable by hand):[^a-pages-push] the site at `/`, Storybook at `/storybook/`, and the `@ouro` namespace registry at `/r/<item>.json` and `/r/registry.json`. The site and Storybook build from main. Before it builds, Pages asks GitHub for the newest release and, when main's `ouro.latestRelease` names an older one, sets it and regenerates the docs in the build, so the site, `llms.txt` and the namespace name a release as soon as Pages runs after it, whether or not main has caught up.[^a-pages-release] Pages writes core's newest release into the Platforms pages the same way, before the site builds (`scripts/platform-versions.mjs --write`), and each other kit's newest release and components into the parity matrix (`scripts/parity-matrix.mjs --write`), so they name it without a pull request; the scheduled Apple checks hold only the Apple release those pages pin, and the Apple components the matrix pins with it, to GitHub.[^a-platforms-release] The namespace builds from that tag (`scripts/namespace.sh`: the tag's own `registry.json`, rewritten by `scripts/registry.mts --from <file> --deps "@ouro/{name}"`, then `shadcn build` over the tag's files), so each item's same-repo dependencies resolve through the namespace and `@ouro` serves released code only.[^a-namespace] Every install from GitHub needs a release tag: main commits no `registry.json`, so an address without a ref, or with a branch or a commit, fails with "did not return a root registry.json file".[^a-uncommitted] Pages deploys only when its push is main's current tip, so an older run that starts late never deploys over a newer one.[^a-pages-tip]
- Release cuts a commit main's own runs already tested; nothing is rehearsed or run twice. When a push to main finishes CI on a commit, Release auto (`release-auto.yml`) dispatches Release (`release.yml`) for the next patch version with that commit's `sha`, and Release tags that exact commit after it checks the commit is main's tip or an ancestor of it, that the checks main's rules require passed in main's own runs of it (`scripts/required-ci.sh`) and that `install-github` passed there; it writes those runs, and the screen-reader lane's run on the commit, to the step summary and the release notes.[^a-release-commit] If several commits land while a release runs, the release that follows takes the commit whose runs finished last.[^a-release-auto] The screen-reader lane (`screen-reader.yml`, on every push to main) is off the tag's path: it reads the same commit right after the tag, and when it fails twice on a commit after passing on the one before, `screen-reader-revert.yml` opens GitHub's revert of the pull request behind it, labelled red-main-fix and set to merge on green, so the next release carries the revert.[^a-sr-revert] Release auto waits for a newer commit when main's `.github/workflows` has moved past the one it would release (#1951).[^a-release-auto-workflows] A wait that lasts over an hour (scripts/release-wait.mjs, timed from the commit that brought the oldest pending change) opens or comments on "Release waiting" and fails Release auto.[^a-release-waiting] The `checks` job still rehearses the release commit's own edits on every run, so a check that needs the release's own tag fails on a pull request.[^a-release-rehearsal]
- Quarantine: `.github/quarantine.json` lists tests known to fail now and then, with its test (Vitest project, file and title), the open issue that tracks it, an owner and a deadline by when it must be fixed and brought back, or re-quarantined with a new deadline. An entry needs an open issue, and leaves with the fix. Release retries a run's failed jobs once, through `scripts/quarantine.mjs retry`, only when every failure is a quarantined test with an open issue; any other failure still stops it, and `quarantine-watch.yml` reports a stale or overdue entry after every push to main without blocking it.[^a-quarantine] Details: [contributing/ci.md](ci.md#quarantine).
- Nobody needs to dispatch a release: it starts when changes/ lists a change the newest release's notes lack, no release is running, and main's push CI has ended on the commit; a release's last job (`next`) starts it again for the commits that landed meanwhile, so a failed step cannot stall the train.[^a-release-auto]
- Release is `release.yml`, started by Release auto or by hand with a `version` such as `0.1.0` (`gh workflow run release.yml -f version=0.1.0`). It checks that the commit's push CI passed, force-pushes `release/v<version>` from main, after a guard that finds the released commit's `.github/workflows` equal to main's tip (GitHub refuses a push by the workflow's token that carries workflow content no branch holds, ourostack/ouro-ui#1951),[^a-release-workflows] with every same-repo `registryDependency` in `registry.json` pinned to `#v<version>`, a `version` field, and "Ouro UI v<version>." at the end of each item's `docs` message, so every `add` prints the version it installed (`pnpm registry --release <version>`).[^a-release-pins] It builds the `@ouro` namespace from that commit (`scripts/namespace.sh "$RUNNER_TEMP/ns" <tag>`) and checks it with `node scripts/public-registry.mjs verify-build "$RUNNER_TEMP/ns" HEAD`: every item in the commit's `registry.json` has its `<item>.json` and no other item is there, each item equals the commit's entry with its same-repo dependencies at `@ouro/<item>`, each file's `content` equals the commit's file byte for byte, and the namespace's `registry.json` is the commit's (the counts come from that file).[^a-release-namespace] Main's push CI and screen-reader lane have already run on the commit Release tags, so it runs no second suite.[^a-release-commit] The release itself needs no pull request.[^a-release-push] The release itself opens no pull request and does not edit main: Pages builds the site from main and names the newest release, read from GitHub at build time.[^a-no-prepare] The `pages` job starts once the tag exists: it dispatches `pages.yml` on main, waits for it (a dispatched run that a newer Pages run for main cancelled counts as done, since that run deploys main), then runs `node scripts/public-registry.mjs verify-live <tag> --wait 900`, which builds the namespace from the tag into a temporary folder, checks it as `verify-build` does, and fails unless Pages serves every item (`/r/<item>.json`) and the index byte for byte as built, with no other item in the served index (it retries while the deploy is stale).[^a-release-pages] The `publish` job, after `pages`, runs `node scripts/published-release.mjs <tag> --wait 900`, which fails when an install command in the published `llms.txt` names another release. Both modes run locally too (`verify-live` reads only public URLs). The daily `scheduled-install.yml` runs the same published-version check.
- After the tag is out, Docs pin (`docs-pin.yml`) points main's docs at the release. Release starts it and never waits for it. It runs `node scripts/latest-release.mjs set <tag>` and `pnpm run docs`, keeps one pull request open on the branch `docs/point-at-release` (force-updating it, titled "Point the docs at a release"), and turns auto-merge on, so the pull request merges once the checks main's ruleset requires pass.[^a-docs-pin] It pushes with the `DOCS_PIN_TOKEN` secret when the repository has one, and with the workflow's own token otherwise. A push with the workflow's own token starts no CI, so until the secret exists the issue drain pushes one empty commit to `docs/point-at-release` from the maintainer's account whenever the pin lags by more than 10 releases or 6 hours, which starts CI on the pull request.[^a-docs-pin-token] Release auto starts nothing for a commit that only does this: package.json changes only `ouro.latestRelease` and `description`, and every other changed file is a docs file whose version literals alone changed.[^a-pin-only]
- Core pin (`core-pin.yml`, on a schedule and by hand) points main's Platforms pages at core's newest release: it runs `node scripts/platform-versions.mjs --write`, which copies core's claim files, rewrites the pages that name core's release and keeps the claim cache in step with their links, and `node scripts/parity-matrix.mjs --render`, then keeps one pull request open on `docs/point-at-core` with auto-merge on.[^a-core-pin] The Pages build does the same at build time, so the site is current either way; this keeps the copy GitHub shows current. It is its own pull request, so a core release that breaks a test here can't hold up Docs pin's.[^a-core-pin]
- Kit pin (`kit-pin.yml`, hourly and by hand) points main's Platforms pages at each sibling kit's newest release, ouro-ui-apple, ouro-ui-windows and ouro-ui-android, one job per kit: it runs `node scripts/kit-pin.mjs --check <kit>`, then `node scripts/platform-versions.mjs --<kit> <tag>`, `node scripts/parity-matrix.mjs --write` (Apple only) and `node scripts/kit-pin.mjs --bump <kit>`, which moves each statement of the old release and keeps the claim cache in step.[^a-kit-pin] Each kit has its own branch, `docs/point-at-<kit>`, pull request and concurrency group, with auto-merge on.[^a-kit-pin] Its pull request runs the claims check, which verifies its version statements against the pages and GitHub, so a wrong citation fails it; a kit whose pages need hand edits, such as a component count that changed, stays open for a person.[^a-kit-claims] On main, apple release warns about a pin behind ouro-ui-apple's newest release for two hours after that release came out, then fails and files its "Apple pages are behind" issue.[^a-apple-judge] On a pull request it holds the pull request only once main has been behind for more than two hours, measured from that release's publication.[^a-apple-judge] A new Apple view that is a part of a component, as `OuroCheckboxMark` is, needs a manual `APPLE_PARTS` edit in `scripts/parity-matrix.mjs`: the pin cannot tell a part from a component, so until it is made the parity page lists the part as a gap.[^a-apple-parts]
- Rerunning is safe. If the tag exists and has a release, the workflow exits with a notice. A failed run deletes its branch, so rerun after fixing the cause. Recovery:
  - CI failed on the release branch: fix main, then run Release again.
  - The tag exists without a GitHub release (the run fails and says so): delete the tag with `git push origin :refs/tags/v<version>`, then run Release again.
  - A wrong release was published: delete it with `gh release delete v<version> --cleanup-tag`, then release a new version (prefer a new version over reusing a published tag).
  - The tag is out but main or Pages did not follow (a failed or timed-out `pages` or `publish` job; the `finish` job opens an issue saying so): run `gh workflow run pages.yml --ref main` and `node scripts/published-release.mjs v<version> --wait 900`.
- `ourostack/ouro-ui/<item>#v<version>` installs the item and all its Ouro dependencies at that tag, because the tagged `registry.json` names them with the same tag.[^a-release-pins]
- Install commands in the docs (`README.md`, `site/`, `site/public/llms.txt`, the release notes) use `npx shadcn@latest`, start with the `init` step (`init --base base --preset nova --yes --no-monorepo`) and pin the newest release tag. That tag has one source, `ouro.latestRelease` in `package.json` (`scripts/latest-release.mjs`): `pnpm run docs` writes it into README.md, llms.txt and package.json's description, the site imports it (`site/src/release.ts`), and Pages builds the namespace from it. Never edit a tag by hand: `scripts/latest-release.test.mjs` fails when a `#vX.Y.Z` or `@vX.Y.Z` literal in the docs names another tag. The same test and `site/src/site.test.tsx` fail on an install address with no ref or any ref but a release tag (`#main`, a branch, a commit; `scripts/addresses.mjs`), outside a sentence that says it is for contributors.[^a-addresses] release.yml sets the new tag on the release branch before it tags (`node scripts/latest-release.mjs set v<x.y.z>`, then `pnpm run docs`), so the tagged commit's README, llms.txt and site name that tag itself (UPGRADING.md keeps its placeholder) (`scripts/latest-release.test.mjs` runs those commands on a copy); Docs pin (`docs-pin.yml`) does the same on main through its pull request, which merges once its checks pass; until it merges, main's docs name the previous release.[^a-docs-pin] On the release branch, before the tag exists, `scripts/namespace.sh` builds the namespace from the checkout, whose `registry.json` already is that release. Release advises deleting a tag only when GitHub answers "release not found"; any other error fails with the raw message. `pnpm registry --check` reads only `registry.json`, so a tag in the docs never fails it; `registry.json` on main stays unpinned.[^a-main-unpinned] The install test and CI keep the exact `shadcn@4.21.1` they verify.
