# Testing machinery

The test suites and lanes beyond a component's own tests: the conformance matrix, mutation testing, ratchets, subset coverage, the README steps, links, the story-wide tests, screenshot baselines, Vitest projects, end-to-end specs, the screen-reader lane and the custom browser commands. Moved out of AGENTS.md, which keeps the rules an agent acts on and links here.

## Conformance matrix

- Conformance matrix (`pnpm conformance`, `test/conformance/`, CI's sharded `conformance` job; [docs/guides/conformance.md](../docs/guides/conformance.md)): every story, with nothing to opt into, through the checks that replace recurring review findings.[^conformance-matrix] After every action a person can take in it (a press, a character typed, an arrow key, Escape for each popup), focus is on an element still in the page and shown, and no live region announces the same text twice; its server HTML (UTC, en-US) hydrates in America/Los_Angeles with de-DE and Asia/Tokyo with ja-JP with no recoverable error or attribute mismatch; in a right-to-left page nothing sticks out of the viewport sideways; and under forced colours every box a person presses, types into, drags or scrolls keeps an edge, an on state looks unlike off, and keyboard focus shows; at a compact `--spacing` each icon keeps its size and a control stays 4px taller than its icon (`density.test.tsx`).[^conformance-matrix] A story states what a check cannot see in `parameters.conformance` (`focusExit` by the control's markers and name, `announces`, `clientOnly`, each with its reason), and a declaration that is no longer true fails; a pull request that adds an exemption (one of those, or a `scripts/physical-allowed.json` class) names it in its description with why (`scripts/conformance-exemptions.mjs`, the Conformance exemptions workflow).[^conformance-exemptions] Run one check or one component's stories while you work (`pnpm conformance test/conformance/rtl.test.tsx`, `pnpm conformance -t "Tabs/"`); `OURO_STORIES` and `OURO_CONFORMANCE_SHARD=<index>/<count>` select stories as CI does. Components hand focus on when a press removes them (`useFocusHandoff`, `lib/ouro/focus-handoff.ts`), keep a control that becomes unavailable where it is focusable (`aria-disabled`), read the time zone, locale, clock and randomness only after hydration (`useSyncExternalStore` with a server snapshot), use logical sides (`start-*`, `ms-*`, `pe-*`, `border-s`, `rounded-e`, `text-start`; `physicalUtilities` in `scripts/source-rules.mjs` fails on a physical one that `scripts/physical-allowed.json` does not list with its reason), and draw edges, states and focus that forced colours keep (`forced-colors:border forced-colors:border-solid`, `forced-colors:data-pressed:bg-[Highlight] forced-colors:data-pressed:text-[HighlightText]`, outlines rather than box shadows).

## Mutation testing

- Mutation testing (`pnpm mutation [<base>] [--only <file>] [--shard <i>/<n>]`, `scripts/mutation.mjs`, CI's `mutation` job on a pull request; [docs/guides/conformance.md](../docs/guides/conformance.md#tests-that-cannot-fail-mutation-testing)): Stryker changes each line the change added or altered in `registry/ouro/components/` and `registry/ouro/lib/ouro/` (not tests, stories or the test kit), one mutant at a time in each of its test runners (two side by side on four cores or more), and runs the mutated file's own tests in Chromium, then, for a mutant they miss, the tests of the components that import that `lib/` file (`scripts/mutation/plugins.mjs`, a Stryker runner over one Vitest instance).[^conformance-mutation-run] A mutant no test fails on fails the run, named by file, line, mutator and replacement: add a test that fails on it, or, for a change that cannot alter behaviour, write `// Stryker disable next-line <Mutator>: <why>` on the line before; any other Stryker comment a change adds fails the run, and so does a rise in the disable count the change does not show.[^conformance-mutation-disables] Tailwind classes in class positions (`className`, `cn()`/`cva()` arguments, `*Class` constants) and the `process.env.NODE_ENV` development check are not mutated; attribute names, selectors and markers are.

## Ratchets

- Ratchet property tests (`scripts/kits/ratchets.test.mjs`, fast-check from a fixed seed; [docs/guides/conformance.md](../docs/guides/conformance.md#ratchets-that-cannot-be-talked-around-property-tests)): whatever edit a generated case makes to the scan, the settings, the baselines, a rename or a removal, the census and source-rules ratchets never let a count rise, or a file go unread, without a recorded reason.[^conformance-ratchets] When a property fails, add the case fast-check shrank the failure to into the kit's own tests with the fix.

## Subset coverage

- An app that installs a subset with its tests must reach 100% coverage of the files it installed.[^a-subsets] `node scripts/subset-coverage.mjs` (CI's `ci` job) checks it for button, dialog, sheet, the form controls and their union: it runs only the tests in the closure of each `<name>-tests` item and measures only the runtime files in it.[^a-subset-closure] When it fails, cover the line in the item's own tests (a new `<stem>.<case>.test.tsx` beside it), never in another component's.

## README steps

- The README's Next.js steps are what CI runs: `scripts/readme-steps.mjs` reads the quick start's and the Next.js section's add commands and its two files, and the `next` install variant runs exactly those and builds before it adds anything else.[^a-readme-steps] The `shadcn` variant type checks the React Router adapter from `docs/OuroProvider.md` against React Router itself.

## Links

- Links: `node scripts/links.mjs` (in `pnpm test:scripts`, and again over `site/dist` in CI) fails when a link in the README, the docs, a guide or an install message opens no page, letter case included, or when a `docs/*.md` file has no page on the site.[^a-links] Hand-written guides live in `docs/guides/` (`installing.md`, `testing.md`, `forms.md`); `pnpm run docs` lists them, and every export's page, in `site/src/docs/pages.json`, and writes the README's item list between the `items` markers.[^a-guides]

## Story-wide tests

- `test/stories.test.tsx` renders every story through `composeStories` and runs axe (zero violations) closed and with each overlay open, light and dark, at 390px and 1280px, in Chromium and WebKit.[^a-stories] `test/stories.tsx` finds every `*.stories.tsx` by glob and keys it by its file name in PascalCase, so two story files may not share a name (it throws).[^a-stories-glob] A controlled story that opens its overlay from a plain button names it in the story's parameters (`parameters: { plainOpeners: ["Open"] }`), and a story that is a screenshot subject names its baseline there (`parameters: { screenshot: { name: "dialog-open", open: true } }`, with `forcedColors: true` for one more shot under forced colours); the visual test fails when a committed baseline has no such story.[^a-screenshot-subjects]

## Screenshot baselines

- Screenshot baselines (`test/__screenshots__/**/*-linux.png`, light, dark and reduced motion at 390px and 1280px) come from Linux CI only.[^a-visual] To refresh them, run the `visual-baselines.yml` workflow on your branch, download its `visual-baselines` artifact into `test/__screenshots__`, review and commit. CI compares with `pnpm test:visual` in its `visual` job. Both workflows pin `ubuntu-24.04`, the image that rendered the baselines; moving to a new image means regenerating them. Local runs on macOS write `*-darwin.png` files, which git ignores.

## Vitest projects

- On a machine several agents share, run local tests one file at a time through `bash scripts/local-test-gate.sh <command>`, which waits for a free test slot and for `memory_pressure` to report enough free memory; leave whole suites and mutation testing to CI.
- Test with Vitest browser mode. Projects: `ouro-chromium`, `ouro-webkit`, `ouro-touch` (files named `*.touch.test.ts(x)`, Chromium as a 390x844 touch phone), from `ouroTestProjects`, `visual` (files named `*.visual.test.ts(x)`, only when `CI_VISUAL=1`) and `themes` (`test/themes/`, Chromium, only when `OURO_THEMES=1`; it writes no motion evidence). nova, shadcn's default preset, is also checked with Ouro check's rules over every story at 1280 and 2560 px, past the root type step (`test/themes/nova-check.test.tsx`).[^a-projects][^a-nova-check]

## End-to-end specs

- End-to-end specs: `pnpm test:e2e` starts Storybook and runs `registry/ouro/e2e/` in Chromium and WebKit. The Skeleton frame comparison (`registry/ouro/e2e/probes/`, repository-only, `playwright.probes.config.ts`) runs as a daily and on-demand probe (`skeleton-frames.yml`) and files one issue when it fails; CI keeps only the check that no animation runs with `shimmer={false}`.[^a-skeleton-frames] The Route profile probe (`site/probes/`, `playwright.route-profile.config.ts`, `route-profile.yml`) runs on demand only: it times the slowest site routes in WebKit and uploads a Playwright trace for each.

## Screen-reader lane

- Screen-reader lane: `registry/ouro/e2e/screen-reader/*.sr.spec.ts` (repository-only, `repoOnlyDirs` in `scripts/registry.mts`) run with real VoiceOver (macOS, WebKit) and NVDA (Windows, Chromium) through Guidepup: `pnpm test:sr --project <voiceover|nvda>` (`playwright.screen-reader.config.ts`; `pnpm test:e2e` ignores them). `screen-reader.yml` runs them nightly on main and when dispatched with `source_sha`, the dispatched branch's tip; ci.yml calls its read-only lane, `screen-reader-lane.yml`, for a pull request from this repository whose change reaches a spec, the specs `scripts/sr-impact.mjs` names; release.yml dispatches it for its release commit and tags only when it passes there. `scripts/sr-classify.mjs` sorts a failure into accessibility (blocks the release) and infrastructure (retried once by a release; the nightly run files one `screen-reader-infra` issue).[^a-sr-classify] A run whose command Playwright refused, so no test ran, is harness: it fails without a retry or an issue.[^a-sr-harness] Guidepup's setup rewrites VoiceOver and TCC settings, so the lane runs only on GitHub-hosted runners, read-only and without secrets, and on a pull request only from this repository, never a fork's.[^a-sr-lane] `docs/guides/screen-reader-lane.md` is the runbook.
## Custom browser commands

- A `userEvent` keyboard, type or tab call that never answers fails its test naming the command, not only "Test timed out" (`registry/ouro/lib/ouro/testing/command-deadline.ts`).[^a-command-deadline] The stall reporter (`scripts/stall-reporter.mts`) names a test that has run for half its timeout, with the longest hold on Node's event loop while it ran, and names a hold of a second or more as it ends, with the tests in flight.[^a-stall-reporter]
- Custom browser commands live in `registry/ouro/lib/ouro/testing/commands.ts`: `commands.emulateMedia({ reducedMotion, colorScheme, forcedColors })` (it returns once the test frame's `matchMedia` matches each preference it set, so a test reads the new styles on its next line; a `forcedColors` switch returns once the transitions it started have finished, so a test reads where each colour lands), `commands.drag({ from, to, steps, durationMs, hold })` (`hold` keeps the button down so a test can inspect the mid-drag state; release with `pointerPress({ action: "up" })`), `commands.flick`, `commands.tap`, `commands.doubleTap({ at, gapMs })` (two taps with real touch input in one command, stamped `gapMs` apart in the page however late they arrive, for a double-tap), `commands.touchDrag({ from, to, steps, durationMs })` (a one-finger drag with real touch input through CDP, for swipe gestures; Chromium only; pass `durationMs` whenever the result depends on the swipe's speed, as over scroll snap points, because without it the speed is whatever the machine manages), `commands.touchStep({ type, x, y })` (one step of such a gesture, for a finger held still mid-swipe; lift the finger with `touchEnd` in a `finally`, and a finger left down is lifted before the next gesture) `commands.parkPointer()` (moves the mouse off the test frame; the two mouse projects run it before every test through `pointer-setup.ts`, so no test starts over a control an earlier test left hovered), `commands.pointerPress({ selector, action })` (holds the real mouse down so `:active` applies; `action: "click"` presses and releases in one command, so the release follows the press however loaded the runner, without the scroll into view `userEvent.click` makes first) and `commands.restoreTouch()` (turns Chromium's touch emulation back on; the `ouro-touch` setup calls it before every test, because a screenshot taller than the viewport, such as a failure screenshot of a tall page, drops it for the rest of the page's life, so read a burst of coarse-pointer failures in one touch worker on an older kit as one real failure plus fallout).[^a-touch-watchdog] Drag tests run in Chromium only.
