# CI, merging and the checks behind them

How Ouro UI's CI decides a pull request: the required `ci` check and its jobs, the CI budget, cancelling and yielding runs, which tests a change runs, required checks, pinned actions, the attribution check and the script tests. Moved out of AGENTS.md, which keeps the rules an agent acts on and links here.

## CI gates

- CI gates: `pnpm run docs --check`, type check, lint, unit and browser tests with 100% line and branch coverage (measured over `registry/**`, without stories, `registry/ouro/lib/ouro/testing/` and `registry/ouro/e2e/`), the script tests (including `scripts/app-lint.test.mjs`, which lints the runtime items' source with a stock Vite app's oxlint config and allows no warnings) and the Storybook build (job `ci`, which passes when the `checks` job, every `browser (n/4)` shard, every `subsets (n/5)` shard and every `scripts (n/2)` shard, every `design (n/12)` shard and, when the plan selected a screen-reader spec for a pull request from this repository, the `screen-reader` job's lane (`scripts/sr-impact.mjs`; `docs/guides/screen-reader-lane.md`) (Ouro check over the site's build at 390×844, 1440×900 and 3840×2160, light and dark, failing on a finding `.github/ouro-check.json` does not waive; a pull request that changes nothing the site build or the check reads starts none of its runners, the plan's `design` output) passed and the browser shards' merged coverage reaches 100%, `scripts/coverage-merge.mjs`, or after a fallback the `browser fallback (n/28)` shards' does).[^a-ci-check] The browser and script tests run in shards side by side, each with the files whose measured times add up to its share, a browser shard an even share of each Vitest project, since the projects run side by side (`scripts/shard.mjs`, `scripts/vitest-shards.mts`, `scripts/shard-timings.json`; `node scripts/shard.mjs refresh <dir>` rewrites the times from a run's `timings-*` artifacts), and the suites that iterate every story or page run in every shard over its own slice of them (`slicedSuites`, `test/slice.ts`); `pnpm registry --check`, `pnpm controls:matrix` and `shadcn registry validate` (job `registry`); `pnpm motion:coverage` over the motion evidence the browser shards upload, with `--expect` naming each Vitest project and shard count they write (job `motion-coverage`); axe over every story under each third-party theme fixture, `pnpm test:themes`, one fixture per shard (job `themes`); the conformance matrix over every story (focus, announcements, hydration under foreign time zones and locales, right to left, forced colours), every *n*th story per shard (jobs `conformance (n/3)`, and `conformance`, which passes when every shard did); mutation testing of a pull request's changed runtime lines (jobs `mutation-plan`, `mutation (i/n)` (as many shards as the changed lines' estimated work needs, at most 24 and at least five cold or three warm, none when no changed path is runtime source, split by changed range, a long component body cut into parts with a spanning unit for what the cuts cross) and `mutation`); the end-to-end specs against Storybook (job `e2e`, over the `e2e (n/8)` shards (`e2e (n/3)` on a push to main, which waits on nobody and leaves runners to pull requests; `sweeps` and `install` likewise run 4 and 3 shards there), each with the spec files whose measured times make up its share, on a reduced pull request of the selected specs, `node scripts/shard.mjs e2e`; the site's sweeps run in the `sweeps (n/14)` shards beside them, each of which saves the looks its pages have, and the `sweeps-compare` job runs the sameness comparison over every shard's looks at once (`scripts/sweeps-compare.mjs`), so a component that looks different on two pages fails whichever shards the pages land in, and a route that moves a page to another shard changes nothing); and the install test (the `shadcn` and `ouro` variants each in two `install (variant, preset, n/2)` shards that each run half of the shipped tests by measured time (`node scripts/shard.mjs install`), whose markers the variant's `install (variant, preset)` check counts; job `install`: the `namespace` and `next` variants; job `install-upgrade`: the `upgrade` variant; job `install-current`: the `current` variant).[^a-ci-gates] The `ci-budget` job, a required check, records each run's critical path (the longest chain of jobs that wait on one another, queues left out), its wall time with queues, the median and 90th percentile of that over the latest runs of the same event, and the runner time it took from the shared pool.[^a-ci-budget] A pull request whose critical path is over the budget in `scripts/ci-budget.mjs` is judged on its work time (the critical path with setup steps left out: the runner's, checkout, pnpm and Node, the install, the browsers): more than three minutes over main's, or past the ceiling (10 minutes, or 1.5 times main's work time), fails the check when the run's earlier attempt (after "Re-run all jobs") or the pull request's previous full run was past it too, warns when that was not, and with neither fails asking for all jobs to be run again; otherwise it gets a warning (`judge`).[^a-ci-budget-gate] A full-suite fallback run is not judged.[^a-ci-budget-gate] Main's baseline is the median of the critical paths, and of the work times once all five recorded one, that main's latest five merge queue runs that passed (every job but `ci-budget`) recorded in their own `ci-timings` artifacts.[^a-ci-budget-gate] A pull request run with a job that no ci.yml job name matches fails the check, since its critical path would leave that job out; a merge group or a push run only warns, so the required check never bounces a queue entry.[^a-ci-budget-gate] Run the tests your change touches locally (`pnpm exec vitest run <files>`, `node --test <file>`); the full suites run in CI. Pull requests merge into main by auto-merge once the checks the `main` ruleset requires pass (strict off), with no merge queue.[^a-merge-queue] On a pull request, a newer push cancels the run in progress, and one watcher (`scripts/ci-fail-fast.mjs`, run by `.github/workflows/ci-fail-fast.yml` for every pull request's run, so no runner is held for each run) cancels a run once a job other than `latency` (which a slow runner can fail) has failed and finished, so a red job frees the run's runners soon while keeping its failure conclusion, log and artifacts; no job waits on it, and the merge queue, main and dispatched runs are never watched and run every job to the end.[^a-fail-fast] The jobs a cancelled run had not finished report cancelled and `ci-budget` does not run, so the pull request stays blocked until a push or a re-run passes.[^a-fail-fast] A pull request's plan first yields to the merge queue (`scripts/ci-yield.mjs`): while a merge group's run has a job waiting for a Linux or Windows runner, it waits, reading once a minute, before any of the run's other jobs queue, so the queue's jobs take the organisation's shared runners first.[^a-yield] It lets the run start once nothing waits, after 20 minutes, on a rate limit or after three failed reads, and `ci-budget` leaves the wait out of the critical path and the work time.[^a-yield] The screen-reader lane yields to main's lane in the same way, through `scripts/sr-yield.mjs`.[^a-sr-yield-ci] `.github/required-checks.json` lists the checks that ruleset requires, and `required-checks.yml` compares it with main's live rules hourly and on a change to it, opening a "Required checks drifted" issue when they differ, at most daily; an API error is no drift (`scripts/required-checks.mjs`).[^a-required-sync] Change the ruleset first, then, in one pull request, the file and whatever names that check as required or advisory: the assertions in `scripts/workflows.test.mjs` and the text here. A push to main never tests a tree that already passed: the plan's `tested` output (`scripts/ci-proof.mjs`) is true when the merge queue's run passed on that very commit (the queue fast-forwards main to the commit it tested), or when the newest CI run of the pull request merged as the commit passed and its `tree-proof` job, named `Full suite passed on tree <tree>`, names the commit's tree (`git rev-parse HEAD^{tree}`).[^a-tree-proof] A pull request's run reports `tree-proof` only when its plan left nothing out (every browser test, the design shards, the install test and the heavy tier) and every job it waits on passed, so a reduced run proves nothing; equal trees are equal files, workflows and tests included.[^a-tree-proof-job] The push run then runs only `install-github`, waiting up to 3 minutes for the pull request's run to finish, since the required checks let it merge while `tree-proof` may still be running; a pull request whose run tested an older main, a red or unfinished run, a direct push or an API that does not answer runs everything.[^a-tree-proof-wait] The release check takes main's CI runs on its commit, the queue's and the proving pull request run included, and passes a required check one of them passed.[^a-queue-tested] Release also stops when `install-github` did not pass in main's own run on that commit, a push or a dispatch on main, since the rules cannot require a job the queue's run skips; when main's commit has no run of its own, as for a Prepare-main tip the queue's run reused, the queue's run alone decides and this gate is skipped.[^a-release-github] The `checks` job also rehearses the release commit: it writes what release.yml's release commit changes (`scripts/release-commit.sh`) for the next patch version, whose tag does not exist yet, then runs `pnpm registry --check`, `pnpm run docs --check`, `pnpm claims:check` and `pnpm site:build` over it, so a check that needs the release's own tag fails on a pull request rather than at release time.[^a-release-rehearsal] A pull request into main runs the browser tests its change can affect (`scripts/test-impact.mjs`, CI's `plan` job): the tests of the components whose folder, spec or docs demo it changed and of every component that imports them (through their own code, or from their tests, stories and docs demo), the tests of every folder those components' tests, stories and docs demos import (one step out) and of every folder the code of any of those imports, and of the `lib/` files all of them load, the shared suites in `test/` over only those components' stories and demos plus the reference stories (`OURO_STORIES`, `selectedStories` in `test/stories.tsx`, `test/story-selection.ts`), the site's tests, the `themes` scan of those stories, their end-to-end specs, their shipped tests in the install shards (none when no component is selected) and the subset-coverage sets that install them, with coverage measured over all those folders and `lib/` files (when only coverage falls short, the job `coverage` says so and the full suite decides, run as a full run runs it in the `browser fallback (n/28)` shards, in the browser shards' Playwright image so text lays out as it did there, whose merged coverage the `ci` job holds to 100%) and `motion-coverage --stems` holding their motion maps complete.[^a-impact] A pull request into main whose every changed file is one the browser tests never read (a change fragment, a Node script test, an end-to-end spec, another workflow) skips the browser shards altogether, and the `coverage`, `ci` and `motion-coverage` checks pass without them; a path `scripts/ci-relevance.mjs` does not list, and a diff it cannot read, run them.[^a-relevance] The plan job's summary prints how many of the repository's runs are queued.[^a-queued] A change to the theme, `lib/`, `test/`, `scripts/`, configuration, dependencies, a workflow, the site's stylesheet or a site file the docs demos load, or one the plan cannot map, runs everything, and so do pushes to main, the merge queue, dispatched runs (release.yml's CI on the release branch) and release branches.[^a-impact-full] Every required check still reports on a reduced run: when the heavy tier runs on a pull request, the `themes` shards pass as "Not affected" when no component changed.[^a-required] A pull request into main runs the install test (the `install (variant, preset, n/6)` shards, their variants' checks, `install` and `install-upgrade`) and the heavy tier (`themes (n/3)`, `visual`, `theme-install`, `latency` and `lighthouse`) in full, whatever it changes: the merge queue is gone, and a skipped required check counts as passing, so nothing may skip.[^a-installs-queue] The end-to-end shards (`e2e (n/8)`, `sweeps (n/14)` and `sweeps-compare`) skip together with the heavy tier when a pull request changes only files on the quiet list, and the `e2e` check then passes as "Not affected". They skip too, and the plan selects no component, for a docs pin, a pull request that only moves the release tag the docs name (`scripts/pin-only.mjs`, the same test release automation uses); `scripts/parity-data/*.json` starts no install shard and selects no component, but still runs the browser, design and heavy tiers, since the site's Apple pages render it.[^a-docs-pin] Workflows pin every action to a full commit SHA with a `# vX.Y.Z` comment, and only the jobs that push a branch (release.yml's release job) keep the checkout's credentials (`scripts/workflows.test.mjs`); Dependabot proposes new pins weekly (`.github/dependabot.yml`).[^a-pins] `scheduled-install.yml` runs the install matrix weekly against main and the newest release tag, because item dependency ranges float, and fails when main's `ouro.latestRelease` is not GitHub's newest release.[^a-scheduled] Any failure opens, or comments on, one "Scheduled install failed" issue (`scripts/scheduled-failure.sh`), so it shows where we look. GitHub pauses scheduled workflows in a public repository after 60 days with no repository activity, and the pause raises no issue: after a quiet spell, check that the workflow is still enabled (Actions, or `gh workflow enable scheduled-install.yml`).[^a-github-pause]

- The `main green` status: `.github/workflows/main-green.yml` posts it on open pull requests into main (`scripts/main-green.mjs`) after CI runs on main, when a pull request into main changes, and by hand.[^a-main-green-trigger] It fails while main's newest completed CI run on main failed; runs still in progress, cancelled or skipped are passed over, and only a success is green.[^a-main-green] A pull request labelled `red-main-fix` may merge while main is red, and so may this repository's docs pin (`docs/point-at-release`) and its automatic `Revert "` pull requests, when they come from the repository itself.[^a-main-green-exempt] The `main` ruleset does not require the status yet.[^a-main-green-unrequired]
- The docs pin also runs on pushes to main, through the stale job in `docs-pin.yml`.[^a-docs-pin-refresh] It points the docs at a release again when a `#v` or `@v` literal in the public docs names another tag than `ouro.latestRelease` (`node scripts/latest-release.mjs check`), or while its pull request is open. While the pull request is open, the release is the one its own `ouro.latestRelease` names, since main's still names the release it replaces, so the pull request is regenerated on the main it merges into and its CI reruns before auto-merge, unless the pull request already holds exactly the files and contents the run generated and none of its checks failed or were cancelled: then nothing is pushed and its CI keeps running, so a busy main does not restart it every few minutes.[^a-docs-pin-refresh]

## Headroom

- Browser shards hold a test to half its own timeout (the test's, else the project's `testTimeout`): a slower test fails the run, and the message names the test, its time and its budget (`scripts/headroom-reporter.mts`, rule in `scripts/headroom.mjs`, tests in `scripts/headroom.test.mjs`). A test near its budget can pass on a quiet pull request runner and time out on a loaded shard, so the pull request that adds it sees it first. Tests already over half are named in `.github/headroom.json` as entries with a `test` (`<project> <file> > <full name>`), a `reason` and an `owner`. Fix the test or give it a larger timeout instead of adding a name. An entry whose test file or title is gone from the source fails as stale (`staleExemptions` in `scripts/headroom.mjs`): remove it. Run times swing too much between runners to judge an entry from them.

## Script tests

- Script tests: `pnpm test:scripts` runs them with a temp folder of their own (`scripts/run-script-tests.mjs`), removed afterwards, and warns about anything left in it (`OURO_STRICT_TMPDIR=1` fails the run instead, to hunt a leak); a test that needs a folder outside the repository makes it with `scratchDir` (`scripts/scratch.mjs`), which removes it after the file's tests. The script tests are every `.test.mjs` file under `scripts/` and `site/scripts/`, except `scripts/kits/`, which `scripts/kits.test.mjs` runs; `scripts/script-tests.mjs` finds them, so a new one needs no edit to `package.json`.[^a-script-tests] A script or test that walks the repository's own folders lists them with `treeFiles` and copies them with `copyTree` (`scripts/tree.mjs`), which never enter a folder `.gitignore` ignores, so a test's scratch folder (`registry/ouro/ax/.tmp/`) that another test removes mid-walk cannot fail it.[^a-tree-walk]

## Actions caches

- Only main saves caches. Every save in `ci.yml` and in the Playwright browsers action is guarded to `refs/heads/main`, so a pull request restores main's caches and saves none that only it could read; the mutation job's incremental results are the one exception, keyed by pull request on purpose.[^a-cache-main-only] `cache-prune.yml` (`scripts/cache-prune.mjs`) runs after main's CI and hourly, deleting each pull request's caches and, on main, all but the newest entry of each key family, so the repository stays under its cache size limit.[^a-cache-prune] setup-node's `cache: pnpm` still saves on a key miss from a pull request, since its input has no switch for saving; the prune removes those entries too.[^a-setup-node-cache]

## AI attribution

- Never add AI attribution to commits, pull requests, code or docs (no `Co-Authored-By`, no "Generated with"). CI enforces it for commits: the `attribution` job, part of the required `ci` check, runs `scripts/attribution.mjs` over a pull request's commits (their authors and committers, and the pull request's title and body as the message that lands, since merging with `gh ouro-pr` passes them as the commit message and GitHub would otherwise copy the AI trailer a cloud signer forces onto branch commits) and over the squash commits the merge queue builds from them, and fails on an author other than the maintainer's address or release.yml's `github-actions[bot]`, a committer other than those or GitHub's `noreply@github.com`, a `*-by:` trailer naming an AI tool or a bot other than release.yml's, or a "generated with" line naming an AI tool; a range it cannot read fails too.[^a-attribution] Each failure prints its commit, its field and the command that fixes it.[^a-attribution] The same job, and the Claims workflow when a description is edited, fail a pull request whose title, body or commit messages name an internal app, repository or organization, with ourostack/.github's guard (`tools/internal-names`), whose one list is kept as hashes; write "an app" or "a consuming app" instead.[^a-internal-names]
