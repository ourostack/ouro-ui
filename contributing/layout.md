# Repository layout in detail

The full description of the folders that AGENTS.md's Layout section lists in short. Moved out of AGENTS.md, which keeps the rules an agent acts on and links here.

## Layout

- `registry/ouro/lib/ouro/testing/`: the test kit the `ouro-testing` item ships: the `act` helper, the custom browser commands, `pageCss()`, the motion helpers (`motion.ts`: `expectMotion`, `expectNoMotion`, `expectGestureSettle`, `expectTransition`, `parseDuration`; see Component conventions), `watchAnnouncements` (`announcements.ts`: what live regions announce, by region and text, so a test proves a message is heard once per change), `axeExclude` (`axe.ts`, the Base UI focus guards to leave out of an axe scan), `commands.compositedLayers()` (Chromium's composited layers and the elements they draw, so a test proves motion lets its layers go once it settles), `watchLayoutReads` (`layout-reads.ts`: the reads that lay the page out, so a test proves a render that changes nothing a component measures costs no forced layout), `pressTab()` (`tab.ts`: Alt+Tab in WebKit on a Mac, where plain Tab skips buttons and links unless the system's "Tab reaches buttons" setting is on; tests and specs never press Tab directly, and `directTabPresses` in `scripts/source-rules.mjs` fails on one), the console setup (`setup.ts`: any console output fails a test, in every project, including output at load or between tests, which fails the next test, and a console mock left in place, which would hide later output; it drops only Vitest's print of the browser's "ResizeObserver loop" notice, so a test for a component that may raise it listens for the window's `error` event itself; and it keeps media emulation (reduced motion, forced colours, colour scheme, contrast) to its file: each file starts from the browser's defaults, a file's `beforeAll` may set media for all its tests, and each test puts back the media it found, so a test that sets one does not change the tests after it) and `ouroTestProjects` (`vitest.ts`; its `page` option sets the page size for Vitest 4), the Vitest browser projects apps add to their config.[^a-testing-kit] This repository's `vitest.config.ts` uses the same projects.
- `registry/ouro/e2e/ouro/`: one Playwright spec per component, installed to an app's `e2e/ouro/`, and `story.ts`, which opens a story by id in the Storybook at `OURO_E2E_URL` (default `http://localhost:6006`). Specs ship as `registry:file`, which the CLI does not rewrite, so they import only `./story` and `../ouro-fixtures`: `test` and `expect` come from `e2e/ouro-fixtures.ts`, a file each app owns and no item ships (`testingSetup` prints it; this repository's copy is `registry/ouro/e2e/ouro-fixtures.ts`), so an app's own fixtures apply to Ouro's specs and an update never rewrites the import.[^a-spec-imports] `scripts/registry.test.mjs` fails on a spec that imports `@playwright/test`.
- `registry/ouro/theme/ouro-base.css`: required in every app, added once (no component depends on it).[^a-ouro-base] Defaults for `--input` and `--radius` with their `@theme inline` mappings, so a field has its border and corners under a theme that defines neither; the success and warning pairs and `--destructive-foreground` (which shadcn's themes lack), the `--ouro-*` motion tokens, `--ouro-layer` (the z-index of the Dialog and Sheet portals, 50 as in shadcn's overlays), `--ouro-shadow-sheet-<side>` (shadcn's `--shadow-*` scale has no upward or sideways shadow), the `press` utility and the keyframes.[^a-ouro-base-contents]
- `test/install-fixture/`: the bare Vite app the install test (`scripts/install-test.sh`) copies, runs `shadcn init` in and installs every component into, with no test config.[^a-install-fixture] `test/install-fixture-tests/`: the files the `ouro-testing` docs message tells an app to add (`vitest.config.ts`, `.storybook/`, `playwright.config.ts`), which the install test copies in before it adds `ouro-tests`. `test/install-fixture-upgrade/`: what the `upgrade` variant adds on top of those: a Vitest config with a project for the app's own test beside `ouroTestProjects`, and that test.
- `changes/`: the behaviour changes since the last release, one fragment file per change (`changes/<any-name>.md` holding `- ` lines), so parallel pull requests edit different files. Each non-blank line is one change, a top-level `- ` line (no wrapped lines or sub-items); `check` fails on anything else. release.yml assembles them, by file name, into `CHANGES.md` on the release commit only, so the tag holds the "Changes in this release" section and the release notes print it at the top (`node scripts/changes.mjs assemble changes` prints it); main keeps the fragments only.[^a-changes] Add a fragment when a change alters what an app sees (a stacking level, a focus target, a dependency range). Release refuses to start while the fragments list no change that `changes/` at the newest release's tag did not already hold (`scripts/changes.mjs check changes --since <tag>`). Fragments stay on main after a release: release.yml's release commit assembles only the lines that were not in `changes/` at the newest release's tag, so no pull request follows a release, and Release auto counts a fresh line the same way (`releasedAt` in `scripts/changes.mjs`).[^a-no-prepare] Measured against the newest release's notes instead, the release after it listed the one before's changes again (#1485).[^a-since-tag] The release job opens no pull request; each workflow that reports a check main's rules require is dispatched on the release commit, and each wait judges the checks main's rules require, not the runs' overall conclusion, which an advisory job (`ci-budget`) also sets (`scripts/required-ci.sh`).[^a-release-required] The release commit must also pass ci.yml's `install-latest` job, a gate main's rules cannot require because main never runs it (`required-ci.sh --also`).[^a-release-latest]
- `UPGRADING.md`: "Upgrading from v0.1.0", the one copy of the note, with a short "What changed, by version" list of the changes an app must act on (keep it in step with `changes/` when a release adds one).[^a-upgrading] Its addresses end in `#{{latestRelease}}`, a placeholder each copy fills, and a line under its title tells readers of the raw file what it stands for; every copy drops that line (`rawHint`): `pnpm run docs` copies its body into README.md with the newest release, the site's Updating page renders it the same way, release.yml prints it into the release notes with the release tag, and the `upgrade` install test runs its commands (`scripts/upgrade-note.mjs`).[^a-upgrading] Edit only this file; `scripts/upgrade-note.test.mjs` fails if a copy of a command appears anywhere else.
- `test/`: the story-wide accessibility test, the screenshot test and their baselines, and `stock-theme.test.tsx`, which checks every tone and variant at 4.5:1 under stock shadcn variables (`test/shadcn-stock.css`, copied from `shadcn init`) plus `ouro-base.css`, and under the Ouro theme.[^a-stock-theme] `theme-fixtures/` holds third-party themes as an app's stylesheet has them (only `:root`, `.dark` and `@theme inline`, each naming its source and version in its header): `nova.css` and `vega.css` from shadcn's presets and `cookbook.css` from Spoonjoy; `theme-fixtures.ts` puts one in place of the Ouro look at runtime.[^a-theme-fixtures] `test/themes/` runs `story-axe.ts`'s scan of every story under each fixture in light and dark (the `themes` project, only with `OURO_THEMES=1`: `pnpm test:themes`); a violation the fixture's own values cause is pinned in `themeFindings` (`test/themes/theme-findings.ts`) node by node (phase, rule and selector) with its reason: the story must flag exactly those nodes, so a new failure in it still fails and the entry fails once the theme is fixed (`test/theme-findings.test.ts`).[^a-theme-findings] `theme-tokens.test.tsx` sets every shadow and font token to a sentinel and checks that each story reads them.[^a-theme-tokens] nova is also checked with Ouro check's rules over every story at 1280 and 2560 px, past the root type step, in `test/themes/nova-check.test.tsx`.[^a-nova-check]
- `scripts/agent-usability/`: the agent-usability test (spec §8), which measures success criterion 1.[^a-usability] Fresh agents build five screens (`screens/<screen>/task.md`, with the `src/api/` stand-in for the backend in `files/`) three ways, three times each: shadcn/ui, shadcn/ui with its official skill, and Ouro HX (`arms/create.sh`, which also records each arm's baseline: what `tsc -b` and oxlint find before any agent runs).[^a-usability-arms] `score.mts <arm> <screen> <app-dir> --arm-record <arm.json>` judges a result with no model calls: `tsc -b` and oxlint errors that are not in the baseline, axe-core's WCAG A and AA rules at 390px and 1280px in light and dark, and the screen's behavior checks (`checks/<screen>.mts`).[^a-usability-score] `formula.mts` defines the score and is the only place that documents it. The scores are published beside shadcn/ui's, so no arm may gain or lose a point for anything but what its agent did: every check must be stated in the prompt (`prompt.mts`) or the task, in behavior or accessibility terms, and when a task changes, its checks and its known-good screen (`test/screens/`) change with it.[^a-usability-fair] `preflight.mts` proves the scorer in a real arm app, `table.mts` writes the results table with the pinned versions, and `page.mts` is the hook for the docs page that will show it. Agent output is committed under `runs/<date>/<arm>/<screen>/<run>/` with each arm's record in `runs/<date>/arms/` (ESLint ignores it), and `agent-usability.yml` scores the newest run weekly and on demand into its job summary; it is not a required check.[^a-usability-workflow] `README.md` there is the runbook, with the exact prompt and the exact command that starts a fresh agent. `score.test.mjs` (in `pnpm test:scripts`) proves the scorer on a known-good plain-React version of every screen and on broken copies.[^a-usability-scorer]
