# Contributing to Ouro UI

Rules for people and coding agents who change this repository. (Consumers read `README.md` and `docs/`, not this file.)

## Names

Use these names, exactly, on every surface: code comments, docs, the site, pull requests and replies.

- **Ouro UI**: the whole kit, and the parts below are its parts. Don't call it "a React component library", and don't let one part stand for it.
- **Ouro HX** (human experience): components for the screens people use, one kit per platform. Say which: Ouro HX for web (this repository), for Apple, for Windows, for Android. Ouro HX is a part of Ouro UI, not the whole.
- **Ouro AX** (agent experience): the doors agents use instead of a screen (command lines, APIs, MCP servers, App Intents, AppFunctions, Windows App Actions), a standard of checkable promises for them, and a kit that keeps the promises. Say what a door is where the word first appears on a page.
- **Actions**: an action declared once becomes the button a person presses and the tool an agent calls. Each is a read, a write, consequential (the person confirms first) or person-only (no agent door offers it).[^a-names-consent]
- **Composed UI**: an agent sends a card as data; Ouro checks it against the app's list of components and actions, and each kit draws it natively.[^a-names-composed] MCP Apps and A2UI are formats it speaks.
- **X-ray**: **HX X-ray** outlines and names every component on a screen; **AX X-ray** calls every door the way an agent would and says which promises hold.[^a-names-xray]
- **Ouro check** opens every page at every screen size, light and dark, and reports what's broken.[^a-names-check] **Ouro Feel** measures how an app feels in use. **Ouro Reins** drives an app's own screens as state and actions, for tests. **Hackamore** ([ourostack/hackamore](https://github.com/ourostack/hackamore)) drives Mac apps for agents, and is part of the Ouro UI family.
- **Ouro Current**: each Ouro UI release arrives in an app's repository as one pull request.[^a-names-current] **Adoption**: the public board of the products that use Ouro UI.

Page titles follow the names: a component page ends "· Ouro HX for web", and a guide or any other page about the whole kit ends "· Ouro UI".

## Merging pull requests

Follow ourostack's shared [PR merge rule](https://github.com/ourostack/.github/blob/main/agents/prs-merge-within-30-minutes.md). Finish, review and validate on your branch first, then publish with `gh ouro-pr`, which turns auto-merge on so green means merged. When a PR here shows on the [PR clock](https://github.com/ourostack/.github/issues?q=is%3Aissue+is%3Aopen+label%3Apr-clock), act on it now: merge it if green, fix the cause if red (file an issue before any rerun), rebase it if conflicted, or close it with a reason if it isn't going anywhere.

**Deliver finished work without being asked.** An agent working in this repository, including a GitHub Copilot app session in the owner's own checkout, commits its finished work, pushes its branch and opens its pull request with `gh ouro-pr` (auto-merge on) without waiting for a request. Host defaults that wait to be asked before committing or pushing give way to this file. It doesn't cover force-pushing shared history, pushing straight to `main`, or committing changes another session left uncommitted.

**Claim an issue before you build it.** Follow ourostack's shared [claim rule](https://github.com/ourostack/.github/blob/main/agents/claim-before-building.md): look for an existing claim first, then run `gh ouro-pr claim <n>` (with `OURO_SESSION` set to your session's name) before you open a branch, and coordinate with the claimant instead of building beside them. `gh ouro-pr` refuses a pull request for an issue another session holds; a claim with no activity lapses on its own, and `--take-over "<reason>"` overrides a live one with the reason posted on the issue.[^a-claim] A pull request opened only to read a CI result is a probe: name its branch `probe/…` or pass `--probe`, and it is labelled `probe` and is not merged.[^a-probe]

## Project constraints

- Copy-in source distributed as a shadcn/ui registry; MIT license, repository `https://github.com/ourostack/ouro-ui`. There is no npm package and no build: apps compile the components with their own Tailwind CSS v4.[^a-tailwind]
- Copy no code from Tailwind Catalyst or Tailwind Plus: ideas only.
- Touch targets are at least 44px on coarse pointers (`@media (pointer: coarse)`).[^a-touch]
- With `prefers-reduced-motion: reduce`, nothing moves, draws or scales: no transform, position, size or `stroke-dashoffset` change animates.[^a-reduced] Only `opacity` and colour properties (`color`, `background-color`, `border-color`, `outline-color`) may transition, over `--ouro-duration-fast`, so a checkbox's tick fades in whole and its box changes colour. Every component's `reduced` lists in `component.json` `motion` hold to this.[^a-reduced] Make a translucent surface honor `prefers-reduced-transparency` (solid surface, no blur) and `prefers-contrast: more` (solid background, defined border).
- The default breakpoint `sm` is 640px.[^a-sm] Below it, `Dialog` with `presentation="auto"` renders as a sheet.
- CI gates, and the jobs behind the required `ci` check (shards, the CI budget, cancelling and yielding runs, which tests a change runs, required-checks sync, pinned actions, the scheduled install): [contributing/ci.md](contributing/ci.md#ci-gates). Run the tests your change touches locally (`pnpm exec vitest run <files>`, `node --test <file>`); the full suites run in CI. To change a required check, change the `main` ruleset first, then, in one pull request, `.github/required-checks.json`, the assertions in `scripts/workflows.test.mjs` and [contributing/ci.md](contributing/ci.md#ci-gates). Pin every action to a full commit SHA with a `# vX.Y.Z` comment (enforced: `scripts/workflows.test.mjs`).[^a-pins] The CI time summary (`scripts/ci-budget.mjs`) prints the screen-reader lane's own critical path on its own line, judged against `laneBudgetMinutes`: report-only until the first 10 pull requests on #2017 set it, so no required job sits outside every budget.[^a-lane-budget]
- Script tests: `pnpm test:scripts` finds every script test itself, so a new one needs no edit to `package.json`.[^a-script-tests] Make a folder outside the repository with `scratchDir` (`scripts/scratch.mjs`), and walk the repository's own folders with `treeFiles` and `copyTree` (`scripts/tree.mjs`).[^a-tree-walk] More: [contributing/ci.md](contributing/ci.md#script-tests).
- Never add AI attribution to commits, pull requests, code or docs (no `Co-Authored-By`, no "Generated with") (enforced for commits and the pull request's title and body: the `attribution` job, `scripts/attribution.mjs`, part of the required `ci` check).[^a-attribution] What it checks: [contributing/ci.md](contributing/ci.md#ai-attribution).
- Consumers contribute what they learn back here. Our own tools and products are consumers: when one of their interfaces teaches something general, land it as a principle, a component or a check with a test, kept generic, so the other products and tools get it too. A tool that needs an instruction booklet is a design bug; put the guidance in the surface (tool descriptions, replies, errors, automatic hooks).
- Meerkat mode: look around first. Before you design or build something new (a component, a kit, a standard, a tool or a platform target), look for prior art to adopt or borrow, and do it again for every decision record: give the record a "Prior art" section that links each find and marks it adopt, borrow, watch or ignore (Ari, 2026-11-03: "make it a standing rule for all the ouro ui stuff!!").
- Art: every picture on every surface follows ourostack/.github's [one-universe art rules](https://github.com/ourostack/.github/blob/83e6b333c3f397821c83935f7329aedb019844f3/agents/art-one-universe.md): the frosted-glass universe, with Ouro on-model, one vision per picture, and words beside or above the art, never over it and never glowing (Ari, 2026-11-17: "NOT storybook universe - that's the OLD one").[^a-art-universe] The site's code still says "storybook" (`site/src/storybook.ts`, `StoryWorld`, `site/public/brand/storybook/`) for historical reasons: those files hold the current frosted-glass scenes, copied byte for byte from ourostack/.github's `brand/`. Never draw in the old storybook style.
- Nothing waits for a person (Ari: "NOTHING waits for me"). Make the call, record why, and keep the work moving; releases are the release workflow's, never a person's sign-off. When an account or tool fails, find the right one before parking anything: `gh-work` for work organisations and `gh-personal` for ourostack (`~/.local/bin`).

## Dev message format

Exact format: `[ouro-ui] <Component>: <what's wrong>. Fix: <exact code>.`

- Emit each message once per component instance.[^a-once]
- Strip messages in production with the bare `process.env.NODE_ENV !== "production"` form, with no `typeof process` guard, so bundlers replace it statically and drop the dead branch.[^a-dev-strip] Put the check at each warn call site (`if (process.env.NODE_ENV !== "production") devWarn(...)`), and build `devThrow`'s fix argument only inside a development branch. `scripts/dev-strip.test.mjs` bundles a probe with Vite in production mode and asserts the message strings are gone.
- Consumers need a bundler that defines `process.env.NODE_ENV` (Vite, Next.js, webpack and React Router all do).[^a-node-env] Without one, dev messages are not stripped and the bare reference throws in a browser.

## Appearance classes warn

In development, a `className` token that sets appearance (`bg-*`, `text-*`, `border-*`, `rounded-*`, `shadow-*`, a `dark:` variant and the like) warns and names the prop to use; layout classes never warn.[^a-layout-classes] The exact rule and how to pass hints: [contributing/components.md](contributing/components.md#appearance-classes-warn).

## Rules for writing components

1. Props-first: the default export takes props that describe the whole thing; building-block parts live in the component's `-parts` file and their JSDoc says when to use them. Exception: `ResizablePanelGroup`, `ResizablePanel` and `ResizableHandle` are exports of `resizable.tsx`, because they are shadcn's public names (an agent porting shadcn's import gets hint types that name the fix, not "no exported member") and do not fit the parts page's `<Family>Root` naming.[^a-resizable]
2. Make anything that "always" applies a required prop (`title` with `hideTitle`, `label` with `hideLabel`, `legend`, `name`), so leaving it out is a type error.
3. One state, one prop: `error`, `loading`, `disabled`, `required` each handle all of their ARIA, messaging and animation.[^a-one-prop]
4. Use named options (`tone`, `variant`, `size`) that map to theme tokens for appearance, never color names or classes.
5. `className` is for layout only; warn in development about appearance classes and give common layout needs a prop (for example `fullWidth`).
6. The prop agents guess is the prop that exists: use the common name, or declare it as a hint type that nothing is assignable to, with JSDoc pointing to the real prop (`isLoading?: { 'Use <Button loading>': never }`), so the type error names the fix. Every enum prop also takes one `string & { '<the fixes>': never }` member (`tone`'s `'danger is "destructive"; …'`, shadcn's Button variants and sizes, and the value list where the type is an alias such as `SheetSide`; parts' enum props and numeric ones such as Heading's `level` too), kept short and ASCII so `tsc` prints the whole union, and an unknown value renders the default and warns in development.[^a-hints] Why not plain `never` or a plain literal union: an attribute whose expected type is a literal (`never` reads as `undefined`) and whose value doesn't match rules out every branch of a union-typed props object, and TypeScript then drops the hover JSDoc of every prop on the element.[^a-hints] Keep the HTML attributes outside a props union (`Text`), or hover is lost even in valid code. Keep the mode-exclusion props (`trigger?: never` with `open`) `never` or a string literal, never a hint type: as hint types they lose hover on `trigger`, `open` and `onOpenChange` in valid code. A literal still tells the modes apart, so `open` beside `trigger` is `TriggerOrOpen` (`lib/ouro/open-mode.ts`), the literal `"Pass trigger, or open and onOpenChange, not both"`, and the type error for both modes names the fix; the other excluded props stay `never`, so an indexed type such as `DialogProps["trigger"]` keeps its value types (`DialogProps["open"]` includes the literal; a wrapper reads `DialogControlledProps["open"]`). An element that passes both modes still shows no hover.[^a-hints] `scripts/fixtures/agent-types/` holds the agent snippets, one pair of files per component: `<item>.snippets.tsx` and `<item>.cases.ts`, which says which channel (type error, hover, development message) names each fix (types and shared helpers in `shared.ts` and `helpers.ts`); `scripts/agent-types.test.mjs` and `test/agent-types.test.tsx` find the files by name and check them.[^a-agent-types] Snippet ids are unique across the files, so a new component names its snippets after itself (`numberField01`).
7. Mode-dependent types follow the mode with discriminated unions (`multiple` makes `Select` use `string[]`; `href` makes `Button` a link).
8. Parts check where they are: outside their parent they throw in development with the correct JSX shape; where it is safe, the parent wraps loose children instead.
9. Docs live in the types: every export has JSDoc with a one-line purpose, a minimal example and "use X instead when" guidance; `README.md` holds the catalog and `docs/<component>.md` a page per component.[^a-docs]
10. Make behavior and motion the component's job (dialog-to-sheet on phones, focus, touch targets, durations, springs, reduced motion): take no duration or easing prop, and read motion from theme tokens. Run state changes as CSS transitions (Base UI's `data-starting-style`/`data-ending-style`) on the three easing tokens `--ouro-ease-out`, `--ouro-ease-in-out` and `--ouro-ease-drawer`, with the `--ouro-duration-*` tokens; use `ease` for hover and color changes, and never `ease-in`. Put gesture settles (a released drag) in `lib/ouro/spring.ts` and `lib/ouro/use-drag.ts`, which SwipeActions, Reorderable and Toast use, on `requestAnimationFrame` with no dependency. Sheet is the exception: its drag is Base UI Drawer's, and its settle is a CSS transition on `--ouro-ease-drawer`. The old `--ouro-ease-spring` and `--ouro-spring-duration` stay defined until their last reader is gone. Components honor reduced motion with `motion-reduce:`/`motion-safe:` variants and `prefers-reduced-motion` queries. No registry item depends on the `motion` package; it is a dev dependency here only for the RedwoodUI reference story and the theme test's spring check, which goes when the spring tokens do.[^a-no-motion] A component that ever needs Motion must wrap its own usage in `MotionConfig reducedMotion="user"` (or use `useReducedMotion`) and must not rely on `OuroProvider`, which is optional.
11. Errors teach: every dev message uses the format above.[^a-dev-format]
12. Higher-level patterns capture whole interactions agents assemble badly (`ConfirmDialog`, later `EditSheet`).

## Layout

The layout mirrors where shadcn installs files, so the CLI's import rewrite lands them in `components/ouro/` and `lib/ouro/` (spec §3).[^a-layout]

- `registry/ouro/components/ouro/<component>/`: components, their parts, tests and stories.
- `registry/ouro/lib/ouro/`: shared helpers and hooks (`cn`, dev messages, the className check, `OuroProvider`, tone names, `useMediaQuery`, `useKeyboardScrollable`, the backdrop anchor, `TouchTarget`, and `env.d.ts`, which declares `process.env.NODE_ENV` so apps without `@types/node` typecheck; `pnpm typecheck` also checks the registry source without Node types).
- `registry/ouro/lib/ouro/testing/`: the test kit the `ouro-testing` item ships (the `act` helper, the custom browser commands, `pageCss()`, the motion helpers, `watchAnnouncements` and more). Tests and specs never press Tab directly; use `pressTab()` (enforced: `directTabPresses` in `scripts/source-rules.mjs`).[^a-tab-press] Any console output fails a test, and a test puts back any media emulation it changes.
- `registry/ouro/e2e/ouro/`: one Playwright spec per component, installed to an app's `e2e/ouro/`. Specs take `test` and `expect` from `../ouro-fixtures`, never from `@playwright/test` (enforced: `scripts/registry.test.mjs`).[^a-spec-imports]
- `registry/ouro/theme/ouro-base.css`: required in every app, added once (no component depends on it).[^a-ouro-base]
- `registry/ouro/theme/ouro-theme.css`: optional. The Ouro color look as a shadcn theme (`:root` and `.dark` values only).
- `app.css`: the repository as its own app. It imports Tailwind, `ouro-base.css` and `ouro-theme.css`, adds the `@custom-variant dark` and `@theme inline` mapping `shadcn init` writes, and scans `registry/`; Storybook and the Vitest projects compile it with `@tailwindcss/vite`.
- `stories/reference/`: repository-only stories, such as the Sheet feel comparison with RedwoodUI's ActionSheet; they ship in no item.[^a-reference-stories]
- `registry.json`: the shadcn registry, generated by `pnpm registry` (`scripts/registry.mts`) and committed only by a release commit; see Registry below.
- `test/install-fixture/`, `test/install-fixture-tests/` and `test/install-fixture-upgrade/`: the apps and files the install test uses.[^a-install-fixture]
- `changes/`: the behaviour changes since the last release, one fragment file per change (`changes/<any-name>.md`), each non-blank line one top-level `- ` line; `scripts/changes.mjs check` fails on anything else.[^a-changes] Add a fragment when a change alters what an app sees (a stacking level, a focus target, a dependency range). The Release note check (`scripts/release-note.mjs`, a required check) fails a pull request that changes a shipped runtime file (component or lib code, or a theme stylesheet) unless `changes/` gains a line or the description has a `no-release: <reason>` line; a docs pin's version literals don't count.[^a-release-note] How releases use them: [contributing/layout.md](contributing/layout.md).
- `UPGRADING.md`: "Upgrading from v0.1.0", the one copy of the note; keep its "What changed, by version" list in step with `changes/`.[^a-upgrading] Edit only this file; `scripts/upgrade-note.test.mjs` fails if a copy of a command appears anywhere else.
- `test/`: the story-wide accessibility test, the screenshot test and their baselines, the stock-theme contrast test, third-party theme fixtures and the shared test helpers.[^a-stock-theme]
- `scripts/agent-usability/`: the agent-usability test (spec §8), which measures success criterion 1.[^a-usability]
- `site/`: the home page, the voyage pages and the docs site (https://ui.ouroboros.bot/). How its parts are built and the rules their tests hold: [contributing/site.md](contributing/site.md). Never describe HX as "for shadcn/ui apps": the shadcn CLI is only how it installs.
- `site/src/docs/spoonjoy.json`: where Spoonjoy uses each component.[^a-spoonjoy] Rerun `node site/scripts/spoonjoy.mts` when Spoonjoy adopts a component, and update the home page's component count (`site/src/voyage/home.tsx`), which `claims:check` compares with the file.
- When an Ouro UI for Apple feature lands on ourostack/ouro-ui-apple's main branch, update the Apple section (`site/src/apple/`) in the same wave; the checklist is in [contributing/site.md](contributing/site.md). Say a feature comes in a later release until a release tag carries it, and give install lines only for a real tag.
- Imports between registry files use `@/registry/ouro/...`, which the shadcn CLI rewrites to an app's aliases on install. `@/` resolves to the repository root (tsconfig `paths` and the Vite alias).

## Component conventions

- Every component root carries `data-ouro="<component>"`, so apps can exclude Ouro UI subtrees from global rules.[^a-data-ouro]
- A component's motion is declared in its `component.json` `motion`, per stem, and each animated part carries `data-ouro-part` (enforced: `readMotion` in `scripts/components.mts`, `test/motion.test.ts` and `pnpm motion:coverage`).[^a-motion-parts] The schema and what its tests must prove: [contributing/components.md](contributing/components.md#motion-declarations).
- Load intelligently and eagerly. Don't gate a fetch on focus, visibility or the person coming back, and don't make a person wait for what could have been fetched already: start a load as soon as the data is known to be needed, and spend the work on what the person is likely to look at next, newest first, within the performance budgets. The source rule's `gated-load` category holds apps to this ([guide](docs/guides/guardrails.md#load-eagerly)).[^a-gated-load]
- Every element a person can focus or operate carries `data-ouro-control` with its item name.[^a-controls] Declare each interactive part in `component.json` `controls`; `pnpm controls:matrix` writes the matrix that `test/controls.test.tsx` checks (`test/generated/`, not committed: every Vitest run and `pnpm typecheck` write both matrices first, so pull requests that add components never edit the same file).[^a-matrices-written] `data-ouro-part` names the part (`trigger`, `option`, `close`), the same name `controls` declares with its role and whether it renders in a portal. A component that renders an Ouro control as its own part passes its own pair (`<Button data-ouro-control="carousel" data-ouro-part="next">`), which Button, Link, Badge and Toggle put before their props so it wins; a control the app passes in (a trigger, footer buttons) keeps its own pair, so a part (`DialogClose`, `PopoverTrigger`) marks its element only without `render`. Base UI's own hidden inputs get theirs through `inputRef` (`controlRef`, `lib/ouro/control-ref.ts`), and what Base UI renders with no prop or ref for it (OtpField's hidden input, Slider's range inputs, the screen-reader Dismiss buttons a Combobox gets) from the component's own layout effect or ref; `scripts/control-matrix.test.mjs` reads every marker the components' source writes and fails on a part its `component.json` does not declare.[^a-controls] A part only a coarse pointer reaches (Combobox's sheet) takes `"touch": true`, and `test/controls.touch.test.tsx` checks it in `ouro-touch`. `test/controls.ts` exports `interactiveSelector` and `censusExclusions` (only Base UI's focus guards), which an app's census of controls copies together. A part that shows only after an interaction (EditSheet's discard prompt, a FileField's chosen files) gets a story whose `play` function reaches that state; `renderStory` runs it. `modes` lists the variants of a discriminated union that change a part's element (Button `["button", "link"]`), and a story that renders any but the first names it in `parameters: { mode: "link" }`. A control a story renders itself, which is no Ouro component, carries `data-test-harness`, and only that control: never the story host or an element around a component.[^a-harness]
- Style with plain Tailwind utilities on shadcn's token names (`bg-primary`, `text-muted-foreground`, `border-border`), merged with `cn(...)` with the app's `className` last, so the app's layout classes win. Round corners with Ouro's radius steps, `rounded-ouro-sm` to `rounded-ouro-4xl` (`rounded-ouro-lg`, `rounded-t-ouro-xl`), not shadcn's `rounded-lg`: `shadcn init` writes shadcn's own `--radius-*` steps into an app's theme, and an add never replaces them, so only the `--radius-ouro-*` steps that ouro-base appends carry Ouro's corner shape, `--ouro-radius-scale` and the Safari fallback.[^a-radius-steps] Give a component neither a class prefix nor a stylesheet of its own. The one exception is `OuroProvider` with `motion="reduced"`: while it is mounted it renders a `<style>` that ends every CSS animation and transition on the page, because an app's own "reduce motion" setting must still the dialogs, sheets and toasts that render outside the provider's element, and Ouro's classes follow only the device's media query.[^a-motion-still]
- Shadows and fonts come from the theme too, read at runtime: `shadow-(--shadow-lg)` (never `shadow-lg`, which Tailwind compiles to its fixed value, and never a color of the component's own) for popovers, menus, selects, comboboxes, navigation menus and toasts, `shadow-(--shadow-xl)` for dialogs, `shadow-(--shadow-sm)` for thumbs and indicators, with a raised surface's hairline as `ring-1 ring-border/60`; a sheet reads `[box-shadow:var(--ouro-shadow-sheet-<side>)]`.[^a-shadows] A title reads `font-[family-name:var(--font-heading,inherit)]`; Kbd keeps the surrounding font (`[font-family:inherit]`), as shadcn's does. `fixedShadows` in `scripts/source-rules.test.mjs` fails on any other shadow, and `test/theme-tokens.test.tsx` checks every story with sentinel tokens.[^a-shadows] Muted text on a muted surface mixes 20% toward the foreground (`text-[color-mix(in_oklab,var(--muted-foreground)_80%,var(--foreground))]`), as `variant="soft"` does with a tone, because shadcn's stock pair is 4.34:1.[^a-muted-mix]
- A layout property the app may override (`h-*`, `px-*`) is one unprefixed class at every width.[^a-layout-class] When it changes at a breakpoint, the class reads a variable and the breakpoint sets the variable (`h-(--ouro-button-h) [--ouro-button-h:…] sm:[--ouro-button-h:…]`), so tailwind-merge replaces it with the app's class.
- `tone` values are the theme token names: `primary`, `secondary`, `destructive`, `success`, `warning`. `secondary` has shadcn's meaning: a quiet surface (`bg-secondary text-secondary-foreground`), never a text color, so Text's `secondary` is the muted foreground.[^a-secondary] `variant="soft"` is the tone at 10% behind text in the tone mixed 20% toward the foreground (shadcn's stock destructive fails 4.5:1 on its own tint otherwise).[^a-soft] Focus outlines use `outline-ring` for every tone.[^a-focus-ring] A tone, variant or size that is not one of ours (`tone="danger"`, shadcn's `variant="destructive"` or `size="icon"`) renders the default and warns with the fix.
- Reset what the browser sets (button borders, backgrounds, margins on `<p>` and headings inside a component, `box-sizing`) in the component's own classes, since Ouro HX ships without a reset.
- Set no margin class on a component root, not even `m-0`. The margin between components is the app's layout, and a parent's `space-y-4` puts it on its children with a zero-specificity rule (`:where(.space-y-4 > :not(:last-child))`), which any margin class on the child beats, so a root with `m-0` loses its gap.[^a-space-y] A root whose element has a margin in the browser's stylesheet (`<p>`, headings, `<fieldset>`, `<figure>`, `<dl>`, lists) clears it with `[@layer_ouro-reset]:m-0`, which puts the rule in a sublayer of Tailwind's utilities: every plain utility beats it whatever its specificity, so `space-y-4` and the app's own margin class still apply (`test/root-margins.test.tsx`).[^a-root-margins] Elements inside a component reset theirs with plain `m-0`. `test/stories.test.tsx` fails on a plain margin reset on any `[data-ouro]` element in any story.
- Draw a required field's marker with CSS (`::after`) on the element around the label (`[data-ouro-label]`, or a group's `[data-ouro-legend]`), never an element or text inside the label and never `::after` on the label itself: a label's text is what Testing Library's `getByLabelText` and Playwright's `getByLabel` compare, and generated content on the labelling element counts toward the control's accessible name.[^a-required-marker]
- A button inside a field (clear, show password, choose date, a file's or chip's remove button, a stepper) is named by visually hidden text, not `aria-label`: an `aria-label` is label text, so Playwright's `getByLabel("Password")` would also match a button labelled "Show password". The one exception is ColorField's swatch, a color `<input>`, which only label text can name; its `pickerLabel` docs say how to find the field.
- Overlay portals are `relative isolate z-(--ouro-layer)`: their own stacking context, at a level apps raise with the token rather than a class edit. Apps raise it in their own unlayered `:root` rule after the Ouro tokens, because `shadcn add` resets the line it wrote; the install test checks that such an override survives a re-add.
- Class strings are literals so Tailwind finds them; `app.css` scans `registry/`. Stories lay out with inline styles and the theme variables (`var(--muted-foreground)`).
- Write hover styles as `pointer-fine:hover:…`, never bare `hover:`: Tailwind's `hover:` checks only `(hover: hover)`, and the rule is `(hover: hover) and (pointer: fine)`, so a tap on a phone leaves no hover state behind (enforced: `ungatedHover` in `scripts/source-rules.test.mjs`).
- Interactive controls use the `press` utility (the scale arrives and releases in 160ms on `--ouro-ease-out`; colors change at once, so a pressed, selected or current control is drawn so on its first frame), a `motion-safe:` press scale of `--ouro-press-scale`, and `<TouchTarget />` (`registry/ouro/lib/ouro/touch-target.tsx`) as the first child of a `relative` root for the 44px coarse-pointer hit area.[^a-press] A linked list row (`Item` with `href`) highlights while pressed instead of scaling, because a full-width row that shrinks reads as a jump; it is at least 44px tall on a coarse pointer instead of using `<TouchTarget />`.[^a-item-row] A `ResizableHandle` changes color on hover (a mouse's only), focus and press instead of scaling, because a 1px splitter line that shrinks looks broken; it still uses `<TouchTarget />`.[^a-resizable]
- Dark mode is the `.dark` class on an ancestor, as in shadcn. The OS setting alone does not switch it.
- Name keyframes in Ouro's namespace (`ouro-spin`), never Tailwind's global `spin` or `pulse`.
- Every variable Ouro UI adds that is not a shadcn color uses the `--ouro-` prefix (`--ouro-ease-out`, `--ouro-sheet-gap`); the prefix on the easing tokens is required, because Tailwind defines its own `--ease-out` and `--ease-in-out`, and an unprefixed token would change the `ease-out` class across the app that installs the library; `registry/ouro/theme/theme.test.tsx` checks the easing and duration tokens, the `press` timing and (until it is retired) the spring against Motion's `spring(0.4, 0.15)`, and checks the Ouro theme's text pairs at 4.5:1 in light and dark.[^a-theme-test]

## Workflow

- A change a person can see: run `pnpm site:build`, then `node registry/ouro/check/check.ts site/dist` (Ouro check, which apps install as `scripts/ouro/check/`; `--pages` narrows it), and fix what it reports before you open the pull request. Then pass the beauty gate in [Design craft](docs/guides/design-craft.md#the-beauty-gate) before a person sees it. Long lines are checked only where `ouro-check.json` declares a measure.[^a-measure] Don't cap text width (`max-width: 65ch` and the like) to satisfy the check unless the request or the design system sets that measure. The Screens workflow runs it at every size on main once a day and on demand, never on a pull request, and reports in its summary without failing ([guide](docs/guides/guardrails.md#the-screen-check)).[^a-screens] CI's `design (n/4)` shards run the same check at a phone's, a laptop's and a 4K screen's size, light and dark, and a finding there fails the `ci` check, unless `.github/ouro-check.json` waives its rule on that page with a reason; the first shard also checks the converted components' pages with the corner-shape fallback forced on, because Playwright's browsers draw corner-shape natively.[^a-design-gate] `test/stories.test.tsx` runs Ouro check's in-page rules over every story at 390px and 1280px, light and dark, and fails on a finding `test/check-known.ts` does not list with its reason and an open issue, or on a listed entry that no longer matches, unless the entry says it shows only sometimes (`sometimes: true`, with why).[^a-story-check] The text-wrap rules (`lone-word`, `overlap`, `narrow-heading`, `clipped-text`) are judged only on Linux, where CI's baseline comes from, since a host's fonts break lines differently; elsewhere they count neither as a finding nor as a stale entry.[^a-text-wrap]
- A pull request that adds something a person can see (a component, a docs page, a guide, a site page) links that thing's page on the live site (https://ui.ouroboros.bot/) in its body, such as `https://ui.ouroboros.bot/docs/dialog/` for Dialog. Pages publishes after the merge, so before it the link is the address the page will have; check it opens once Pages has run.
- Use pnpm 10. Run `pnpm run docs --check`, `pnpm registry --check`, `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm motion:coverage` (right after `pnpm test`: a run of fewer tests rewrites the partitions of the projects it ran), `pnpm test:themes`, `pnpm conformance`, `pnpm test:scripts`, `pnpm test:e2e` and `pnpm build-storybook` before opening a pull request.
- Conformance matrix (`pnpm conformance`, [docs/guides/conformance.md](docs/guides/conformance.md)): every story, with nothing to opt into, through the checks that replace recurring review findings.[^conformance-matrix] So components hand focus on when a press removes them (`useFocusHandoff`), keep a control that becomes unavailable focusable (`aria-disabled`), read the time zone, locale, clock and randomness only after hydration (`useSyncExternalStore` with a server snapshot), use logical sides (`ms-*`, `border-s`, `text-start`; enforced: `physicalUtilities` in `scripts/source-rules.mjs`, exceptions in `scripts/physical-allowed.json` with a reason), and draw edges, states and focus that forced colours keep (outlines, not box shadows). A story states what a check cannot see in `parameters.conformance`, and a pull request that adds an exemption names it in its description with why (enforced: the Conformance exemptions workflow).[^conformance-exemptions] Details: [contributing/testing.md](contributing/testing.md#conformance-matrix).
- Mutation testing (`pnpm mutation`, CI's `mutation` job on a pull request) mutates the runtime lines a change adds or alters. Details: [contributing/testing.md](contributing/testing.md#mutation-testing).
- Ratchet property tests (`scripts/kits/ratchets.test.mjs`): when a property fails, add the case fast-check shrank the failure to into the kit's own tests with the fix.[^conformance-ratchets]
- An app that installs a subset with its tests must reach 100% coverage of the files it installed (enforced: `node scripts/subset-coverage.mjs`, part of the required `ci` check).[^a-subsets] When it fails, cover the line in the item's own tests (a new `<stem>.<case>.test.tsx` beside it), never in another component's.
- No component installs `ouro-base`.[^a-ouro-base-only] In development, `useDevWarnings` (which every component calls) runs `checkTheme()` from `lib/ouro/dev.ts` once per page: when `--ouro-layer` is unset on the document root it logs the command that adds `ouro-base`.[^a-check-theme] The tag in that command is kept in step by `pnpm run docs` (`syncedFiles`).
- Links: `node scripts/links.mjs` (in `pnpm test:scripts`) fails on a link that opens no page, and on a `docs/*.md` file with no page on the site.[^a-links] Hand-written guides live in `docs/guides/`.
- `docs/<Export>.md`, `docs/parts.md` and the catalog in `README.md` (between the `catalog` markers) are generated from the JSDoc and prop types in `registry/` by `pnpm run docs` (with `run`: bare `pnpm docs` is pnpm's `npm docs`, which opens a browser[^a-npm-docs]) (`scripts/gen-docs.mts`, TypeScript compiler API) and committed; Edit the JSDoc, never the output (enforced: `pnpm run docs --check` in CI). Generation fails when an export lacks a purpose or an `@example`, when a component lacks a "use X instead when" sentence, or when an export has no catalog group: each export names its group in its JSDoc (`@group Forms`), one of `groupOrder` in `scripts/catalog-groups.mts` (Actions, Text, Forms, Overlays, Menus, Feedback, Display, Lists, Layout, Navigation, Data, Chat) or `App setup` for what sets up an app rather than composing its screens (`OuroProvider`, and `Inspector`, X-ray);[^a-gen-docs-fails] the catalog, the README and the site list each group that has exports, in that order, and each group's exports by name, App setup last. The site has a page for every component, App setup's included (`siteGroups`); the site's `DocsItem.group` type and tests read the same constants.[^a-site-groups] The documented files and part files (`<folder>/<stem>-parts.tsx`) come from the components' `component.json`. Tag an export that is shared between registry files but not for apps with `@internal`.
- `test/stories.test.tsx` runs axe over every story; two story files may not share a name.[^a-stories-glob] Story parameters (`plainOpeners`, `screenshot`) and the rest: [contributing/testing.md](contributing/testing.md#story-wide-tests).
- Screenshot baselines (`test/__screenshots__/**/*-linux.png`) come from Linux CI only: run `visual-baselines.yml` on your branch and commit its artifact.[^a-visual] Details: [contributing/testing.md](contributing/testing.md#screenshot-baselines).
- Source rules (`scripts/source-rules.test.mjs`): no registry file has a comment before its first statement, because the shadcn CLI drops it on install; start with the imports, or with an export list (`export { a, b };`) in a file without imports, and put the guidance in JSDoc after it.[^a-first-comment] The install job checks that every installed file kept its source's comments.[^a-comments] Write coverage hints as `/* istanbul ignore <next|if|else> @preserve -- reason */`; esbuild strips them without `@preserve`. Every test's full name (describe titles and title) is unique across the suite, so a name filter runs exactly one.[^a-unique-names] No file name and no test title says a component "warns" or has "warnings" where a consumer's own "no warnings in tests" rule would read it as a failure (`alarmingFileName`, `alarmingTestTitle`: the helper is `use-dev-messages.ts`, and a title says what the message is about).[^a-alarming] Every runtime file under `components/ouro/` and every `lib/ouro/*.tsx` starts with `"use client";` (before the imports) unless it is pure: a component's `<stem>-styles.ts` (by its name) or a file on the pure list (`pureFiles` in `scripts/source-rules.mjs`: `touch-target.tsx`), and so does any other module that calls a hook (including React 19's `use()` and a hook imported from react under another name), calls `createContext` or defines a class component; no other file does, so a Next.js Server Component can render the components and still import plain values; the shadcn CLI keeps the directive in apps with `"rsc": true`, and its removal regex never matches the form with a semicolon, so apps with `"rsc": false` keep it too (the install check fails if an installed file loses it).[^a-use-client] That is deliberate: without the semicolon, shadcn@4.21.1 strips the directive from every other file only (its regex is global and stateful), and an app that later moves to Server Components would break.[^a-shadcn-rsc] `docs/guides/installing.md` tells Vite apps how to silence the bundler's notice.
- Wait on conditions in tests, never on fixed timers: `expect.poll` until a value is reached or a transition has finished (`getAnimations()` empty and two reads agree), `act` to flush React before asserting that something did not happen, and a frame for media query changes. A settle that runs in JavaScript (a spring) is invisible to `getAnimations()`, so it sets `data-ouro-settling` on the element while it runs, and tests wait for the attribute to clear. The projects give every poll 10s, so a loaded runner waits longer instead of failing; don't pass a shorter `timeout`.[^a-poll] A poll that is a deliberate bound says why in a `// short poll: <reason>` comment on the line before its statement, the only exception: `shortPollTimeouts` in `scripts/source-rules.mjs` fails any other poll whose timeout is under 10 s or not a literal, and any `vi.waitFor` with no timeout.[^a-short-poll]
- A state that lasts a set time on the real clock (CopyButton's Copied, a toast's countdown, a story's save in progress) can end between a test's steps on a loaded runner, so a poll for it is a flake. Hold the page's clock (`vi.useFakeTimers` and waits on real frames in Vitest, `page.clock.install()` and `holdClock` from `e2e/ouro/story.ts` in Playwright) or record the state as it happens (`watchAnnouncements`, `watchToasts` in `site/e2e/toasts.ts`). `timerBoundReads` in `scripts/source-rules.mjs` fails a test that polls for one of these states, or for a page-wide text or dialog, or one in the Notifications region, in a file with toasts (all of `site/`, and a spec that opens a `feedback-toast--` story), unless a call before the read holds the clock or records the toasts.[^a-timed-reads] A read that means the real clock carries a `// real clock: <reason>` comment on its statement (which covers that statement only, or a loop's one statement), and a pull request that adds or moves one names the file in its description (`scripts/real-clock-ratchet.mjs` counts escapes by file, test and statement).[^a-timed]
- Test with Vitest browser mode (projects `ouro-chromium`, `ouro-webkit`, `ouro-touch` and more: [contributing/testing.md](contributing/testing.md#vitest-projects)).[^a-projects]
- Write tests that hold under any shadcn theme, since they ship to apps: compare with the theme's computed variables, never with Ouro's hex values (`themeColor` in `button.test.tsx`), and read compiled CSS with `pageCss()`, never by importing `app.css`. A component's tests, stories and spec import only items their `-tests` item depends on; a `-tests` item may depend on any runtime item.
- End-to-end specs: `pnpm test:e2e` starts Storybook and runs `registry/ouro/e2e/` in Chromium and WebKit.[^a-skeleton-frames]
- Screen-reader lane: `pnpm test:sr --project <voiceover|nvda>`. How it runs in CI and gates a release: [contributing/testing.md](contributing/testing.md#screen-reader-lane). A pull request from this repository runs the specs its change reaches, as part of the required `ci` check, on the same hosted macOS and Windows runners as main's runs, after yielding to main's lane. Guidepup's setup changes VoiceOver and TCC settings, which die with the ephemeral GitHub-hosted runner, so the lane may run for a pull request there, but never for a fork's: a fork's code is not a branch of this repository.[^a-sr-pr] How the selection works: [docs/guides/screen-reader-lane.md](docs/guides/screen-reader-lane.md#on-a-pull-request).
- Custom browser commands (`commands.emulateMedia`, `commands.drag`, `commands.tap` and more) live in `registry/ouro/lib/ouro/testing/commands.ts`; [contributing/testing.md](contributing/testing.md#custom-browser-commands) says what the commands wait for. Pass `durationMs` whenever a swipe's speed matters, lift a finger with `touchEnd` in a `finally`, and keep drag tests to Chromium.
- Contributors need Node 22.18 or later (`devEngines`; `.node-version` pins 24) because the scripts run through Node's type stripping.[^a-node]
- The repository installs from registry.npmjs.org (`.npmrc`), and `pnpm-lock.yaml` names no other registry or tarball host.[^a-npm-registry] pnpm reads a project `.npmrc` ahead of the user's own, so a machine whose npm config points elsewhere (a corporate feed) sets `npm_config_registry` in its environment rather than editing the repository's `.npmrc`, and never commits a lockfile resolved there.

## Claims

A factual sentence is a claim, on every surface: Markdown, JSDoc, the site's copy, changes fragments, and a pull request's title and body.[^claim-surfaces] A claim carries its primary source and a machine check, so the next agent can trust it without rebuilding the proof ([guide](docs/guides/claims.md)).

- Run `pnpm claims:check` before you push: it lints every surface and runs every claim's checks, as the `ci` job does.
- Run `pnpm claims:lint --pr --title "<title>" --body-file body.md` on a pull request's text before you open it: it lints the title, the body and the change fragments the branch adds or changes, with the check the Claims workflow runs on GitHub.[^a-claims-command]
- Open a pull request here with the `gh ouro-pr` alias, which runs that lint first and fetches its script from ourostack/.github's main each time. A bare `gh pr create`, the GitHub Copilot app's `create_pull_request` tool, an old local copy of `ouro-pr.sh` and a `gh pr edit` of the title or body skip that lint, so their text meets it first in the Claims check, which runs when a pull request is opened or edited.[^a-claims-paths] A lane that opens pull requests with the `create_pull_request` tool runs `pnpm claims:lint --pr --title "<title>" --body-file body.md` on the title and body before it calls the tool, and passes the body it linted. To change a pull request's text, lint the new text first: `pnpm claims:lint --pr --title "<title>" --body-file body.md && gh pr edit <number> --title "<title>" --body-file body.md`. Lint a probe pull request's text as well, though it is closed without merging.
- `pnpm i` installs a pre-push hook (`scripts/install-hooks.mjs`, `scripts/pre-push.mjs`) that runs the same lint before each push: on the open pull request's title and body, when `gh` can read them, and on the change fragments the branch adds.[^claims-pre-push] `git push --no-verify` skips it once.
- Run `pnpm claims:show <file>` to see a file's claims, their sources and whether each check holds.

To make a claim, cite the source and add a check, as in this snippet:

```md
Ouro HX ships [95 components](registry.json "verify:count(registry:ui)=95").
Every story passes axe.[^axe]

[^axe]: test:test/stories.test.tsx::at $width px > %s > $id has no axe violations, closed and with each overlay open verify:testExists(test/stories.test.tsx::at $width px > %s > $id has no axe violations, closed and with each overlay open)
```

In JSDoc, add `@claim "<words of the sentence>" <source> verify:<check>` to the comment, one per sentence it backs; in TypeScript copy, wrap the string in `claim(text, { source, verify })` from `lib/ouro/claims.ts`. Do not reword a claim to dodge the lint: source it, correct it, or remove it.

## Registry

- Never edit `registry.json`: `pnpm registry` generates it, and main never commits it. The generated files that list every component (`registry.json`, `site/public/llms.txt`, `site/src/docs/catalog.json`, `sources.json`, `pages.json` and `page-index.json`, and the control and motion matrices) are written by `pnpm i` (`scripts/generate.mjs`, the postinstall) and by their generators, and `.gitignore` keeps them out of commits, so two pull requests that add components never conflict in them (`scripts/generated-files.mjs`).[^a-uncommitted] Ouro Feel's built probe (`registry/ouro/feel/ouro-feel-probe.js`, from `feel/probe/probe.ts`) is generated the same way, so no change to `probe.ts` can leave main with a stale copy.[^a-feel-built] `.gitattributes` checks text out with LF line endings everywhere, Windows included, because those generators parse it as committed.[^a-uncommitted] Run `pnpm registry` after adding, renaming or moving a registry file, changing an import, a theme CSS file, a dependency version or a component's JSDoc purpose, so your checkout's copy is current. `pnpm registry --check` (job `registry`) fails on main and on a pull request into it when git tracks any of them, or when a file `registry.json` lists is not committed or is a Git LFS pointer, which a GitHub install at a release tag could not read. Only a release commit adds them (`scripts/release-commit.sh`), so every tag carries the `registry.json` that `shadcn add ourostack/ouro-ui/<item>#<tag>` reads.[^a-uncommitted]
- `scripts/registry.mts` derives every item from the layout.[^a-registry] Each component is two items: `<name>` (runtime source only) and the opt-in `<name>-tests`.[^a-two-items] Details: [contributing/releases.md](contributing/releases.md#registry).
- A runtime item's `registryDependencies` are its runtime imports only. Stories and tests count as imports of the `-tests` item (`heading-tests` depends on `button` through its stories), never of the component.[^a-tests-imports]
- A component file exports only components and types, so an app's React Fast Refresh lint passes: shared class strings, value lists and dev-message helpers go in `<stem>-styles.ts` (`sheet-styles.ts`, `dialog-styles.ts`, `text-styles.ts`), and hooks in their own module (`use-ouro.ts`).
- A component's docs message gives its import line and every Ouro item installed with it.[^a-docs-message] `ouro-testing` starts its description with "Installed with every …; you don't need to add it."; `ouro-base` says to add it once.[^a-docs-message] Theme tokens named `--ouro-*` go to the item's `css` under `:root` and `.dark`, not `cssVars`, so the CLI writes no self-referential `@theme inline` mapping for them; `scripts/install-check.mjs` fails on any `--x: var(--x)`.[^a-self-reference]
- `ouro-theme` is a `registry:theme` (it replaces the app's colors, and the CLI warns before that); `ouro-base` is a `registry:item`, because it only adds variables.
- The `ouro-testing` docs message prints the files an app adds to run the shipped tests and specs (`testingSetup` in the script). `test/install-fixture-tests` holds those files verbatim, and the registry test fails if they drift or if the bare `test/install-fixture` has them.
- The components come from each folder's `component.json` (`scripts/components.mts`); a registry file no item ships fails the generator unless it is in `repoOnly`.[^a-component-json] Edit `site/llms.txt`, never `site/public/llms.txt`, which `pnpm registry` overwrites. Details: [contributing/releases.md](contributing/releases.md#registry).
- The shadcn CLI is pinned to `shadcn@4.21.1` in `.github/workflows/ci.yml`, `pages.yml` and `scripts/install-test.sh`.
- The install test (`scripts/install-test.sh <shadcn|ouro|github|current|namespace|next|upgrade> <dir>`) runs locally too. Every variant adds `ouro-base` first and checks that no later add changes the stylesheet by a byte.[^a-install-byte] What the variants prove: [contributing/releases.md](contributing/releases.md#install-test).

## Adding a component

A component touches only its own files, so parallel pull requests do not conflict. Create:

1. `registry/ouro/components/ouro/<folder>/component.json`: `{ "order": <the highest order of any folder>, "components": ["<stem>"] }`. Equal orders sort by folder name. That makes conflicts rarer, not impossible: pull requests whose components fall in the same gap still conflict there, so regenerate after a rebase.[^a-component-json]
2. `registry/ouro/components/ouro/<folder>/<stem>.tsx` (and `<stem>-parts.tsx`, `<stem>-styles.ts` as needed), with JSDoc on each export including `@example` and `@group <group>`, one of Actions, Text, Forms, Overlays, Menus, Feedback, Display, Lists, Layout, Navigation, Data or Chat (`scripts/catalog-groups.mts`).[^a-gen-docs-fails]
3. In the same folder: `<stem>.test.tsx`, `<stem>.test-d.ts` and `<stem>.stories.tsx` (story `parameters` for `plainOpeners` and `screenshot` where they apply), plus `registry/ouro/e2e/ouro/<stem>.spec.ts`.
4. `site/src/docs/demos/<stem>.demo.tsx`: the docs page's live demo, as its default export.
5. `test/install-fixture-next/src/app/sections/<stem>.tsx`: a Server Component section with `// expect: <text>` lines.
6. `scripts/fixtures/agent-types/<stem>.snippets.tsx` and `<stem>.cases.ts`, with snippet ids named after the component.
7. `changes/<stem>.md`: a `- New: ...` line. One top-level `- ` line per change, with no wrapped lines or sub-items: `scripts/changes.mjs check` fails on any other non-blank line, because only those lines reach the release notes.[^a-changes]

Then regenerate, never hand-merge: `pnpm run docs` (`docs/` and `README.md`, which you commit, and the site's `catalog.json`, `sources.json`, `pages.json` and `page-index.json`, which git ignores) and `pnpm registry` (`registry.json` and `site/public/llms.txt`, which git ignores). After a rebase, run both again instead of resolving conflicts in `docs/` or `README.md`. Screenshot baselines come from the `visual-baselines.yml` workflow.

## Pages and releases
