# Contributing to Ouro UI

Rules for people and coding agents who change this repository. (Consumers read `README.md` and `docs/`, not this file.)

## Project constraints

- Copy-in source distributed as a shadcn/ui registry; MIT license, repository `https://github.com/ourostack/ouro-ui`. There is no npm package and no build: apps compile the components with their own Tailwind CSS v4.
- No code is copied from Tailwind Catalyst or Tailwind Plus. Ideas only.
- Touch targets are at least 44px on coarse pointers (`@media (pointer: coarse)`).
- With `prefers-reduced-motion: reduce`, nothing moves, draws or scales: no transform, position, size or `stroke-dashoffset` change animates. Only `opacity` and colour properties (`color`, `background-color`, `border-color`, `outline-color`) may transition, over `--ouro-duration-fast`, so a checkbox's tick fades in whole and its box changes colour. Every component's `reduced` lists in `component.json` `motion` hold to this. Translucent surfaces also honor `prefers-reduced-transparency` (solid surface, no blur) and `prefers-contrast: more` (solid background, defined border).
- The default breakpoint `sm` is 640px. Below it, `Dialog` with `presentation="auto"` renders as a sheet.
- CI gates: `pnpm run docs --check`, type check, lint, unit and browser tests with 100% line and branch coverage (measured over `registry/**`, without stories, `registry/ouro/lib/ouro/testing/` and `registry/ouro/e2e/`), the script tests (including `scripts/app-lint.test.mjs`, which lints the runtime items' source with a stock Vite app's oxlint config and allows no warnings) and the Storybook build (job `ci`); `pnpm registry --check`, `pnpm controls:matrix --check` and `shadcn registry validate` (job `registry`); `pnpm motion:coverage` over the motion evidence the `ci` job's `pnpm test` uploads, with `--expect` naming each Vitest project and shard count that run writes (job `motion-coverage`); axe over every story under each third-party theme fixture, `pnpm test:themes`, one fixture per shard (job `themes`); the conformance matrix over every story (focus, announcements, hydration under foreign time zones and locales, right to left, forced colours), every *n*th story per shard (job `conformance`); the end-to-end specs against Storybook (job `e2e`); and the install test (job `install`: the `shadcn`, `ouro`, `namespace` and `next` variants; job `install-upgrade`: the `upgrade` variant). A pull request into main runs the browser tests its change can affect (`scripts/test-impact.mjs`, CI's `plan` job): the tests of the components whose folder, spec or docs demo it changed and of every component that imports them (through their own code, or from their tests, stories and docs demo), the tests of every folder those components' tests, stories and docs demos import (one step out) and of every folder the code of any of those imports, and of the `lib/` files all of them load, the shared suites in `test/` over only those components' stories and demos plus the reference stories (`OURO_STORIES`, `selectedStories` in `test/stories.tsx`, `test/story-selection.ts`), the site's tests, the `themes` scan of those stories, their end-to-end specs and the subset-coverage sets that install them, with coverage measured over all those folders and `lib/` files (when only coverage falls short, the full suite decides) and `motion-coverage --stems` holding their motion maps complete. A change to the theme, `lib/`, `test/`, `scripts/`, configuration, dependencies, a workflow, the site's stylesheet or a site file the docs demos load, or one the plan cannot map, runs everything, and so do pushes to main, the merge queue, dispatched runs (release.yml's CI on the release branch) and release branches. Every required check still reports on a reduced run: the `themes` shards pass as "Not affected" when no component changed. Workflows pin every action to a full commit SHA with a `# vX.Y.Z` comment, and only release.yml keeps the checkout's credentials (`scripts/workflows.test.mjs`); Dependabot proposes new pins weekly (`.github/dependabot.yml`). `scheduled-install.yml` runs the install matrix weekly against main and the newest release tag, because item dependency ranges float, and fails when main's `ouro.latestRelease` is not GitHub's newest release. Any failure opens, or comments on, one "Scheduled install failed" issue (`scripts/scheduled-failure.sh`), so it shows where we look. GitHub pauses scheduled workflows in a public repository after 60 days with no repository activity, and the pause raises no issue: after a quiet spell, check that the workflow is still enabled (Actions, or `gh workflow enable scheduled-install.yml`).
- Never add AI attribution to commits, pull requests, code or docs (no `Co-Authored-By`, no "Generated with").

## Dev message format

Exact format: `[ouro-ui] <Component>: <what's wrong>. Fix: <exact code>.`

- Emit each message once per component instance.
- Strip messages in production with the bare `process.env.NODE_ENV !== "production"` form, with no `typeof process` guard, so bundlers replace it statically and drop the dead branch. Put the check at each warn call site (`if (process.env.NODE_ENV !== "production") devWarn(...)`), and build `devThrow`'s fix argument only inside a development branch. `scripts/dev-strip.test.mjs` bundles a probe with Vite in production mode and asserts the message strings are gone.
- Consumers need a bundler that defines `process.env.NODE_ENV` (Vite, Next.js, webpack and React Router all do). Without one, dev messages are not stripped and the bare reference throws in a browser.

## Appearance classes warn

A `className` token warns when, after removing variants (split on `:` outside `[...]`) and a leading or trailing `!`, its base matches `/^(bg|text|border|rounded|shadow|font|ring|from|via|to|fill|stroke)-/` or is exactly `border`, `rounded`, `shadow` or `ring`, or when `dark` appears at any variant position. Ordinary layout classes (`mt-4`, `w-full`, `grid-cols-2`, `size-4`) never warn, and neither do text wrapping, text overflow and table layout classes that share a prefix (`text-wrap`, `text-nowrap`, `text-balance`, `text-pretty`, `text-ellipsis`, `text-clip`, `border-collapse`, `border-separate`, `border-spacing-*`). Alignment classes (`text-left|center|right|justify|start|end`) also warn, and the message points to the component's `align` prop where one exists (the `alignHint` argument), or else shows the class on a parent element. Hints are exact code, such as `tone="destructive"`. A component may pass a hint function that picks the fix from the offending token (`registry/ouro/lib/ouro/appearance-hints.ts` maps `bg-red-500` to `tone="destructive"` and `text-lg` to `size="lg"`); pass hints only in development (`process.env.NODE_ENV !== "production" ? hint : ""`) so their text is stripped.

## Rules for writing components (spec section 4)

1. Props-first: the default export takes props that describe the whole thing; building-block parts live in the component's `-parts` file and their JSDoc says when to use them. Exception: `ResizablePanelGroup`, `ResizablePanel` and `ResizableHandle` are exports of `resizable.tsx`, because they are shadcn's public names (an agent porting shadcn's import gets hint types that name the fix, not "no exported member") and do not fit the parts page's `<Family>Root` naming.
2. Anything that "always" applies is a required prop (`title` with `hideTitle`, `label` with `hideLabel`, `legend`, `name`); leaving it out is a type error.
3. One state, one prop: `error`, `loading`, `disabled`, `required` each handle all of their ARIA, messaging and animation.
4. Appearance comes from named options (`tone`, `variant`, `size`) that map to theme tokens, never color names or classes.
5. `className` is for layout only; warn in development about appearance classes and give common layout needs a prop (for example `fullWidth`).
6. The prop agents guess is the prop that exists: use the common name, or declare it as a hint type that nothing is assignable to, with JSDoc pointing to the real prop (`isLoading?: { 'Use <Button loading>': never }`), so the type error names the fix. Every enum prop also takes one `string & { '<the fixes>': never }` member (`tone`'s `'danger is "destructive"; …'`, shadcn's Button variants and sizes, and the value list where the type is an alias such as `SheetSide`; parts' enum props and numeric ones such as Heading's `level` too), kept short and ASCII so `tsc` prints the whole union, and an unknown value renders the default and warns in development. Why not plain `never` or a plain literal union: an attribute whose expected type is a literal (`never` reads as `undefined`) and whose value doesn't match rules out every branch of a union-typed props object, and TypeScript then drops the hover JSDoc of every prop on the element. Keep the HTML attributes outside a props union (`Text`), or hover is lost even in valid code. The mode-exclusion props (`trigger?: never` with `open`) stay `never`: as hint types they lose hover on `trigger`, `open` and `onOpenChange` in valid code, so an element that passes both modes shows no hover and relies on the development error, which names the fix. `scripts/fixtures/agent-types/` holds the agent snippets, one pair of files per component: `<item>.snippets.tsx` and `<item>.cases.ts`, which says which channel (type error, hover, development message) names each fix (types and shared helpers in `shared.ts` and `helpers.ts`); `scripts/agent-types.test.mjs` and `test/agent-types.test.tsx` find the files by name and check them. Snippet ids are unique across the files, so a new component names its snippets after itself (`numberField01`).
7. Mode-dependent types follow the mode with discriminated unions (`multiple` makes `Select` use `string[]`; `href` makes `Button` a link).
8. Parts check where they are: outside their parent they throw in development with the correct JSX shape; where it is safe, the parent wraps loose children instead.
9. Docs live in the types: every export has JSDoc with a one-line purpose, a minimal example and "use X instead when" guidance; `README.md` holds the catalog and `docs/<component>.md` a page per component.
10. Behavior and motion are the component's job (dialog-to-sheet on phones, focus, touch targets, durations, springs, reduced motion); no component takes a duration or easing prop, motion comes from theme tokens. State changes are CSS transitions (Base UI's `data-starting-style`/`data-ending-style`) on the three easing tokens `--ouro-ease-out`, `--ouro-ease-in-out` and `--ouro-ease-drawer`, with the `--ouro-duration-*` tokens; hover and color changes use `ease`, and `ease-in` is never used. Gesture settles (a released drag) live in `lib/ouro/spring.ts` and `lib/ouro/use-drag.ts`, which SwipeActions, Reorderable and Toast use; they run on `requestAnimationFrame` with no dependency. Sheet is the exception: its drag is Base UI Drawer's, and its settle is a CSS transition on `--ouro-ease-drawer`. The old `--ouro-ease-spring` and `--ouro-spring-duration` stay defined until their last reader is gone. Components honor reduced motion with `motion-reduce:`/`motion-safe:` variants and `prefers-reduced-motion` queries. No registry item depends on the `motion` package; it is a dev dependency here only for the RedwoodUI reference story and the theme test's spring check, which goes when the spring tokens do. A component that ever needs Motion must wrap its own usage in `MotionConfig reducedMotion="user"` (or use `useReducedMotion`) and must not rely on `OuroProvider`, which is optional.
11. Errors teach: every dev message uses the format above.
12. Higher-level patterns capture whole interactions agents assemble badly (`ConfirmDialog`, later `EditSheet`).

## Layout

The layout mirrors where shadcn installs files, so the CLI's import rewrite lands them in `components/ouro/` and `lib/ouro/` (spec §3).

- `registry/ouro/components/ouro/<component>/`: components, their parts, tests and stories.
- `registry/ouro/lib/ouro/`: shared helpers and hooks (`cn`, dev messages, the className check, `OuroProvider`, tone names, `useMediaQuery`, `useKeyboardScrollable`, the backdrop anchor, `TouchTarget`, and `env.d.ts`, which declares `process.env.NODE_ENV` so apps without `@types/node` typecheck; `pnpm typecheck` also checks the registry source without Node types).
- `registry/ouro/lib/ouro/testing/`: the test kit the `ouro-testing` item ships: the `act` helper, the custom browser commands, `pageCss()`, the motion helpers (`motion.ts`: `expectMotion`, `expectNoMotion`, `expectGestureSettle`, `expectTransition`, `parseDuration`; see Component conventions), `watchAnnouncements` (`announcements.ts`: what live regions announce, by region and text, so a test proves a message is heard once per change), `axeExclude` (`axe.ts`, the Base UI focus guards to leave out of an axe scan), `pressTab()` (`tab.ts`: Alt+Tab in WebKit on a Mac, where plain Tab skips buttons and links unless the system's "Tab reaches buttons" setting is on; tests and specs never press Tab directly, and `directTabPresses` in `scripts/source-rules.mjs` fails on one), the console setup (`setup.ts`: any console output fails a test, in every project, including output at load or between tests, which fails the next test, and a console mock left in place, which would hide later output; it drops only Vitest's print of the browser's "ResizeObserver loop" notice, so a test for a component that may raise it listens for the window's `error` event itself) and `ouroTestProjects` (`vitest.ts`; its `page` option sets the page size for Vitest 4), the Vitest browser projects apps add to their config. This repository's `vitest.config.ts` uses the same projects.
- `registry/ouro/e2e/ouro/`: one Playwright spec per component, installed to an app's `e2e/ouro/`, and `story.ts`, which opens a story by id in the Storybook at `OURO_E2E_URL` (default `http://localhost:6006`). Specs ship as `registry:file`, which the CLI does not rewrite, so they import only `./story` and `../ouro-fixtures`: `test` and `expect` come from `e2e/ouro-fixtures.ts`, a file each app owns and no item ships (`testingSetup` prints it; this repository's copy is `registry/ouro/e2e/ouro-fixtures.ts`), so an app's own fixtures apply to Ouro's specs and an update never rewrites the import. `scripts/registry.test.mjs` fails on a spec that imports `@playwright/test`.
- `registry/ouro/theme/ouro-base.css`: required in every app, added once (no component depends on it). Defaults for `--input` and `--radius` with their `@theme inline` mappings, so a field has its border and corners under a theme that defines neither; the success and warning pairs and `--destructive-foreground` (which shadcn's themes lack), the `--ouro-*` motion tokens, `--ouro-layer` (the z-index of the Dialog and Sheet portals, 50 as in shadcn's overlays), `--ouro-shadow-sheet-<side>` (shadcn's `--shadow-*` scale has no upward or sideways shadow), the `press` utility and the keyframes.
- `registry/ouro/theme/ouro-theme.css`: optional. The Ouro color look as a shadcn theme (`:root` and `.dark` values only).
- `app.css`: the repository as its own app. It imports Tailwind, `ouro-base.css` and `ouro-theme.css`, adds the `@custom-variant dark` and `@theme inline` mapping `shadcn init` writes, and scans `registry/`; Storybook and the Vitest projects compile it with `@tailwindcss/vite`.
- `stories/reference/`: repository-only stories, such as the Sheet feel comparison with RedwoodUI's ActionSheet; they ship in no item.
- `registry.json`: the shadcn registry, generated by `pnpm registry` (`scripts/registry.mts`) and committed; see Registry below.
- `test/install-fixture/`: the bare Vite app the install test (`scripts/install-test.sh`) copies, runs `shadcn init` in and installs every component into, with no test config. `test/install-fixture-tests/`: the files the `ouro-testing` docs message tells an app to add (`vitest.config.ts`, `.storybook/`, `playwright.config.ts`), which the install test copies in before it adds `ouro-tests`. `test/install-fixture-upgrade/`: what the `upgrade` variant adds on top of those: a Vitest config with a project for the app's own test beside `ouroTestProjects`, and that test.
- `changes/`: the behaviour changes since the last release, one fragment file per change (`changes/<any-name>.md` holding `- ` lines), so parallel pull requests never edit the same file. Each non-blank line is one change, a top-level `- ` line (no wrapped lines or sub-items); `check` fails on anything else. release.yml assembles them, by file name, into `CHANGES.md` on the release commit only, so the tag holds the "Changes in this release" section and the release notes print it at the top (`node scripts/changes.mjs assemble changes` prints it); main keeps the fragments only. Add a fragment when a change alters what an app sees (a stacking level, a focus target, a dependency range). Release refuses to start while the fragments list no change, or while one still lists a change from the last release's notes (`scripts/changes.mjs check`). After a release, release.yml opens "Prepare main for the next release", which deletes the fragments that release used (`git rm -- 'changes/*.md'`, on a branch off the released commit, so a fragment added during the release stays; `scripts/changes.test.mjs` runs that race) and makes the new tag the newest release (see Pages and releases); the release run merges it once its checks pass, and if it could not, merge it by hand before the next release. That PR is opened with GITHUB_TOKEN, so GitHub records its `pull_request` CI run but holds it (`action_required`, no jobs), and main's ruleset counts only `pull_request`-event checks, not a dispatched run. release.yml therefore finds the held run on the PR's head and approves it (`gh api -X POST repos/ourostack/ouro-ui/actions/runs/<run id>/approve`, with `actions: write`). GitHub documents that endpoint for fork PRs and names only OAuth and classic personal access tokens ([docs](https://docs.github.com/en/rest/actions/workflow-runs#approve-a-workflow-run-for-a-fork-pull-request)), so if GITHUB_TOKEN is refused, the workflow warns, dispatches CI on the branch (a signal only, not what the ruleset counts) and writes the exact approve command to the job summary and the PR body: run it as a maintainer, then wait for the checks. Never add a ruleset bypass for the bot.
- `UPGRADING.md`: "Upgrading from v0.1.0", the one copy of the note, with a short "What changed, by version" list of the changes an app must act on (keep it in step with `changes/` when a release adds one). Its addresses end in `#{{latestRelease}}`, a placeholder each copy fills, and a line under its title tells readers of the raw file what it stands for; every copy drops that line (`rawHint`): `pnpm run docs` copies its body into README.md with the newest release, the site's Updating page renders it the same way, release.yml prints it into the release notes with the release tag, and the `upgrade` install test runs its commands (`scripts/upgrade-note.mjs`). Edit only this file; `scripts/upgrade-note.test.mjs` fails if a copy of a command appears anywhere else.
- `test/`: the story-wide accessibility test, the screenshot test and their baselines, and `stock-theme.test.tsx`, which checks every tone and variant at 4.5:1 under stock shadcn variables (`test/shadcn-stock.css`, copied from `shadcn init`) plus `ouro-base.css`, and under the Ouro theme. `theme-fixtures/` holds third-party themes as an app's stylesheet has them (only `:root`, `.dark` and `@theme inline`, each naming its source and version in its header): `nova.css` and `vega.css` from shadcn's presets and `cookbook.css` from Spoonjoy; `theme-fixtures.ts` puts one in place of the Ouro look at runtime. `test/themes/` runs `story-axe.ts`'s scan of every story under each fixture in light and dark (the `themes` project, only with `OURO_THEMES=1`: `pnpm test:themes`); a violation the fixture's own values cause is pinned in `themeFindings` (`test/themes/theme-findings.ts`) node by node (phase, rule and selector) with its reason: the story must flag exactly those nodes, so a new failure in it still fails and the entry fails once the theme is fixed (`test/theme-findings.test.ts`). `theme-tokens.test.tsx` sets every shadow and font token to a sentinel and checks that each story reads them.
- `scripts/agent-usability/`: the agent-usability test (spec §8), which measures success criterion 1. Fresh agents build five screens (`screens/<screen>/task.md`, with the `src/api/` stand-in for the backend in `files/`) three ways, three times each: shadcn/ui, shadcn/ui with its official skill, and Ouro HX (`arms/create.sh`, which also records each arm's baseline: what `tsc -b` and oxlint find before any agent runs). `score.mts <arm> <screen> <app-dir> --arm-record <arm.json>` judges a result with no model calls: `tsc -b` and oxlint errors that are not in the baseline, axe-core's WCAG A and AA rules at 390px and 1280px in light and dark, and the screen's behavior checks (`checks/<screen>.mts`). `formula.mts` defines the score and is the only place that documents it. The scores are published beside shadcn/ui's, so no arm may gain or lose a point for anything but what its agent did: every check must be stated in the prompt (`prompt.mts`) or the task, in behavior or accessibility terms, and when a task changes, its checks and its known-good screen (`test/screens/`) change with it. `preflight.mts` proves the scorer in a real arm app, `table.mts` writes the results table with the pinned versions, and `page.mts` is the hook for the docs page that will show it. Agent output is committed under `runs/<date>/<arm>/<screen>/<run>/` with each arm's record in `runs/<date>/arms/` (ESLint ignores it), and `agent-usability.yml` scores the newest run weekly and on demand into its job summary; it is not a required check. `README.md` there is the runbook, with the exact prompt and the exact command that starts a fresh agent. `score.test.mjs` (in `pnpm test:scripts`) proves the scorer on a known-good plain-React version of every screen and on broken copies.
- `site/`: the landing page and docs site (https://ourostack.github.io/ouro-ui/), built with Vite from the root dependencies, not a workspace package. Docs pages render the generated `docs/*.md`, each page loading only its own files before it renders or hydrates (`site/src/docs/content.ts`, through the docs module's `prepare`), and the index lists every page from the summaries `pnpm run docs` writes into `catalog.json` and `pages.json`, so the docs' first load doesn't grow with each page; each registry item's page is `docs/<item name>/`, listed from `site/src/docs/catalog.json` (written by `pnpm run docs`), with the live demo from `site/src/docs/demos/<item name>.demo.tsx` (its default export; `site/src/docs/demos.tsx` finds them by glob). Demos are site code and ship in no item. `pnpm site:build` writes `site/dist` (prerendered HTML per route, with Open Graph and Twitter tags from `site/src/head.ts`), `pnpm site:dev` serves it. `site/public/og.png`, the 1200x630 link-preview image, is a screenshot of the landing page with its sheet open; regenerate it with `node site/scripts/og-image.mts` after the landing page changes, review it and commit it. The "Agents read the types" examples live in `site/src/agents/examples.ts`; `pnpm site:messages` regenerates their compiler output (`site:build` and `pnpm test:scripts` fail when it is stale), and the `site` Vitest project checks each quoted dev message against the real component. Each page kind (the landing page, the `/voyage/` preview, the docs) is its own chunk: `site/scripts/prerender.mts` links its stylesheet, `site/src/entry-client.tsx` loads the page's module once the server HTML has painted (so the paint gets the bandwidth) and then hydrates, `App` marks the hydrated page `html[data-site-ready]` (end-to-end specs wait for it before they click), and `site/e2e/catalog.spec.ts` holds each closure to its gzip ceiling (the landing page may not grow; Recharts and docs demos are never in one).
- `site/src/pages/voyage.tsx`: the new landing page ("Mobilis in mobili", `site-design.md`), built in slices on the hidden `/voyage/` route (`noindex`, linked from nowhere) until it replaces `/`. Its chrome is built from Ouro HX components, and it themes the page with six presets, each a plain shadcn/ui theme in `site/src/themes/<preset>.css` (`:root` and `.dark`, plus `--font-heading`, the `--shadow-*` scale and `--ouro-backdrop-color`). `pnpm site:themes` (`site/scripts/themes.mts`) writes `presets.generated.css` (each preset scoped to `[data-theme="<preset>"]`) and `themes.json` (the "Copy theme" and "Copy tokens only" CSS); `--check` (in `site:build`) fails when they are stale, a font's checksum or budget is off, or the synced part of `cookbook.css` was edited. Cookbook is Spoonjoy's own tokens: `node site/scripts/themes.mts sync-cookbook <spoonjoy-v2 checkout>` copies them in and records the commit. The fonts are self-hosted Latin subsets in `site/public/fonts/<family>-<version>.woff2`, listed with their package, checksum, licence and changes in `site/src/themes/fonts.json`; only Geist and Geist Mono are preloaded, and a preset's display face loads when it is chosen. The theme a reader picks is stored in `localStorage` (`ouro-site-theme`) and applied before first paint by the inline script `head.ts` puts first in every page (`site/src/themes/prepaint.ts`). CI's `theme-install` job (`site/scripts/theme-install-test.sh`) pastes each preset's copied CSS into the clean shadcn app the install test starts from, with Checklist and Dialog, and compares it with the site (`site/theme-install/`). The Ouro HX logo in the headers and the favicon comes from `site/public/brand/`: byte-identical copies of the approved artwork, listed with their checksums and source commit in `provenance.json` and checked by `site/scripts/brand.test.mjs`; never recolour, re-export or redraw them (`site/src/components/brand.tsx` renders the rich render with its `srcset`).
- The voyage hero's porthole stage (`site/src/voyage/stage/`): `scene.tsx` layers the original drawings in `site/src/nautilus/art/` (coloured from the theme in `stage.css`, so presets repaint it), `stage.tsx` drives it with HX controls, and `copy.ts` holds every word it says, the crew's log lines and `STAGE_CONTROLS`. Each control in `STAGE_CONTROLS` needs a test named `control: <id>` in `site/e2e/stage.spec.ts` that operates it and asserts what it visibly changes (`site/scripts/stage-census.test.mjs` fails otherwise, for the stage and each chapter: `CENSUSES` in `site/scripts/stage-census.mts`); the same spec holds touch, reduced motion and off-screen rest; `site/e2e/stage.latency.spec.ts` holds each control to its click-to-paint budget in `site/e2e/latency.ts` (4× CPU; of 20 presses after two warm-ups, p95 within 100 ms for every control and the median within twice the control's CI baseline or 24 ms over it, whichever is more, from `BASELINE_MEDIAN` in the spec; Event Timing reports 8 ms steps; every sample printed; other `*.latency.spec.ts` files use the same helper) and runs alone (`pnpm test:latency`, `playwright.latency.config.ts`, CI's `latency` job) so no other test shares the CPU; and `stage.test.tsx` holds the copy to Flesch–Kincaid grade 6 (`site/test/readability.ts`). Every drawing is listed in `site/src/nautilus/art/manifest.json` (creator, source, licence, checksum, its `subject`, and for any drawing with the Nautilus in it, `"subject": "nautilus"` however small the ship, the Verne passages its shape follows); `node site/scripts/art.mts` (in `site:build`) fails on an unlisted file, a stale checksum, a licence outside the allow-list, public-domain art that is not de Neuville's or Riou's from 1871 or earlier on Commons or Gallica, or art over the hero's 35 KB gzip budget; `--write` refreshes checksums. Draw the Nautilus from Verne's text, never the 1954 film's design. The hero's proof claims are computed at build time from the repository (`site/scripts/proof.mts`, served as `virtual:site-proof`), so each claim is only what its source says, and each links to its evidence; the same module picks the hero's install item, the first of `PREFERRED_INSTALL` that is in `ouro.latestRelease`'s `registry.json` (read with `git show`), so the command never names a component the release lacks; the hero shows that command whole and pinned (`#${latestRelease}`), as every public install address must be (`scripts/latest-release.test.mjs`). ## Component conventions

- Every component root carries `data-ouro="<component>"`, so apps can exclude Ouro UI subtrees from global rules.
- A component's motion is declared in its `component.json` `motion`, per stem: `{ "states": { "<attribute>[=<value>]": { "kind": "motion" | "gesture-settle" | "none", "parts"?: { "<part>": { "properties": [...], "reduced": [...] } }, "tests": ["<file>::<full test name>"] } }, "transitions"?: [{ "from", "to", "interrupt", "tests" }], "gestures"?: [{ "name", "tests" }] }`. A state is one of `STATE_ATTRIBUTES` (`test/motion.ts`, from `scripts/motion-states.mts`); every other `data-*` is metadata. Each animated part carries `data-ouro-part`, alone when it is no control (Checkbox's `tick`); `reduced` lists what still runs with reduced motion and may be `[]`. Each helper fails unless the part, or an element around it inside the part's own component root (`[data-ouro]`), carries the state's attribute when it is called (Checkbox's `data-invalid` is on that root, its Field, around the box; a checked row or an open overlay around the component does not count), so a test renders outside the state and then changes into it: a part that mounts in its state proves nothing. A transition the browser cancels counts only when an equal one takes its place (running at the helper's next read, or, on a slow frame, a transition of the same property, or a CSS animation of the same name, on the same element that began after the cancellation and ended uncancelled before that read, seen through its transition or animation events) or it had run 90% of its duration in time (elapsed, not eased progress). `test/motion.test.ts` renders each mapped component's stories, as they render and after each control is clicked once, and fails on a `STATE_ATTRIBUTES` attribute on the root or an animated part that the map leaves out, so give a state a story when none reaches it (Checkbox's `ReadOnly`). The named tests prove it with the test kit's `expectMotion` (exactly those properties, once per part, under both reduced-motion settings for a `motion` state) or `expectNoMotion` (an explicit empty set), which record into the test's meta; `scripts/motion-reporter.mts` writes each run's records to `.tmp/motion/<project>.<shard>.<worker>.json`, and `pnpm motion:coverage` (after `pnpm test`, and in CI's `motion-coverage` job over the uploaded partitions) fails on a property missing or extra for a (stem, part, state, reduced), a named test that recorded nothing (unexercised) or never ran (stale), a record the map does not declare, and a `motion` state with no reduced-motion record. `scripts/components.mts` (`readMotion`) rejects an unknown kind or state, a part the stem never renders, a duplicate property and a test title its file does not hold; `pnpm controls:matrix` also writes `test/generated/motion-matrix.json`. Components without `motion` are not checked yet.
- Every element a person can focus or operate carries `data-ouro-control` with its item name. Declare each interactive part in `component.json` `controls`; `pnpm controls:matrix` regenerates the matrix that `test/controls.test.tsx` checks. `data-ouro-part` names the part (`trigger`, `option`, `close`), the same name `controls` declares with its role and whether it renders in a portal. A component that renders an Ouro control as its own part passes its own pair (`<Button data-ouro-control="carousel" data-ouro-part="next">`), which Button, Link, Badge and Toggle put before their props so it wins; a control the app passes in (a trigger, footer buttons) keeps its own pair, so a part (`DialogClose`, `PopoverTrigger`) marks its element only without `render`. Base UI's own hidden inputs get theirs through `inputRef` (`controlRef`, `lib/ouro/control-ref.ts`), and what Base UI renders with no prop or ref for it (OtpField's hidden input, Slider's range inputs, the screen-reader Dismiss buttons a Combobox gets) from the component's own layout effect or ref; `scripts/control-matrix.test.mjs` reads every marker the components' source writes and fails on a part its `component.json` does not declare. A part only a coarse pointer reaches (Combobox's sheet) takes `"touch": true`, and `test/controls.touch.test.tsx` checks it in `ouro-touch`. `test/controls.ts` exports `interactiveSelector` and `censusExclusions` (only Base UI's focus guards), which an app's census of controls copies together. A part that shows only after an interaction (EditSheet's discard prompt, a FileField's chosen files) gets a story whose `play` function reaches that state; `renderStory` runs it. `modes` lists the variants of a discriminated union that change a part's element (Button `["button", "link"]`), and a story that renders any but the first names it in `parameters: { mode: "link" }`. A control a story renders itself, which is no Ouro component, carries `data-test-harness`, and only that control: never the story host or an element around a component.
- Style with plain Tailwind utilities on shadcn's token names (`bg-primary`, `text-muted-foreground`, `border-border`, `rounded-lg`), merged with `cn(...)` with the app's `className` last, so the app's layout classes win. There is no prefix and no stylesheet per component.
- Shadows and fonts come from the theme too, read at runtime: `shadow-(--shadow-lg)` (never `shadow-lg`, which Tailwind compiles to its fixed value, and never a color of the component's own) for popovers, menus, selects, comboboxes, navigation menus and toasts, `shadow-(--shadow-xl)` for dialogs, `shadow-(--shadow-sm)` for thumbs and indicators, with a raised surface's hairline as `ring-1 ring-border/60`; a sheet reads `[box-shadow:var(--ouro-shadow-sheet-<side>)]`. A title reads `font-[family-name:var(--font-heading,inherit)]`; Kbd keeps the surrounding font (`[font-family:inherit]`), as shadcn's does. `fixedShadows` in `scripts/source-rules.test.mjs` fails on any other shadow, and `test/theme-tokens.test.tsx` checks every story with sentinel tokens. Muted text on a muted surface mixes 20% toward the foreground (`text-[color-mix(in_oklab,var(--muted-foreground)_80%,var(--foreground))]`), as `variant="soft"` does with a tone, because shadcn's stock pair is 4.34:1.
- A layout property the app may override (`h-*`, `px-*`) is one unprefixed class at every width. When it changes at a breakpoint, the class reads a variable and the breakpoint sets the variable (`h-(--ouro-button-h) [--ouro-button-h:…] sm:[--ouro-button-h:…]`), so tailwind-merge replaces it with the app's class.
- `tone` values are the theme token names: `primary`, `secondary`, `destructive`, `success`, `warning`. `secondary` has shadcn's meaning: a quiet surface (`bg-secondary text-secondary-foreground`), never a text color, so Text's `secondary` is the muted foreground. `variant="soft"` is the tone at 10% behind text in the tone mixed 20% toward the foreground (shadcn's stock destructive fails 4.5:1 on its own tint otherwise). Focus outlines use `outline-ring` for every tone. A tone, variant or size that is not one of ours (`tone="danger"`, shadcn's `variant="destructive"` or `size="icon"`) renders the default and warns with the fix.
- There is no reset, so reset what the browser sets (button borders, backgrounds, margins on `<p>` and headings inside a component, `box-sizing`) in the component's own classes.
- A component root sets no margin class, not even `m-0`. The margin between components is the app's layout, and a parent's `space-y-4` puts it on its children with a zero-specificity rule (`:where(.space-y-4 > :not(:last-child))`), which any margin class on the child beats, so a root with `m-0` loses its gap. A root whose element has a margin in the browser's stylesheet (`<p>`, headings, `<fieldset>`, `<figure>`, `<dl>`, lists) clears it with `[@layer_ouro-reset]:m-0`, which puts the rule in a sublayer of Tailwind's utilities: every plain utility beats it whatever its specificity, so `space-y-4` and the app's own margin class still apply (`test/root-margins.test.tsx`). Elements inside a component reset theirs with plain `m-0`. `test/stories.test.tsx` fails on a plain margin reset on any `[data-ouro]` element in any story.
- A required field's marker is CSS (`::after`) on the element around the label (`[data-ouro-label]`, or a group's `[data-ouro-legend]`), never an element or text inside the label and never `::after` on the label itself: a label's text is what Testing Library's `getByLabelText` and Playwright's `getByLabel` compare, and generated content on the labelling element counts toward the control's accessible name.
- A button inside a field (clear, show password, choose date, a file's or chip's remove button, a stepper) is named by visually hidden text, not `aria-label`: an `aria-label` is label text, so Playwright's `getByLabel("Password")` would also match a button labelled "Show password". The one exception is ColorField's swatch, a color `<input>`, which only label text can name; its `pickerLabel` docs say how to find the field.
- Overlay portals are `relative isolate z-(--ouro-layer)`: their own stacking context, at a level apps raise with the token rather than a class edit. Apps raise it in their own unlayered `:root` rule after the Ouro tokens, because `shadcn add` resets the line it wrote; the install test checks that such an override survives a re-add.
- Class strings are literals so Tailwind finds them; `app.css` scans `registry/`. Stories lay out with inline styles and the theme variables (`var(--muted-foreground)`).
- Write hover styles as `pointer-fine:hover:…`, never bare `hover:`: Tailwind's `hover:` checks only `(hover: hover)`, and the rule is `(hover: hover) and (pointer: fine)`, so a tap on a phone leaves no hover state behind.
- Interactive controls use the `press` utility (the scale arrives and releases in 160ms on `--ouro-ease-out`, colors ease in 150ms), a `motion-safe:` press scale of `--ouro-press-scale`, and `<TouchTarget />` (`registry/ouro/lib/ouro/touch-target.tsx`) as the first child of a `relative` root for the 44px coarse-pointer hit area. A linked list row (`Item` with `href`) highlights while pressed instead of scaling, because a full-width row that shrinks reads as a jump; it is at least 44px tall on a coarse pointer instead of using `<TouchTarget />`. A `ResizableHandle` changes color on hover (a mouse's only), focus and press instead of scaling, because a 1px splitter line that shrinks looks broken; it still uses `<TouchTarget />`.
- Dark mode is the `.dark` class on an ancestor, as in shadcn. The OS setting alone does not switch it.
- Keyframes are namespaced (`ouro-spin`), never Tailwind's global `spin` or `pulse`.
- Every variable Ouro UI adds that is not a shadcn color uses the `--ouro-` prefix (`--ouro-ease-out`, `--ouro-sheet-gap`); the prefix on the easing tokens is required, because Tailwind defines its own `--ease-out` and `--ease-in-out`, and an unprefixed token would change the `ease-out` class across the app that installs the library; `registry/ouro/theme/theme.test.tsx` checks the easing and duration tokens, the `press` timing and (until it is retired) the spring against Motion's `spring(0.4, 0.15)`, and checks the Ouro theme's text pairs at 4.5:1 in light and dark.

## Workflow

- Use pnpm 10. Run `pnpm run docs --check`, `pnpm registry --check`, `pnpm controls:matrix --check`, `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm motion:coverage` (right after `pnpm test`: a run of fewer tests rewrites the partitions of the projects it ran), `pnpm test:themes`, `pnpm conformance`, `pnpm test:scripts`, `pnpm test:e2e` and `pnpm build-storybook` before opening a pull request.
- Conformance matrix (`pnpm conformance`, `test/conformance/`, CI's sharded `conformance` job; [docs/guides/conformance.md](docs/guides/conformance.md)): every story, with nothing to opt into, through the checks that replace recurring review findings. After every action a person can take in it (a press, a character typed, an arrow key, Escape for each popup), focus is on an element still in the page and shown, and no live region announces the same text twice; its server HTML (UTC, en-US) hydrates in America/Los_Angeles with de-DE and Asia/Tokyo with ja-JP with no recoverable error or attribute mismatch; in a right-to-left page nothing sticks out of the viewport sideways; and under forced colours every box a person presses, types into, drags or scrolls keeps an edge, an on state looks unlike off, and keyboard focus shows. A story states what a check cannot see in `parameters.conformance` (`focusExit`, `announces`, `clientOnly`, each with its reason), and a declaration that is no longer true fails. Run one check or one component's stories while you work (`pnpm conformance test/conformance/rtl.test.tsx`, `pnpm conformance -t "Tabs/"`); `OURO_STORIES` and `OURO_CONFORMANCE_SHARD=<index>/<count>` select stories as CI does. Components hand focus on when a press removes them (`useFocusHandoff`, `lib/ouro/focus-handoff.ts`), keep a control that becomes unavailable where it is focusable (`aria-disabled`), read the time zone, locale, clock and randomness only after hydration (`useSyncExternalStore` with a server snapshot), use logical sides (`start-*`, `ms-*`, `pe-*`, `border-s`, `rounded-e`, `text-start`; `physicalUtilities` in `scripts/source-rules.mjs` fails on a physical one that `physicalAllowed` does not list with its reason), and draw edges, states and focus that forced colours keep (`forced-colors:border forced-colors:border-solid`, `forced-colors:data-pressed:bg-[Highlight] forced-colors:data-pressed:text-[HighlightText]`, outlines rather than box shadows).
- Mutation testing (`pnpm mutation [<base>] [--only <file>]`, `scripts/mutation.mjs`, CI's `mutation` job on a pull request; [docs/guides/conformance.md](docs/guides/conformance.md#tests-that-cannot-fail-mutation-testing)): Stryker changes each line the change added or altered in `registry/ouro/components/` and `registry/ouro/lib/ouro/` (not tests, stories or the test kit), one mutant at a time, and runs the mutated file's own tests in Chromium, then, for a mutant they miss, the tests of the components that import that `lib/` file (`scripts/mutation/plugins.mjs`, a Stryker runner over one Vitest instance, since Stryker's Vitest runner has no browser mode). A mutant no test fails on fails the run, named by file, line, mutator and replacement: add a test that fails on it, or, for a change that cannot alter behaviour, write `// Stryker disable next-line <Mutator>: <why>` on the line before; any other Stryker comment a change adds fails the run, and so does a rise in the disable count the change does not show. Tailwind classes in class positions (`className`, `cn()`/`cva()` arguments, `*Class` constants) and the `process.env.NODE_ENV` development check are not mutated; attribute names, selectors and markers are.
- Ratchet property tests (`scripts/kits/ratchets.test.mjs`, fast-check from a fixed seed; [docs/guides/conformance.md](docs/guides/conformance.md#ratchets-that-cannot-be-talked-around-property-tests)): whatever edit a generated case makes to the scan, the settings, the baselines, a rename or a removal, the census and source-rules ratchets never let a count rise, or a file go unread, without a recorded reason. A failing property prints its smallest case: add it to the kit's own tests with the fix.
- An app that installs a subset with its tests must reach 100% coverage of the files it installed. `node scripts/subset-coverage.mjs` (CI's `ci` job) checks it for button, dialog, sheet, the form controls and their union: it runs only the tests in the closure of each `<name>-tests` item and measures only the runtime files in it. When it fails, cover the line in the item's own tests (a new `<stem>.<case>.test.tsx` beside it), never in another component's.
- No component installs `ouro-base`, so nothing fails without it. In development, `useDevWarnings` (which every component calls) runs `checkTheme()` from `lib/ouro/dev.ts` once per page: when `--ouro-layer` is unset on the document root it logs the command that adds `ouro-base`. The tag in that command is kept in step by `pnpm run docs` (`syncedFiles`).
- The README's Next.js steps are what CI runs: `scripts/readme-steps.mjs` reads the quick start's and the Next.js section's add commands and its two files, and the `next` install variant runs exactly those and builds before it adds anything else. The `shadcn` variant type checks the React Router adapter from `docs/OuroProvider.md` against React Router itself.
- Links: `node scripts/links.mjs` (in `pnpm test:scripts`, and again over `site/dist` in CI) fails when a link in the README, the docs, a guide or an install message opens no page, letter case included, or when a `docs/*.md` file has no page on the site. Hand-written guides live in `docs/guides/` (`installing.md`, `testing.md`, `forms.md`); `pnpm run docs` lists them, and every export's page, in `site/src/docs/pages.json`, and writes the README's item list between the `items` markers.
- `docs/<Export>.md`, `docs/parts.md` and the catalog in `README.md` (between the `catalog` markers) are generated from the JSDoc and prop types in `registry/` by `pnpm run docs` (always with `run`: bare `pnpm docs` is pnpm's `npm docs`, which opens a browser) (`scripts/gen-docs.mts`, TypeScript compiler API) and committed; CI runs `pnpm run docs --check`. Edit the JSDoc, never the output. Generation fails when an export lacks a purpose or an `@example`, when a component lacks a "use X instead when" sentence, or when an export has no catalog group: each export names its group in its JSDoc (`@group Forms`), one of `groupOrder` in `scripts/catalog-groups.mts` (Actions, Text, Forms, Overlays, Menus, Feedback, Display, Lists, Layout, Navigation, Data, Chat) or `App setup` for what sets up an app rather than composing its screens (`OuroProvider`, and `Inspector`, X-ray); the catalog, the README and the site list each group that has exports, in that order, and each group's exports by name, App setup last. The site has a page for every component, App setup's included (`siteGroups`); the site's `DocsItem.group` type and tests read the same constants. The documented files and part files (`<folder>/<stem>-parts.tsx`) come from the components' `component.json`. Tag an export that is shared between registry files but not for apps with `@internal`.
- `test/stories.test.tsx` renders every story through `composeStories` and runs axe (zero violations) closed and with each overlay open, light and dark, at 390px and 1280px, in Chromium and WebKit. `test/stories.tsx` finds every `*.stories.tsx` by glob and keys it by its file name in PascalCase, so two story files may not share a name (it throws). A controlled story that opens its overlay from a plain button names it in the story's parameters (`parameters: { plainOpeners: ["Open"] }`), and a story that is a screenshot subject names its baseline there (`parameters: { screenshot: { name: "dialog-open", open: true } }`); the visual test fails when a committed baseline has no such story.
- Screenshot baselines (`test/__screenshots__/**/*-linux.png`, light, dark and reduced motion at 390px and 1280px) come from Linux CI only. To refresh them, run the `visual-baselines.yml` workflow on your branch, download its `visual-baselines` artifact into `test/__screenshots__`, review and commit. CI compares with `pnpm test:visual` in its `visual` job. Both workflows pin `ubuntu-24.04`, the image that rendered the baselines; moving to a new image means regenerating them. Local runs on macOS write `*-darwin.png` files, which git ignores.
- Source rules (`scripts/source-rules.test.mjs`): no registry file has a comment before its first statement, because the shadcn CLI drops it on install; start with the imports, or with an export list (`export { a, b };`) in a file without imports, and put the guidance in JSDoc after it. The install job checks that every installed file kept its source's comments. Write coverage hints as `/* istanbul ignore <next|if|else> @preserve -- reason */`; esbuild strips them without `@preserve`. Every test's full name (describe titles and title) is unique across the suite, so a name filter runs exactly one. No file name and no test title says a component "warns" or has "warnings" where a consumer's own "no warnings in tests" rule would read it as a failure (`alarmingFileName`, `alarmingTestTitle`: the helper is `use-dev-messages.ts`, and a title says what the message is about). Every runtime file under `components/ouro/` and every `lib/ouro/*.tsx` starts with `"use client";` (before the imports) unless it is pure: a component's `<stem>-styles.ts` (by its name) or a file on the pure list (`pureFiles` in `scripts/source-rules.mjs`: `touch-target.tsx`), and so does any other module that calls a hook (including React 19's `use()` and a hook imported from react under another name), calls `createContext` or defines a class component; no other file does, so a Next.js Server Component can render the components and still import plain values; the shadcn CLI keeps the directive in apps with `"rsc": true`, and its removal regex never matches the form with a semicolon, so apps with `"rsc": false` keep it too (the install check fails if an installed file loses it). That is deliberate: without the semicolon the CLI strips the directive from every other file only (its regex is global and stateful), and an app that later moves to Server Components would break. `docs/guides/installing.md` tells Vite apps how to silence the bundler's notice.
- Tests wait on conditions, never on fixed timers: `expect.poll` until a value is reached or a transition has finished (`getAnimations()` empty and two reads agree), `act` to flush React before asserting that something did not happen, and a frame for media query changes. A settle that runs in JavaScript (a spring) is invisible to `getAnimations()`, so it sets `data-ouro-settling` on the element while it runs, and tests wait for the attribute to clear. The projects give every poll 10s, so a loaded runner waits longer instead of failing; don't pass a shorter `timeout`.
- Test with Vitest browser mode. Projects: `ouro-chromium`, `ouro-webkit`, `ouro-touch` (files named `*.touch.test.ts(x)`, Chromium as a 390x844 touch phone), from `ouroTestProjects`, `visual` (files named `*.visual.test.ts(x)`, only when `CI_VISUAL=1`) and `themes` (`test/themes/`, Chromium, only when `OURO_THEMES=1`; it writes no motion evidence).
- Tests ship to apps, so they hold under any shadcn theme: compare with the theme's computed variables, never with Ouro's hex values (`themeColor` in `button.test.tsx`), and read compiled CSS with `pageCss()`, never by importing `app.css`. A component's tests, stories and spec import only items their `-tests` item depends on; a `-tests` item may depend on any runtime item.
- End-to-end specs: `pnpm test:e2e` starts Storybook and runs `registry/ouro/e2e/` in Chromium and WebKit.
- Screen-reader lane: `registry/ouro/e2e/screen-reader/*.sr.spec.ts` (repository-only, `repoOnlyDirs` in `scripts/registry.mts`) run with real VoiceOver (macOS, WebKit) and NVDA (Windows, Chromium) through Guidepup: `pnpm test:sr --project <voiceover|nvda>` (`playwright.screen-reader.config.ts`; `pnpm test:e2e` ignores them). `screen-reader.yml` runs them nightly on main and when dispatched with `source_sha`, the dispatched branch's tip; release.yml dispatches it for its release commit and tags only when it passes there. `scripts/sr-classify.mjs` sorts a failure into accessibility (blocks the release) and infrastructure (retried once by a release; the nightly run files one `screen-reader-infra` issue). Guidepup's setup rewrites VoiceOver and TCC settings, so the lane runs only on GitHub-hosted runners, read-only and without secrets, and never for a pull request. `docs/guides/screen-reader-lane.md` is the runbook.
- Custom browser commands live in `registry/ouro/lib/ouro/testing/commands.ts`: `commands.emulateMedia({ reducedMotion, colorScheme })`, `commands.drag({ from, to, steps, durationMs, hold })` (`hold` keeps the button down so a test can inspect the mid-drag state; release with `pointerPress({ action: "up" })`), `commands.flick`, `commands.tap`, `commands.touchDrag({ from, to, steps, durationMs })` (a one-finger drag with real touch input through CDP, for swipe gestures; Chromium only; pass `durationMs` whenever the result depends on the swipe's speed, as over scroll snap points, because without it the speed is whatever the machine manages), `commands.touchStep({ type, x, y })` (one step of such a gesture, for a finger held still mid-swipe; lift the finger with `touchEnd` in a `finally`, and a finger left down is lifted before the next gesture) `commands.pointerPress({ selector, action })` (holds the real mouse down so `:active` applies) and `commands.restoreTouch()` (turns Chromium's touch emulation back on; the `ouro-touch` setup calls it before every test, because a screenshot taller than the viewport, such as a failure screenshot of a tall page, drops it for the rest of the page's life, so read a burst of coarse-pointer failures in one touch worker on an older kit as one real failure plus fallout). Drag tests run in Chromium only.
- Contributors need Node 22.18 or later (`devEngines`; `.node-version` pins 24) because the scripts run through Node's type stripping.

## Registry

- `registry.json` is generated; never edit it. Run `pnpm registry` after adding, renaming or moving a registry file, changing an import, a theme CSS file, a dependency version or a component's JSDoc purpose, and commit the result. CI fails on a stale file.
- `scripts/registry.mts` derives everything from the layout. Each component is two items. `<name>` ships the runtime source only: `<stem>.tsx`, `<stem>-parts.tsx` and `<stem>-styles.ts` (`registry:ui`), targeted at `@components/ouro/<folder>/`. The opt-in `<name>-tests` ships its tests and type tests (`registry:component`), stories and `e2e/ouro/<stem>.spec.ts` (`registry:file`, to `~/e2e/ouro/`), depends on `<name>`, `ouro-testing` and the `-tests` item of everything `<name>` installs, and names the Storybook, Vitest and Playwright devDependencies. Each helper in `lib/ouro` is its own item, `lib-<stem>`, with `lib-<stem>-tests` for its tests, so a component installs only the helpers it imports (and `OuroProvider`, which only the app imports, comes with every component that renders links, through `lib-router-link`, and with `tooltip`, whose tooltips it groups; any other app adds `lib-ouro-provider` by name, which the README's Next.js steps do); `ouro-lib` and `ouro-lib-tests` depend on all of them, and `ouro-tests` depends on every `-tests` item. A runtime item that needs a devDependency fails the generator. `registryDependencies` come from the `@/registry/...` imports, as full unpinned addresses (`ourostack/ouro-ui/<item>`; release tags pin them, see Pages and releases); npm `dependencies` come from the imports, at the caret range in this repository's `package.json`. `devDependencies` carry no version, because the CLI hands a versioned one to the package manager on every add, which would move a version the app pinned; the minimum each tool needs is in the item's `meta.requires` and in `docs/guides/testing.md`. No item depends on `ouro-base` or `ouro-theme`: an item with `css` or `cssVars` in its tree makes the CLI rewrite the app's stylesheet, so the app adds `ouro-base` once and no later add touches its CSS (`scripts/registry.test.mjs` holds both rules). The theme items' `cssVars` and `css` come from `registry/ouro/theme/*.css`; a theme file may hold only `:root`, `.dark`, `@theme inline`, `@utility` and `@keyframes`. Descriptions and docs messages come from `docs/<Component>.md`.
- A runtime item's `registryDependencies` are its runtime imports only. Stories and tests count as imports of the `-tests` item (`heading-tests` depends on `button` through its stories), never of the component.
- A component file exports only components and types, so an app's React Fast Refresh lint passes: shared class strings, value lists and dev-message helpers go in `<stem>-styles.ts` (`sheet-styles.ts`, `dialog-styles.ts`, `text-styles.ts`), and hooks in their own module (`use-ouro.ts`).
- A component's docs message gives its import line and every Ouro item installed with it. `ouro-testing` starts its description with "Installed with every …; you don't need to add it."; `ouro-base` says to add it once. Theme tokens named `--ouro-*` go to the item's `css` under `:root` and `.dark`, not `cssVars`, so the CLI writes no self-referential `@theme inline` mapping for them; `scripts/install-check.mjs` fails on any `--x: var(--x)`.
- `ouro-theme` is a `registry:theme` (it replaces the app's colors, and the CLI warns before that); `ouro-base` is a `registry:item`, because it only adds variables.
- The `ouro-testing` docs message prints the files an app adds to run the shipped tests and specs (`testingSetup` in the script). `test/install-fixture-tests` holds those files verbatim, and the registry test fails if they drift or if the bare `test/install-fixture` has them.
- The components come from each folder's `component.json` (`scripts/components.mts`): `{ "order": 70, "components": ["text-field", "text-area"] }` lists the folder's component file stems (item name `<stem>`, export name the stem in PascalCase), and `order` places the folder in `registry.json` (equal orders sort by folder name). The manifest ships in no item. A registry file no item ships fails the generator unless it is in `repoOnly`. `pnpm registry` also writes the item list in `site/public/llms.txt` (`## Items`), and `--check` fails when it is stale.
- The shadcn CLI is pinned to `shadcn@4.21.1` in `.github/workflows/ci.yml`, `pages.yml` and `scripts/install-test.sh`.
- The install test (`scripts/install-test.sh <shadcn|ouro|namespace|next|upgrade> <dir>`) runs locally too. Every variant adds `ouro-base` first and then checks that no later add changes the stylesheet by a byte. The `shadcn` variant first strips `--input` and `--radius` from the preset's theme, so the shipped field spec proves `ouro-base` alone gives a field its border. With the test tools pinned to this repository's versions and a rule of its own in the stylesheet, it adds `sheet` and `button-tests` and compares the stylesheet and `package.json` byte for byte. It installs the runtime items into the bare fixture first and checks that they added no test, story, spec, test kit or test tooling, and that `npx vitest run` finds no tests; then it copies in `test/install-fixture-tests/`, adds `ouro-tests` and runs the shipped tests and specs. The `ouro` variant fetches `ouro-theme` from GitHub, so push first. Refs are not inherited by `registryDependencies`, so the script installs from a locally built copy of the registry whose dependencies point at the built item files (`--deps <dir>/{name}.json`). The `namespace` variant builds the namespace as Pages does, from the newest release tag (`scripts/namespace.sh`), serves it on localhost, registers `@ouro` in the app's `components.json` and installs `@ouro/dialog`, checking that every dependency came through the namespace, that no test item came with it, that each served item names that release and that every installed file equals the tag's source. The `next` variant creates a Next.js App Router app with `create-next-app` (TypeScript, Tailwind CSS v4, `src/`), runs `shadcn init` (which writes `"rsc": true`), adds every runtime item (the `registry:ui` items in `registry.json`, as every variant installs), renders each component from a Server Component page (ConfirmDialog's `onConfirm` is a server action) and runs `next build`. Each component has its own section, `test/install-fixture-next/src/app/sections/<item>.tsx`, whose `// expect: <pattern>` lines say what the prerendered page must hold; the script writes `sections/index.ts` from the files, and fails when a component has no section. The `upgrade` variant installs `dialog` at `#v0.1.0` from GitHub (which brings `button` and `sheet`) into an app with the v0.1.0 test setup and a test of its own (`test/install-fixture-upgrade/`), then runs the commands in `UPGRADING.md` against this commit's registry, in two layouts. In an `app/` layout with `~/*` aliases on `./app/*`, step 1 on an app with no Ouro component must stop without adding anything, then steps 1 to 3 run. In the `src/` layout, steps 1 and 2 run, and separately steps 1 to 3. Each app must type check, build, run its own test with its own config, keep the same components and have no self-referential token. The note's commands find the app's folders with `npx shadcn info --json` (`resolvedPaths`), never a hard-coded `src/`; `scripts/upgrade-note.test.mjs` also runs them with a stand-in `npx` in bash and zsh. The `github` variant is the ref-less install from `main`; CI runs it (job `install-github`) after each push to main.

## Adding a component

A component touches only its own files, so parallel pull requests do not conflict. Create:

1. `registry/ouro/components/ouro/<folder>/component.json`: `{ "order": <number after the last folder's>, "components": ["<stem>"] }`.
2. `registry/ouro/components/ouro/<folder>/<stem>.tsx` (and `<stem>-parts.tsx`, `<stem>-styles.ts` as needed), with JSDoc on each export including `@example` and `@group <group>`, one of Actions, Text, Forms, Overlays, Menus, Feedback, Display, Lists, Layout, Navigation, Data or Chat (`scripts/catalog-groups.mts`).
3. In the same folder: `<stem>.test.tsx`, `<stem>.test-d.ts` and `<stem>.stories.tsx` (story `parameters` for `plainOpeners` and `screenshot` where they apply), plus `registry/ouro/e2e/ouro/<stem>.spec.ts`.
4. `site/src/docs/demos/<stem>.demo.tsx`: the docs page's live demo, as its default export.
5. `test/install-fixture-next/src/app/sections/<stem>.tsx`: a Server Component section with `// expect: <text>` lines.
6. `scripts/fixtures/agent-types/<stem>.snippets.tsx` and `<stem>.cases.ts`, with snippet ids named after the component.
7. `changes/<stem>.md`: a `- New: ...` line. One top-level `- ` line per change, with no wrapped lines or sub-items: `scripts/changes.mjs check` fails on any other non-blank line, because only those lines reach the release notes.

Then regenerate, never hand-merge: `pnpm run docs` (`docs/`, `README.md`, `site/src/docs/catalog.json`) and `pnpm registry` (`registry.json`, `site/public/llms.txt`), and commit the result. After a rebase, run both again instead of resolving conflicts in those files. Screenshot baselines come from the `visual-baselines.yml` workflow.

## Pages and releases

- `pages.yml` publishes https://ourostack.github.io/ouro-ui/ after CI passes on a push to main (`workflow_run`; also runnable by hand): the site at `/`, Storybook at `/storybook/`, and the `@ouro` namespace registry at `/r/<item>.json` and `/r/registry.json`. The site and Storybook build from main. Before it builds, Pages asks GitHub for the newest release and, when main's `ouro.latestRelease` names an older one, sets it and regenerates the docs in the build, so the site, `llms.txt` and the namespace name a release as soon as Pages runs after it, whether or not main has caught up. The namespace builds from that tag (`scripts/namespace.sh`: the tag's own `registry.json`, rewritten by `scripts/registry.mts --from <file> --deps "@ouro/{name}"`, then `shadcn build` over the tag's files), so each item's same-repo dependencies resolve through the namespace and `@ouro` serves released code only. The unpinned GitHub path (`ourostack/ouro-ui/<item>`) still serves main, by nature; public docs use a tag or `@ouro` and call the unpinned path main, for contributors. Pages deploys only when the CI run it follows is for main's current tip, so an older run that finishes late never deploys over a newer one.
- Release by running the Release workflow (`release.yml`) with a `version` such as `0.1.0` (Actions, or `gh workflow run release.yml -f version=0.1.0`). It checks that CI passed on main's head, force-pushes `release/v<version>` from main with every same-repo `registryDependency` in `registry.json` pinned to `#v<version>`, a `version` field, and "Ouro UI v<version>." at the end of each item's `docs` message, so every `add` prints the version it installed (`pnpm registry --release <version>`). It builds the `@ouro` namespace from that commit (`scripts/namespace.sh "$RUNNER_TEMP/ns" <tag>`) and checks it with `node scripts/public-registry.mjs verify-build "$RUNNER_TEMP/ns" HEAD`: every item in the commit's `registry.json` has its `<item>.json` and no other item is there, each item equals the commit's entry with its same-repo dependencies at `@ouro/<item>`, each file's `content` equals the commit's file byte for byte, and the namespace's `registry.json` is the commit's (the counts come from that file). Then it runs CI on that commit (dispatched, because pushes made with `GITHUB_TOKEN` trigger no workflows; it waits on the run for that exact commit; on a release branch CI also installs with `shadcn@latest`, job `install-latest`). Then it dispatches the screen-reader lane (`screen-reader.yml`) for that commit and waits for it to pass there, dispatching once more after an infrastructure failure. When both pass, it tags the commit, creates the GitHub release with the items and both install commands, and deletes the branch. The release itself needs no pull request. Afterwards the run merges "Prepare main for the next release" once that pull request's checks pass, starts CI on main's new tip (a merge made with the workflow's token starts no workflow, and the next release needs a passing run there, so the release check accepts a dispatched run), waits for that exact tip's CI to pass, deploys Pages only if main still names the verified tip, and last runs `node scripts/published-release.mjs <tag> --wait 900`, which fails when an install command in the published `llms.txt` or main's README names another release, then `node scripts/public-registry.mjs verify-live <tag> --wait 900`, which builds the namespace from the tag into a temporary folder, checks it as `verify-build` does, and fails unless Pages serves every item (`/r/<item>.json`) and the index byte for byte as built, with no other item in the served index (it retries while the deploy is stale). Both modes run locally too (`verify-live` reads only public URLs). v0.7.0 showed why: the site named v0.6.0 for about two hours, because the prepare pull request waited for a person and Pages then skipped the deploys whose CI run was no longer for main's tip. If approval or merge fails, main CI is missing or fails, CI dispatch fails, or main moves before the Pages dispatch, the run fails without deploying Pages; the release remains published. Complete the prepare PR by hand if needed, then pass CI on main's current tip before deploying Pages. The daily `scheduled-install.yml` runs the same published-version check.
- Main is never pinned: only the tag points at the release commit. `pnpm registry --check` reads the `version` field, so CI on the release branch checks the pinned file; on main and on pull requests into main it fails on a `version` field or a `#v` dependency.
- Rerunning is safe. If the tag exists and has a release, the workflow exits with a notice. A failed run deletes its branch, so rerun after fixing the cause. Recovery:
  - CI failed on the release branch: fix main, then run Release again.
  - The tag exists without a GitHub release (the run fails and says so): delete the tag with `git push origin :refs/tags/v<version>`, then run Release again.
  - A wrong release was published: delete it with `gh release delete v<version> --cleanup-tag`, then release a new version (prefer a new version over reusing a published tag).
- `ourostack/ouro-ui/<item>#v<version>` installs the item and all its Ouro dependencies at that tag, because the tagged `registry.json` names them with the same tag.
- Install commands in the docs (`README.md`, `site/`, `site/public/llms.txt`, the release notes) use `npx shadcn@latest`, start with the `init` step (`init --base base --preset nova --yes --no-monorepo`) and pin the newest release tag. That tag has one source, `ouro.latestRelease` in `package.json` (`scripts/latest-release.mjs`): `pnpm run docs` writes it into README.md, llms.txt and package.json's description, the site imports it (`site/src/release.ts`), and Pages builds the namespace from it. Never edit a tag by hand: `scripts/latest-release.test.mjs` fails when a `#vX.Y.Z` or `@vX.Y.Z` literal in the docs names another tag. The same test and `site/src/site.test.tsx` fail on an install address with no ref or any ref but a release tag (`#main`, a branch, a commit; `scripts/addresses.mjs`), outside a sentence that says it is for contributors. release.yml sets the new tag on the release branch before it tags (`node scripts/latest-release.mjs set v<x.y.z>`, then `pnpm run docs`), so the tagged commit's README, llms.txt and site name that tag itself (UPGRADING.md keeps its placeholder) (`scripts/latest-release.test.mjs` runs those commands on a copy); its "Prepare main for the next release" PR does the same on main, and when it merges, the docs, the site and `@ouro` move to the release. On the release branch, before the tag exists, `scripts/namespace.sh` builds the namespace from the checkout, whose `registry.json` already is that release. Release advises deleting a tag only when GitHub answers "release not found"; any other error fails with the raw message. `pnpm registry --check` reads only `registry.json`, so a tag in the docs never fails it; `registry.json` on main stays unpinned. The install test and CI keep the exact `shadcn@4.21.1` they verify.
