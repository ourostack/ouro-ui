# Contributing to Ouro UI

Rules for people and coding agents who change this repository. (Consumers read `README.md` and `docs/`, not this file.)

## Project constraints

- Copy-in source distributed as a shadcn/ui registry; MIT license, repository `https://github.com/ourostack/ouro-ui`. There is no npm package and no build: apps compile the components with their own Tailwind CSS v4.
- No code is copied from Tailwind Catalyst or Tailwind Plus. Ideas only.
- Touch targets are at least 44px on coarse pointers (`@media (pointer: coarse)`).
- With `prefers-reduced-motion: reduce`, no transform or position change animates. Opacity may still animate.
- The default breakpoint `sm` is 640px. Below it, `Dialog` with `presentation="auto"` renders as a sheet.
- CI gates: `pnpm run docs --check`, type check, lint, unit and browser tests with 100% line and branch coverage (measured over `registry/**`, without stories, `registry/ouro/lib/ouro/testing/` and `registry/ouro/e2e/`), the script tests (including `scripts/app-lint.test.mjs`, which lints the runtime items' source with a stock Vite app's oxlint config and allows no warnings) and the Storybook build (job `ci`); `pnpm registry --check` and `shadcn registry validate` (job `registry`); the end-to-end specs against Storybook (job `e2e`); and the install test (job `install`: the `shadcn`, `ouro`, `namespace` and `next` variants; job `install-upgrade`: the `upgrade` variant). Workflows pin every action to a full commit SHA with a `# vX.Y.Z` comment, and only release.yml keeps the checkout's credentials (`scripts/workflows.test.mjs`); Dependabot proposes new pins weekly (`.github/dependabot.yml`). `scheduled-install.yml` runs the install matrix weekly against main and the newest release tag, because item dependency ranges float, and fails when main's `ouro.latestRelease` is not GitHub's newest release. Any failure opens, or comments on, one "Scheduled install failed" issue (`scripts/scheduled-failure.sh`), so it shows where we look. GitHub pauses scheduled workflows in a public repository after 60 days with no repository activity, and the pause raises no issue: after a quiet spell, check that the workflow is still enabled (Actions, or `gh workflow enable scheduled-install.yml`).
- Never add AI attribution to commits, pull requests, code or docs (no `Co-Authored-By`, no "Generated with").

## Dev message format

Exact format: `[ouro-ui] <Component>: <what's wrong>. Fix: <exact code>.`

- Emit each message once per component instance.
- Strip messages in production with the bare `process.env.NODE_ENV !== "production"` form, with no `typeof process` guard, so bundlers replace it statically and drop the dead branch. Put the check at each warn call site (`if (process.env.NODE_ENV !== "production") devWarn(...)`), and build `devThrow`'s fix argument only inside a development branch. `scripts/dev-strip.test.mjs` bundles a probe with Vite in production mode and asserts the message strings are gone.
- Consumers need a bundler that defines `process.env.NODE_ENV` (Vite, Next.js, webpack and React Router all do). Without one, dev messages are not stripped and the bare reference throws in a browser.

## Appearance classes warn

A `className` token warns when, after removing variants (split on `:` outside `[...]`) and a leading or trailing `!`, its base matches `/^(bg|text|border|rounded|shadow|font|ring|from|via|to|fill|stroke)-/` or is exactly `border`, `rounded`, `shadow` or `ring`, or when `dark` appears at any variant position. Ordinary layout classes (`mt-4`, `w-full`, `grid-cols-2`, `size-4`) never warn, and neither do text wrapping, text overflow and table layout classes that share a prefix (`text-wrap`, `text-nowrap`, `text-balance`, `text-pretty`, `text-ellipsis`, `text-clip`, `border-collapse`, `border-separate`, `border-spacing-*`). Alignment classes (`text-left|center|right|justify|start|end`) also warn, and the message points to the component's `align` prop where one exists (the `alignHint` argument), or else shows the class on a parent element. Hints are exact code, such as `tone="destructive"`. A component may pass a hint function that picks the fix from the offending token (`registry/ouro/lib/ouro/appearance-hints.ts` maps `bg-red-500` to `tone="destructive"` and `text-lg` to `size="lg"`); pass hints only in development (`process.env.NODE_ENV !== "production" ? hint : ""`) so their text is stripped.

## Rules for writing components (spec section 4)

1. Props-first: the default export takes props that describe the whole thing; building-block parts live in the component's `-parts` file and their JSDoc says when to use them.
2. Anything that "always" applies is a required prop (`title` with `hideTitle`, `label` with `hideLabel`, `legend`, `name`); leaving it out is a type error.
3. One state, one prop: `error`, `loading`, `disabled`, `required` each handle all of their ARIA, messaging and animation.
4. Appearance comes from named options (`tone`, `variant`, `size`) that map to theme tokens, never color names or classes.
5. `className` is for layout only; warn in development about appearance classes and give common layout needs a prop (for example `fullWidth`).
6. The prop agents guess is the prop that exists: use the common name, or declare it as a hint type that nothing is assignable to, with JSDoc pointing to the real prop (`isLoading?: { 'Use <Button loading>': never }`), so the type error names the fix. Every enum prop also takes one `string & { '<the fixes>': never }` member (`tone`'s `'danger is "destructive"; …'`, shadcn's Button variants and sizes, and the value list where the type is an alias such as `SheetSide`; parts' enum props and numeric ones such as Heading's `level` too), kept short and ASCII so `tsc` prints the whole union, and an unknown value renders the default and warns in development. Why not plain `never` or a plain literal union: an attribute whose expected type is a literal (`never` reads as `undefined`) and whose value doesn't match rules out every branch of a union-typed props object, and TypeScript then drops the hover JSDoc of every prop on the element. Keep the HTML attributes outside a props union (`Text`), or hover is lost even in valid code. The mode-exclusion props (`trigger?: never` with `open`) stay `never`: as hint types they lose hover on `trigger`, `open` and `onOpenChange` in valid code, so an element that passes both modes shows no hover and relies on the development error, which names the fix. `scripts/fixtures/agent-types/` holds the agent snippets and, in `cases.ts`, which channel (type error, hover, development message) names each fix; `scripts/agent-types.test.mjs` and `test/agent-types.test.tsx` check them.
7. Mode-dependent types follow the mode with discriminated unions (`multiple` makes `Select` use `string[]`; `href` makes `Button` a link).
8. Parts check where they are: outside their parent they throw in development with the correct JSX shape; where it is safe, the parent wraps loose children instead.
9. Docs live in the types: every export has JSDoc with a one-line purpose, a minimal example and "use X instead when" guidance; `README.md` holds the catalog and `docs/<component>.md` a page per component.
10. Behavior and motion are the component's job (dialog-to-sheet on phones, focus, touch targets, durations, springs, reduced motion); no component takes a duration or easing prop, motion comes from theme tokens. Components animate with CSS only (Base UI's `data-starting-style`/`data-ending-style` transitions, the theme spring as a `linear()` easing) and honor reduced motion with `motion-reduce:`/`motion-safe:` variants and `prefers-reduced-motion` queries. No registry item depends on the `motion` package; it is a dev dependency here only for the RedwoodUI reference story and the theme test's spring check. A component that ever needs Motion must wrap its own usage in `MotionConfig reducedMotion="user"` (or use `useReducedMotion`) and must not rely on `OuroProvider`, which is optional.
11. Errors teach: every dev message uses the format above.
12. Higher-level patterns capture whole interactions agents assemble badly (`ConfirmDialog`, later `EditSheet`).

## Layout

The layout mirrors where shadcn installs files, so the CLI's import rewrite lands them in `components/ouro/` and `lib/ouro/` (spec §3).

- `registry/ouro/components/ouro/<component>/`: components, their parts, tests and stories.
- `registry/ouro/lib/ouro/`: shared helpers and hooks (`cn`, dev messages, the className check, `OuroProvider`, tone names, `useMediaQuery`, `useKeyboardScrollable`, the backdrop anchor, `TouchTarget`, and `env.d.ts`, which declares `process.env.NODE_ENV` so apps without `@types/node` typecheck; `pnpm typecheck` also checks the registry source without Node types).
- `registry/ouro/lib/ouro/testing/`: the test kit the `ouro-testing` item ships: the `act` helper, the custom browser commands, `pageCss()`, `axeExclude` (`axe.ts`, the Base UI focus guards to leave out of an axe scan), the act-warning setup and `ouroTestProjects` (`vitest.ts`), the Vitest browser projects apps add to their config. This repository's `vitest.config.ts` uses the same projects.
- `registry/ouro/e2e/ouro/`: one Playwright spec per component, installed to an app's `e2e/ouro/`, and `story.ts`, which opens a story by id in the Storybook at `OURO_E2E_URL` (default `http://localhost:6006`). Specs ship as `registry:file`, which the CLI does not rewrite, so they import only `@playwright/test` and `./story`.
- `registry/ouro/theme/ouro-base.css`: required in every app. The success and warning pairs and `--destructive-foreground` (which shadcn's themes lack), the `--ouro-*` motion tokens, `--ouro-layer` (the z-index of the Dialog and Sheet portals, 50 as in shadcn's overlays), the `press` utility and the keyframes.
- `registry/ouro/theme/ouro-theme.css`: optional. The Ouro color look as a shadcn theme (`:root` and `.dark` values only).
- `app.css`: the repository as its own app. It imports Tailwind, `ouro-base.css` and `ouro-theme.css`, adds the `@custom-variant dark` and `@theme inline` mapping `shadcn init` writes, and scans `registry/`; Storybook and the Vitest projects compile it with `@tailwindcss/vite`.
- `stories/reference/`: repository-only stories, such as the Sheet feel comparison with RedwoodUI's ActionSheet; they ship in no item.
- `registry.json`: the shadcn registry, generated by `pnpm registry` (`scripts/registry.mts`) and committed; see Registry below.
- `test/install-fixture/`: the bare Vite app the install test (`scripts/install-test.sh`) copies, runs `shadcn init` in and installs every component into, with no test config. `test/install-fixture-tests/`: the files the `ouro-testing` docs message tells an app to add (`vitest.config.ts`, `.storybook/`, `playwright.config.ts`), which the install test copies in before it adds `ouro-tests`. `test/install-fixture-upgrade/`: what the `upgrade` variant adds on top of those: a Vitest config with a project for the app's own test beside `ouroTestProjects`, and that test.
- `CHANGES.md`: the behaviour changes since the last release, which release.yml prints at the top of the release notes. Add a `- ` line when a change alters what an app sees (a stacking level, a focus target, a dependency range). Release refuses to start while the file lists no change, or while it still lists a change from the last release's notes (`scripts/changes.mjs check`). After a release, release.yml opens "Prepare main for the next release", which leaves only the heading and makes the new tag the newest release (see Pages and releases); merge it before adding the next release's lines. That PR is opened with GITHUB_TOKEN, so GitHub records its `pull_request` CI run but holds it (`action_required`, no jobs), and main's ruleset counts only `pull_request`-event checks, not a dispatched run. release.yml therefore finds the held run on the PR's head and approves it (`gh api -X POST repos/ourostack/ouro-ui/actions/runs/<run id>/approve`, with `actions: write`). GitHub documents that endpoint for fork PRs and names only OAuth and classic personal access tokens ([docs](https://docs.github.com/en/rest/actions/workflow-runs#approve-a-workflow-run-for-a-fork-pull-request)), so if GITHUB_TOKEN is refused, the workflow warns, dispatches CI on the branch (a signal only, not what the ruleset counts) and writes the exact approve command to the job summary and the PR body: run it as a maintainer, then wait for the checks. Never add a ruleset bypass for the bot.
- `UPGRADING.md`: "Upgrading from v0.1.0", the one copy of the note, with a short "What changed, by version" list of the changes an app must act on (keep it in step with CHANGES.md when a release adds one). Its addresses end in `#{{latestRelease}}`, a placeholder each copy fills, and a line under its title tells readers of the raw file what it stands for; every copy drops that line (`rawHint`): `pnpm run docs` copies its body into README.md with the newest release, the site's Updating page renders it the same way, release.yml prints it into the release notes with the release tag, and the `upgrade` install test runs its commands (`scripts/upgrade-note.mjs`). Edit only this file; `scripts/upgrade-note.test.mjs` fails if a copy of a command appears anywhere else.
- `test/`: the story-wide accessibility test, the screenshot test and their baselines, and `stock-theme.test.tsx`, which checks every tone and variant at 4.5:1 under stock shadcn variables (`test/shadcn-stock.css`, copied from `shadcn init`) plus `ouro-base.css`, and under the Ouro theme.
- `site/`: the landing page and docs site (https://ourostack.github.io/ouro-ui/), built with Vite from the root dependencies, not a workspace package. Docs pages render the generated `docs/*.md`; each registry item's page is `docs/<item name>/`. `pnpm site:build` writes `site/dist` (prerendered HTML per route, with Open Graph and Twitter tags from `site/src/head.ts`), `pnpm site:dev` serves it. `site/public/og.png`, the 1200x630 link-preview image, is a screenshot of the landing page with its sheet open; regenerate it with `node site/scripts/og-image.mts` after the landing page changes, review it and commit it. The "Agents read the types" examples live in `site/src/agents/examples.ts`; `pnpm site:messages` regenerates their compiler output (`site:build` and `pnpm test:scripts` fail when it is stale), and the `site` Vitest project checks each quoted dev message against the real component.
- Imports between registry files use `@/registry/ouro/...`, which the shadcn CLI rewrites to an app's aliases on install. `@/` resolves to the repository root (tsconfig `paths` and the Vite alias).

## Component conventions

- Every component root carries `data-ouro="<component>"`, so apps can exclude Ouro UI subtrees from global rules.
- Style with plain Tailwind utilities on shadcn's token names (`bg-primary`, `text-muted-foreground`, `border-border`, `rounded-lg`), merged with `cn(...)` with the app's `className` last, so the app's layout classes win. There is no prefix and no stylesheet per component.
- A layout property the app may override (`h-*`, `px-*`) is one unprefixed class at every width. When it changes at a breakpoint, the class reads a variable and the breakpoint sets the variable (`h-(--ouro-button-h) [--ouro-button-h:…] sm:[--ouro-button-h:…]`), so tailwind-merge replaces it with the app's class.
- `tone` values are the theme token names: `primary`, `secondary`, `destructive`, `success`, `warning`. `secondary` has shadcn's meaning: a quiet surface (`bg-secondary text-secondary-foreground`), never a text color, so Text's `secondary` is the muted foreground. `variant="soft"` is the tone at 10% behind text in the tone mixed 20% toward the foreground (shadcn's stock destructive fails 4.5:1 on its own tint otherwise). Focus outlines use `outline-ring` for every tone. A tone, variant or size that is not one of ours (`tone="danger"`, shadcn's `variant="destructive"` or `size="icon"`) renders the default and warns with the fix.
- There is no reset, so reset what the browser sets (button borders, backgrounds, margins on `<p>` and headings, `box-sizing`) in the component's own classes.
- Overlay portals are `relative isolate z-(--ouro-layer)`: their own stacking context, at a level apps raise with the token rather than a class edit. Apps raise it in their own unlayered `:root` rule after the Ouro tokens, because `shadcn add` resets the line it wrote; the install test checks that such an override survives a re-add.
- Class strings are literals so Tailwind finds them; `app.css` scans `registry/`. Stories lay out with inline styles and the theme variables (`var(--muted-foreground)`).
- Interactive controls use the `press` utility (spring release, quick color easing), a `motion-safe:` press scale of `--ouro-press-scale`, and `<TouchTarget />` (`registry/ouro/lib/ouro/touch-target.tsx`) as the first child of a `relative` root for the 44px coarse-pointer hit area.
- Dark mode is the `.dark` class on an ancestor, as in shadcn. The OS setting alone does not switch it.
- Keyframes are namespaced (`ouro-spin`), never Tailwind's global `spin` or `pulse`.
- Every variable Ouro UI adds that is not a shadcn color uses the `--ouro-` prefix (`--ouro-spring-duration`, `--ouro-sheet-gap`); `registry/ouro/theme/theme.test.tsx` checks the spring against Motion's `spring(0.4, 0.15)` and checks the Ouro theme's text pairs at 4.5:1 in light and dark.

## Workflow

- Use pnpm 10. Run `pnpm run docs --check`, `pnpm registry --check`, `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm test:scripts`, `pnpm test:e2e` and `pnpm build-storybook` before opening a pull request.
- `docs/<Export>.md`, `docs/parts.md` and the catalog in `README.md` (between the `catalog` markers) are generated from the JSDoc and prop types in `registry/` by `pnpm run docs` (always with `run`: bare `pnpm docs` is pnpm's `npm docs`, which opens a browser) (`scripts/gen-docs.mts`, TypeScript compiler API) and committed; CI runs `pnpm run docs --check`. Edit the JSDoc, never the output. Generation fails when an export lacks a purpose or an `@example`, when a component lacks a "use X instead when" sentence, or when a new export has no catalog group (`groups` in the script). Tag an export that is shared between registry files but not for apps with `@internal`.
- `test/stories.test.tsx` renders every story through `composeStories` and runs axe (zero violations) closed and with each overlay open, light and dark, at 390px and 1280px, in Chromium and WebKit. A new `*.stories.tsx` file must be added to `test/stories.tsx`; a controlled story that opens from a plain button lists it in `plainOpeners` there.
- Screenshot baselines (`test/__screenshots__/**/*-linux.png`, light, dark and reduced motion at 390px and 1280px) come from Linux CI only. To refresh them, run the `visual-baselines.yml` workflow on your branch, download its `visual-baselines` artifact into `test/__screenshots__`, review and commit. CI compares with `pnpm test:visual` in its `visual` job. Both workflows pin `ubuntu-24.04`, the image that rendered the baselines; moving to a new image means regenerating them. Local runs on macOS write `*-darwin.png` files, which git ignores.
- Source rules (`scripts/source-rules.test.mjs`): no registry file has a comment before its first statement, because the shadcn CLI drops it on install; start with the imports, or with an export list (`export { a, b };`) in a file without imports, and put the guidance in JSDoc after it. The install job checks that every installed file kept its source's comments. Write coverage hints as `/* istanbul ignore <next|if|else> @preserve -- reason */`; esbuild strips them without `@preserve`. Every test's full name (describe titles and title) is unique across the suite, so a name filter runs exactly one. Every runtime file under `components/ouro/` and every `lib/ouro/*.tsx` starts with `"use client";` (before the imports) unless it is on the pure list (`pureFiles` in `scripts/source-rules.mjs`: the `-styles.ts` files and `touch-target.tsx`), and so does any other module that calls a hook (including React 19's `use()` and a hook imported from react under another name), calls `createContext` or defines a class component; no other file does, so a Next.js Server Component can render the components and still import plain values; the shadcn CLI keeps the directive in apps with `"rsc": true`, and its removal regex never matches the form with a semicolon, so Vite apps keep it too (the install check fails if an installed file loses it).
- Tests wait on conditions, never on fixed timers: `expect.poll` until a value is reached or a transition has finished (`getAnimations()` empty and two reads agree), `act` to flush React before asserting that something did not happen, and a frame for media query changes. The projects give every poll 10s, so a loaded runner waits longer instead of failing; don't pass a shorter `timeout`.
- Test with Vitest browser mode. Projects: `ouro-chromium`, `ouro-webkit`, `ouro-touch` (files named `*.touch.test.ts(x)`, Chromium as a 390x844 touch phone), from `ouroTestProjects`, and `visual` (files named `*.visual.test.ts(x)`, only when `CI_VISUAL=1`).
- Tests ship to apps, so they hold under any shadcn theme: compare with the theme's computed variables, never with Ouro's hex values (`themeColor` in `button.test.tsx`), and read compiled CSS with `pageCss()`, never by importing `app.css`. A component's tests, stories and spec import only items their `-tests` item depends on; a `-tests` item may depend on any runtime item.
- End-to-end specs: `pnpm test:e2e` starts Storybook and runs `registry/ouro/e2e/` in Chromium and WebKit.
- Custom browser commands live in `registry/ouro/lib/ouro/testing/commands.ts`: `commands.emulateMedia({ reducedMotion, colorScheme })`, `commands.drag({ from, to, steps, durationMs, hold })` (`hold` keeps the button down so a test can inspect the mid-drag state; release with `pointerPress({ action: "up" })`), `commands.flick`, `commands.tap` and `commands.pointerPress({ selector, action })` (holds the real mouse down so `:active` applies). Drag tests run in Chromium only.
- Contributors need Node 22.18 or later (`devEngines`; `.node-version` pins 24) because the scripts run through Node's type stripping.

## Registry

- `registry.json` is generated; never edit it. Run `pnpm registry` after adding, renaming or moving a registry file, changing an import, a theme CSS file, a dependency version or a component's JSDoc purpose, and commit the result. CI fails on a stale file.
- `scripts/registry.mts` derives everything from the layout. Each component is two items. `<name>` ships the runtime source only: `<stem>.tsx`, `<stem>-parts.tsx` and `<stem>-styles.ts` (`registry:ui`), targeted at `@components/ouro/<folder>/`. The opt-in `<name>-tests` ships its tests and type tests (`registry:component`), stories and `e2e/ouro/<stem>.spec.ts` (`registry:file`, to `~/e2e/ouro/`), depends on `<name>` and `ouro-testing`, and carries the Storybook, Vitest and Playwright devDependencies. `ouro-lib-tests` holds `lib/ouro`'s tests, and `ouro-tests` depends on every `-tests` item. A runtime item that needs a devDependency fails the generator. `registryDependencies` come from the `@/registry/...` imports, as full unpinned addresses (`ourostack/ouro-ui/<item>`; release tags pin them, see Pages and releases); npm `dependencies` and `devDependencies` come from the imports, at the range in this repository's `package.json`. The theme items' `cssVars` and `css` come from `registry/ouro/theme/*.css`; a theme file may hold only `:root`, `.dark`, `@theme inline`, `@utility` and `@keyframes`. Descriptions and docs messages come from `docs/<Component>.md`.
- A runtime item's `registryDependencies` are its runtime imports only. Stories and tests count as imports of the `-tests` item (`heading-tests` depends on `button` through its stories), never of the component.
- A component file exports only components and types, so an app's React Fast Refresh lint passes: shared class strings, value lists and dev-message helpers go in `<stem>-styles.ts` (`sheet-styles.ts`, `dialog-styles.ts`, `text-styles.ts`), and hooks in their own module (`use-ouro.ts`).
- A component's docs message gives its import line and every Ouro item installed with it. `ouro-base`, `ouro-lib` and `ouro-testing` start their descriptions with "Installed with every …; you don't need to add it." Theme tokens named `--ouro-*` go to the item's `css` under `:root` and `.dark`, not `cssVars`, so the CLI writes no self-referential `@theme inline` mapping for them; `scripts/install-check.mjs` fails on any `--x: var(--x)`.
- `ouro-theme` is a `registry:theme` (it replaces the app's colors, and the CLI warns before that); `ouro-base` is a `registry:item`, because it only adds variables.
- The `ouro-testing` docs message prints the files an app adds to run the shipped tests and specs (`testingSetup` in the script). `test/install-fixture-tests` holds those files verbatim, and the registry test fails if they drift or if the bare `test/install-fixture` has them.
- A new component goes in the script's `components` list; a registry file no item ships fails the generator unless it is in `repoOnly`.
- The shadcn CLI is pinned to `shadcn@4.21.1` in `.github/workflows/ci.yml`, `pages.yml` and `scripts/install-test.sh`.
- The install test (`scripts/install-test.sh <shadcn|ouro|namespace|next|upgrade> <dir>`) runs locally too. It installs the runtime items into the bare fixture first and checks that they added no test, story, spec, test kit or test tooling, and that `npx vitest run` finds no tests; then it copies in `test/install-fixture-tests/`, adds `ouro-tests` and runs the shipped tests and specs. The `ouro` variant fetches `ouro-theme` from GitHub, so push first. Refs are not inherited by `registryDependencies`, so the script installs from a locally built copy of the registry whose dependencies point at the built item files (`--deps <dir>/{name}.json`). The `namespace` variant builds the namespace as Pages does, from the newest release tag (`scripts/namespace.sh`), serves it on localhost, registers `@ouro` in the app's `components.json` and installs `@ouro/dialog`, checking that every dependency came through the namespace, that no test item came with it, that each served item names that release and that every installed file equals the tag's source. The `next` variant creates a Next.js App Router app with `create-next-app` (TypeScript, Tailwind CSS v4, `src/`), runs `shadcn init` (which writes `"rsc": true`), adds every runtime item, renders each component from a Server Component page (ConfirmDialog's `onConfirm` is a server action) and runs `next build`; the prerendered page must hold each component's text. The `upgrade` variant installs `dialog` at `#v0.1.0` from GitHub (which brings `button` and `sheet`) into an app with the v0.1.0 test setup and a test of its own (`test/install-fixture-upgrade/`), then runs the commands in `UPGRADING.md` against this commit's registry, in two layouts. In an `app/` layout with `~/*` aliases on `./app/*`, step 1 on an app with no Ouro component must stop without adding anything, then steps 1 to 3 run. In the `src/` layout, steps 1 and 2 run, and separately steps 1 to 3. Each app must type check, build, run its own test with its own config, keep the same components and have no self-referential token. The note's commands find the app's folders with `npx shadcn info --json` (`resolvedPaths`), never a hard-coded `src/`; `scripts/upgrade-note.test.mjs` also runs them with a stand-in `npx` in bash and zsh. The `github` variant is the ref-less install from `main`; CI runs it (job `install-github`) after each push to main.

## Pages and releases

- `pages.yml` publishes https://ourostack.github.io/ouro-ui/ after CI passes on a push to main (`workflow_run`; also runnable by hand): the site at `/`, Storybook at `/storybook/`, and the `@ouro` namespace registry at `/r/<item>.json` and `/r/registry.json`. The site and Storybook build from main. The namespace builds from the newest release tag, `ouro.latestRelease` in main's package.json (`scripts/namespace.sh`: the tag's own `registry.json`, rewritten by `scripts/registry.mts --from <file> --deps "@ouro/{name}"`, then `shadcn build` over the tag's files), so each item's same-repo dependencies resolve through the namespace and `@ouro` serves released code only. The unpinned GitHub path (`ourostack/ouro-ui/<item>`) still serves main, by nature; public docs use a tag or `@ouro` and call the unpinned path main, for contributors. Pages deploys only when the CI run it follows is for main's current tip, so an older run that finishes late never deploys over a newer one.
- Release by running the Release workflow (`release.yml`) with a `version` such as `0.1.0` (Actions, or `gh workflow run release.yml -f version=0.1.0`). It checks that CI passed on main's head, force-pushes `release/v<version>` from main with every same-repo `registryDependency` in `registry.json` pinned to `#v<version>`, a `version` field, and "Ouro UI v<version>." at the end of each item's `docs` message, so every `add` prints the version it installed (`pnpm registry --release <version>`), and runs CI on that commit (dispatched, because pushes made with `GITHUB_TOKEN` trigger no workflows; it waits on the run for that exact commit). When CI passes, it tags the commit, creates the GitHub release with the items and both install commands, and deletes the branch. There is no pull request.
- Main is never pinned: only the tag points at the release commit. `pnpm registry --check` reads the `version` field, so CI on the release branch checks the pinned file; on main and on pull requests into main it fails on a `version` field or a `#v` dependency.
- Rerunning is safe. If the tag exists and has a release, the workflow exits with a notice. A failed run deletes its branch, so rerun after fixing the cause. Recovery:
  - CI failed on the release branch: fix main, then run Release again.
  - The tag exists without a GitHub release (the run fails and says so): delete the tag with `git push origin :refs/tags/v<version>`, then run Release again.
  - A wrong release was published: delete it with `gh release delete v<version> --cleanup-tag`, then release a new version (prefer a new version over reusing a published tag).
- `ourostack/ouro-ui/<item>#v<version>` installs the item and all its Ouro dependencies at that tag, because the tagged `registry.json` names them with the same tag.
- Install commands in the docs (`README.md`, `site/`, `site/public/llms.txt`, the release notes) use `npx shadcn@latest`, start with the `init` step (`init --base base --preset nova --yes --no-monorepo`) and pin the newest release tag. That tag has one source, `ouro.latestRelease` in `package.json` (`scripts/latest-release.mjs`): `pnpm run docs` writes it into README.md, llms.txt and package.json's description, the site imports it (`site/src/release.ts`), and Pages builds the namespace from it. Never edit a tag by hand: `scripts/latest-release.test.mjs` fails when a `#vX.Y.Z` or `@vX.Y.Z` literal in the docs names another tag. The same test and `site/src/site.test.tsx` fail on an install address with no ref or any ref but a release tag (`#main`, a branch, a commit; `scripts/addresses.mjs`), outside a sentence that says it is for contributors. release.yml sets the new tag on the release branch before it tags (`node scripts/latest-release.mjs set v<x.y.z>`, then `pnpm run docs`), so the tagged commit's README, llms.txt and site name that tag itself (UPGRADING.md keeps its placeholder) (`scripts/latest-release.test.mjs` runs those commands on a copy); its "Prepare main for the next release" PR does the same on main, and when it merges, the docs, the site and `@ouro` move to the release. On the release branch, before the tag exists, `scripts/namespace.sh` builds the namespace from the checkout, whose `registry.json` already is that release. Release advises deleting a tag only when GitHub answers "release not found"; any other error fails with the raw message. `pnpm registry --check` reads only `registry.json`, so a tag in the docs never fails it; `registry.json` on main stays unpinned. The install test and CI keep the exact `shadcn@4.21.1` they verify.
