# Contributing to Ouro UI

Rules for people and coding agents who change this repository. (Consumers read `README.md` and `docs/`, not this file.)

## Project constraints

- Copy-in source distributed as a shadcn/ui registry; MIT license, repository `https://github.com/ourostack/ouro-ui`. There is no npm package and no build: apps compile the components with their own Tailwind CSS v4.
- No code is copied from Tailwind Catalyst or Tailwind Plus. Ideas only.
- Touch targets are at least 44px on coarse pointers (`@media (pointer: coarse)`).
- With `prefers-reduced-motion: reduce`, no transform or position change animates. Opacity may still animate. Translucent surfaces also honor `prefers-reduced-transparency` (solid surface, no blur) and `prefers-contrast: more` (solid background, defined border).
- The default breakpoint `sm` is 640px. Below it, `Dialog` with `presentation="auto"` renders as a sheet.
- CI gates: `pnpm run docs --check`, type check, lint, unit and browser tests with 100% line and branch coverage (measured over `registry/**`, without stories, `registry/ouro/lib/ouro/testing/` and `registry/ouro/e2e/`), the script tests (including `scripts/app-lint.test.mjs`, which lints the runtime items' source with a stock Vite app's oxlint config and allows no warnings) and the Storybook build (job `ci`); `pnpm registry --check` and `shadcn registry validate` (job `registry`); the end-to-end specs against Storybook (job `e2e`); and the install test (job `install`: the `shadcn`, `ouro`, `namespace` and `next` variants; job `install-upgrade`: the `upgrade` variant). Workflows pin every action to a full commit SHA with a `# vX.Y.Z` comment, and only release.yml keeps the checkout's credentials (`scripts/workflows.test.mjs`); Dependabot proposes new pins weekly (`.github/dependabot.yml`). `scheduled-install.yml` runs the install matrix weekly against main and the newest release tag, because item dependency ranges float, and fails when main's `ouro.latestRelease` is not GitHub's newest release. Any failure opens, or comments on, one "Scheduled install failed" issue (`scripts/scheduled-failure.sh`), so it shows where we look. GitHub pauses scheduled workflows in a public repository after 60 days with no repository activity, and the pause raises no issue: after a quiet spell, check that the workflow is still enabled (Actions, or `gh workflow enable scheduled-install.yml`).
- Never add AI attribution to commits, pull requests, code or docs (no `Co-Authored-By`, no "Generated with").

## Dev message format

Exact format: `[ouro-ui] <Component>: <what's wrong>. Fix: <exact code>.`

- Emit each message once per component instance.
- Strip messages in production with the bare `process.env.NODE_ENV !== "production"` form, with no `typeof process` guard, so bundlers replace it statically and drop the dead branch. Put the check at each warn call site (`if (process.env.NODE_ENV !== "production") devWarn(...)`), and build `devThrow`'s fix argument only inside a development branch. `scripts/dev-strip.test.mjs` bundles a probe with Vite in production mode and asserts the message strings are gone.
- Consumers need a bundler that defines `process.env.NODE_ENV` (Vite, Next.js, webpack and React Router all do). Without one, dev messages are not stripped and the bare reference throws in a browser.

## Appearance classes warn

A `className` token warns when, after removing variants (split on `:` outside `[...]`) and a leading or trailing `!`, its base matches `/^(bg|text|border|rounded|shadow|font|ring|from|via|to|fill|stroke)-/` or is exactly `border`, `rounded`, `shadow` or `ring`, or when `dark` appears at any variant position. Ordinary layout classes (`mt-4`, `w-full`, `grid-cols-2`, `size-4`) never warn, and neither do text wrapping, text overflow and table layout classes that share a prefix (`text-wrap`, `text-nowrap`, `text-balance`, `text-pretty`, `text-ellipsis`, `text-clip`, `border-collapse`, `border-separate`, `border-spacing-*`). Alignment classes (`text-left|center|right|justify|start|end`) also warn, and the message points to the component's `align` prop where one exists (the `alignHint` argument), or else shows the class on a parent element. Hints are exact code, such as `tone="destructive"`. A component may pass a hint function that picks the fix from the offending token (`registry/ouro/lib/ouro/appearance-hints.ts` maps `bg-red-500` to `tone="destructive"` and `text-lg` to `size="lg"`); pass hints only in development (`process.env.NODE_ENV !== "production" ? hint : ""`) so their text is stripped.

## Rules for writing components (spec section 4)

1. Props-first: the default export takes props that describe the whole thing; building-block parts live in the component's `-parts` file and their JSDoc says when to use them. Exception: `ResizablePanelGroup`, `ResizablePanel` and `ResizableHandle` are exports of `resizable.tsx`, because they are shadcn's public names (an agent porting shadcn's import gets hint types that name the fix, not "no exported member") and do not fit the parts page's `<Family>Root` naming.
2. Anything that "always" applies is a required prop (`title` with `hideTitle`, `label` with `hideLabel`, `legend`, `name`); leaving it out is a type error.
3. One state, one prop: `error`, `loading`, `disabled`, `required` each handle all of their ARIA, messaging and animation.
4. Appearance comes from named options (`tone`, `variant`, `size`) that map to theme tokens, never color names or classes.
5. `className` is for layout only; warn in development about appearance classes and give common layout needs a prop (for example `fullWidth`).
6. The prop agents guess is the prop that exists: use the common name, or declare it as a hint type that nothing is assignable to, with JSDoc pointing to the real prop (`isLoading?: { 'Use <Button loading>': never }`), so the type error names the fix. Every enum prop also takes one `string & { '<the fixes>': never }` member (`tone`'s `'danger is "destructive"; …'`, shadcn's Button variants and sizes, and the value list where the type is an alias such as `SheetSide`; parts' enum props and numeric ones such as Heading's `level` too), kept short and ASCII so `tsc` prints the whole union, and an unknown value renders the default and warns in development. Why not plain `never` or a plain literal union: an attribute whose expected type is a literal (`never` reads as `undefined`) and whose value doesn't match rules out every branch of a union-typed props object, and TypeScript then drops the hover JSDoc of every prop on the element. Keep the HTML attributes outside a props union (`Text`), or hover is lost even in valid code. The mode-exclusion props (`trigger?: never` with `open`) stay `never`: as hint types they lose hover on `trigger`, `open` and `onOpenChange` in valid code, so an element that passes both modes shows no hover and relies on the development error, which names the fix. `scripts/fixtures/agent-types/` holds the agent snippets, one pair of files per component: `<item>.snippets.tsx` and `<item>.cases.ts`, which says which channel (type error, hover, development message) names each fix (types and shared helpers in `shared.ts` and `helpers.ts`); `scripts/agent-types.test.mjs` and `test/agent-types.test.tsx` find the files by name and check them. Snippet ids are unique across the files, so a new component names its snippets after itself (`numberField01`).
7. Mode-dependent types follow the mode with discriminated unions (`multiple` makes `Select` use `string[]`; `href` makes `Button` a link).
8. Parts check where they are: outside their parent they throw in development with the correct JSX shape; where it is safe, the parent wraps loose children instead.
9. Docs live in the types: every export has JSDoc with a one-line purpose, a minimal example and "use X instead when" guidance; `README.md` holds the catalog and `docs/<component>.md` a page per component.
10. Behavior and motion are the component's job (dialog-to-sheet on phones, focus, touch targets, durations, springs, reduced motion); no component takes a duration or easing prop, motion comes from theme tokens. State changes are CSS transitions (Base UI's `data-starting-style`/`data-ending-style`) on the three easing tokens `--ouro-ease-out`, `--ouro-ease-in-out` and `--ouro-ease-drawer`, with the `--ouro-duration-*` tokens; hover and color changes use `ease`, and `ease-in` is never used. Gesture settles (a released drag) will live in `lib/ouro/spring.ts` and `lib/ouro/use-drag.ts`, added with their first users (SwipeActions and Reorderable); until they exist nothing settles in JavaScript. They will run on `requestAnimationFrame` with no dependency. The old `--ouro-ease-spring` and `--ouro-spring-duration` stay defined until their last reader is gone. Components honor reduced motion with `motion-reduce:`/`motion-safe:` variants and `prefers-reduced-motion` queries. No registry item depends on the `motion` package; it is a dev dependency here only for the RedwoodUI reference story and the theme test's spring check, which goes when the spring tokens do. A component that ever needs Motion must wrap its own usage in `MotionConfig reducedMotion="user"` (or use `useReducedMotion`) and must not rely on `OuroProvider`, which is optional.
11. Errors teach: every dev message uses the format above.
12. Higher-level patterns capture whole interactions agents assemble badly (`ConfirmDialog`, later `EditSheet`).

## Layout

The layout mirrors where shadcn installs files, so the CLI's import rewrite lands them in `components/ouro/` and `lib/ouro/` (spec §3).

- `registry/ouro/components/ouro/<component>/`: components, their parts, tests and stories.
- `registry/ouro/lib/ouro/`: shared helpers and hooks (`cn`, dev messages, the className check, `OuroProvider`, tone names, `useMediaQuery`, `useKeyboardScrollable`, the backdrop anchor, `TouchTarget`, and `env.d.ts`, which declares `process.env.NODE_ENV` so apps without `@types/node` typecheck; `pnpm typecheck` also checks the registry source without Node types).
- `registry/ouro/lib/ouro/testing/`: the test kit the `ouro-testing` item ships: the `act` helper, the custom browser commands, `pageCss()`, `axeExclude` (`axe.ts`, the Base UI focus guards to leave out of an axe scan), the act-warning setup and `ouroTestProjects` (`vitest.ts`), the Vitest browser projects apps add to their config. This repository's `vitest.config.ts` uses the same projects.
- `registry/ouro/e2e/ouro/`: one Playwright spec per component, installed to an app's `e2e/ouro/`, and `story.ts`, which opens a story by id in the Storybook at `OURO_E2E_URL` (default `http://localhost:6006`). Specs ship as `registry:file`, which the CLI does not rewrite, so they import only `@playwright/test` and `./story`.
- `registry/ouro/theme/ouro-base.css`: required in every app. The success and warning pairs and `--destructive-foreground` (which shadcn's themes lack), the `--ouro-*` motion tokens, `--ouro-layer` (the z-index of the Dialog and Sheet portals, 50 as in shadcn's overlays), the `press` utility and the keyframes.
- `registry/ouro/theme/ouro-theme.css`: optional. The Ouro color look as a shadcn theme (`:root` and `.dark` values only).
- `app.css`: the repository as its own app. It imports Tailwind, `ouro-base.css` and `ouro-theme.css`, adds the `@custom-variant dark` and `@theme inline` mapping `shadcn init` writes, and scans `registry/`; Storybook and the Vitest projects compile it with `@tailwindcss/vite`.
- `stories/reference/`: repository-only stories, such as the Sheet feel comparison with RedwoodUI's ActionSheet; they ship in no item.
- `registry.json`: the shadcn registry, generated by `pnpm registry` (`scripts/registry.mts`) and committed; see Registry below.
- `test/install-fixture/`: the bare Vite app the install test (`scripts/install-test.sh`) copies, runs `shadcn init` in and installs every component into, with no test config. `test/install-fixture-tests/`: the files the `ouro-testing` docs message tells an app to add (`vitest.config.ts`, `.storybook/`, `playwright.config.ts`), which the install test copies in before it adds `ouro-tests`. `test/install-fixture-upgrade/`: what the `upgrade` variant adds on top of those: a Vitest config with a project for the app's own test beside `ouroTestProjects`, and that test.
- `changes/`: the behaviour changes since the last release, one fragment file per change (`changes/<any-name>.md` holding `- ` lines), so parallel pull requests never edit the same file. Each non-blank line is one change, a top-level `- ` line (no wrapped lines or sub-items); `check` fails on anything else. release.yml assembles them, by file name, into `CHANGES.md` on the release commit only, so the tag holds the "Changes in this release" section and the release notes print it at the top (`node scripts/changes.mjs assemble changes` prints it); main keeps the fragments only. Add a fragment when a change alters what an app sees (a stacking level, a focus target, a dependency range). Release refuses to start while the fragments list no change, or while one still lists a change from the last release's notes (`scripts/changes.mjs check`). After a release, release.yml opens "Prepare main for the next release", which deletes the fragments that release used (`git rm -- 'changes/*.md'`, on a branch off the released commit, so a fragment added during the release stays; `scripts/changes.test.mjs` runs that race) and makes the new tag the newest release (see Pages and releases); merge it before the next release. That PR is opened with GITHUB_TOKEN, so GitHub records its `pull_request` CI run but holds it (`action_required`, no jobs), and main's ruleset counts only `pull_request`-event checks, not a dispatched run. release.yml therefore finds the held run on the PR's head and approves it (`gh api -X POST repos/ourostack/ouro-ui/actions/runs/<run id>/approve`, with `actions: write`). GitHub documents that endpoint for fork PRs and names only OAuth and classic personal access tokens ([docs](https://docs.github.com/en/rest/actions/workflow-runs#approve-a-workflow-run-for-a-fork-pull-request)), so if GITHUB_TOKEN is refused, the workflow warns, dispatches CI on the branch (a signal only, not what the ruleset counts) and writes the exact approve command to the job summary and the PR body: run it as a maintainer, then wait for the checks. Never add a ruleset bypass for the bot.
- `UPGRADING.md`: "Upgrading from v0.1.0", the one copy of the note, with a short "What changed, by version" list of the changes an app must act on (keep it in step with `changes/` when a release adds one). Its addresses end in `#{{latestRelease}}`, a placeholder each copy fills, and a line under its title tells readers of the raw file what it stands for; every copy drops that line (`rawHint`): `pnpm run docs` copies its body into README.md with the newest release, the site's Updating page renders it the same way, release.yml prints it into the release notes with the release tag, and the `upgrade` install test runs its commands (`scripts/upgrade-note.mjs`). Edit only this file; `scripts/upgrade-note.test.mjs` fails if a copy of a command appears anywhere else.
- `test/`: the story-wide accessibility test, the screenshot test and their baselines, and `stock-theme.test.tsx`, which checks every tone and variant at 4.5:1 under stock shadcn variables (`test/shadcn-stock.css`, copied from `shadcn init`) plus `ouro-base.css`, and under the Ouro theme.
- `scripts/agent-usability/`: the agent-usability test (spec §8), which measures success criterion 1. Fresh agents build five screens (`screens/<screen>/task.md`, with the `src/api/` stand-in for the backend in `files/`) three ways, three times each: shadcn/ui, shadcn/ui with its official skill, and Ouro HX (`arms/create.sh`, which also records each arm's baseline: what `tsc -b` and oxlint find before any agent runs). `score.mts <arm> <screen> <app-dir> --arm-record <arm.json>` judges a result with no model calls: `tsc -b` and oxlint errors that are not in the baseline, axe-core's WCAG A and AA rules at 390px and 1280px in light and dark, and the screen's behavior checks (`checks/<screen>.mts`). `formula.mts` defines the score and is the only place that documents it. The scores are published beside shadcn/ui's, so no arm may gain or lose a point for anything but what its agent did: every check must be stated in the prompt (`prompt.mts`) or the task, in behavior or accessibility terms, and when a task changes, its checks and its known-good screen (`test/screens/`) change with it. `preflight.mts` proves the scorer in a real arm app, `table.mts` writes the results table with the pinned versions, and `page.mts` is the hook for the docs page that will show it. Agent output is committed under `runs/<date>/<arm>/<screen>/<run>/` with each arm's record in `runs/<date>/arms/` (ESLint ignores it), and `agent-usability.yml` scores the newest run weekly and on demand into its job summary; it is not a required check. `README.md` there is the runbook, with the exact prompt and the exact command that starts a fresh agent. `score.test.mjs` (in `pnpm test:scripts`) proves the scorer on a known-good plain-React version of every screen and on broken copies.
- `site/`: the landing page and docs site (https://ourostack.github.io/ouro-ui/), built with Vite from the root dependencies, not a workspace package. Docs pages render the generated `docs/*.md`; each registry item's page is `docs/<item name>/`, listed from `site/src/docs/catalog.json` (written by `pnpm run docs`), with the live demo from `site/src/docs/demos/<item name>.demo.tsx` (its default export; `site/src/docs/demos.tsx` finds them by glob). Demos are site code and ship in no item. `pnpm site:build` writes `site/dist` (prerendered HTML per route, with Open Graph and Twitter tags from `site/src/head.ts`), `pnpm site:dev` serves it. `site/public/og.png`, the 1200x630 link-preview image, is a screenshot of the landing page with its sheet open; regenerate it with `node site/scripts/og-image.mts` after the landing page changes, review it and commit it. The "Agents read the types" examples live in `site/src/agents/examples.ts`; `pnpm site:messages` regenerates their compiler output (`site:build` and `pnpm test:scripts` fail when it is stale), and the `site` Vitest project checks each quoted dev message against the real component.
- Imports between registry files use `@/registry/ouro/...`, which the shadcn CLI rewrites to an app's aliases on install. `@/` resolves to the repository root (tsconfig `paths` and the Vite alias).

## Component conventions

- Every component root carries `data-ouro="<component>"`, so apps can exclude Ouro UI subtrees from global rules.
- Style with plain Tailwind utilities on shadcn's token names (`bg-primary`, `text-muted-foreground`, `border-border`, `rounded-lg`), merged with `cn(...)` with the app's `className` last, so the app's layout classes win. There is no prefix and no stylesheet per component.
- A layout property the app may override (`h-*`, `px-*`) is one unprefixed class at every width. When it changes at a breakpoint, the class reads a variable and the breakpoint sets the variable (`h-(--ouro-button-h) [--ouro-button-h:…] sm:[--ouro-button-h:…]`), so tailwind-merge replaces it with the app's class.
- `tone` values are the theme token names: `primary`, `secondary`, `destructive`, `success`, `warning`. `secondary` has shadcn's meaning: a quiet surface (`bg-secondary text-secondary-foreground`), never a text color, so Text's `secondary` is the muted foreground. `variant="soft"` is the tone at 10% behind text in the tone mixed 20% toward the foreground (shadcn's stock destructive fails 4.5:1 on its own tint otherwise). Focus outlines use `outline-ring` for every tone. A tone, variant or size that is not one of ours (`tone="danger"`, shadcn's `variant="destructive"` or `size="icon"`) renders the default and warns with the fix.
- There is no reset, so reset what the browser sets (button borders, backgrounds, margins on `<p>` and headings inside a component, `box-sizing`) in the component's own classes.
- A component root sets no margin class, not even `m-0`. The margin between components is the app's layout, and a parent's `space-y-4` puts it on its children with a zero-specificity rule (`:where(.space-y-4 > :not(:last-child))`), which any margin class on the child beats, so a root with `m-0` loses its gap. A root whose element has a margin in the browser's stylesheet (`<p>`, headings, `<fieldset>`, `<figure>`, `<dl>`, lists) clears it with `[@layer_ouro-reset]:m-0`, which puts the rule in a sublayer of Tailwind's utilities: every plain utility beats it whatever its specificity, so `space-y-4` and the app's own margin class still apply (`test/root-margins.test.tsx`). Elements inside a component reset theirs with plain `m-0`. `test/stories.test.tsx` fails on a plain margin reset on any `[data-ouro]` element in any story.
- A required field's marker is CSS (`::after`) on the element around the label (`[data-ouro-label]`, or a group's `[data-ouro-legend]`), never an element or text inside the label and never `::after` on the label itself: a label's text is what Testing Library's `getByLabelText` and Playwright's `getByLabel` compare, and generated content on the labelling element counts toward the control's accessible name.
- A button inside a field (clear, show password, choose date) is named by visually hidden text, not `aria-label`: an `aria-label` is label text, so Playwright's `getByLabel("Password")` would also match a button labelled "Show password".
- Overlay portals are `relative isolate z-(--ouro-layer)`: their own stacking context, at a level apps raise with the token rather than a class edit. Apps raise it in their own unlayered `:root` rule after the Ouro tokens, because `shadcn add` resets the line it wrote; the install test checks that such an override survives a re-add.
- Class strings are literals so Tailwind finds them; `app.css` scans `registry/`. Stories lay out with inline styles and the theme variables (`var(--muted-foreground)`).
- Write hover styles as `pointer-fine:hover:…`, never bare `hover:`: Tailwind's `hover:` checks only `(hover: hover)`, and the rule is `(hover: hover) and (pointer: fine)`, so a tap on a phone leaves no hover state behind.
- Interactive controls use the `press` utility (the scale arrives and releases in 160ms on `--ouro-ease-out`, colors ease in 150ms), a `motion-safe:` press scale of `--ouro-press-scale`, and `<TouchTarget />` (`registry/ouro/lib/ouro/touch-target.tsx`) as the first child of a `relative` root for the 44px coarse-pointer hit area. A linked list row (`Item` with `href`) highlights while pressed instead of scaling, because a full-width row that shrinks reads as a jump; it is at least 44px tall on a coarse pointer instead of using `<TouchTarget />`. A `ResizableHandle` changes color on hover, focus and press instead of scaling, because a 1px splitter line that shrinks looks broken; it still uses `<TouchTarget />`.
- Dark mode is the `.dark` class on an ancestor, as in shadcn. The OS setting alone does not switch it.
- Keyframes are namespaced (`ouro-spin`), never Tailwind's global `spin` or `pulse`.
- Every variable Ouro UI adds that is not a shadcn color uses the `--ouro-` prefix (`--ouro-ease-out`, `--ouro-sheet-gap`); the prefix on the easing tokens is required, because Tailwind defines its own `--ease-out` and `--ease-in-out`, and an unprefixed token would change the `ease-out` class across the app that installs the library; `registry/ouro/theme/theme.test.tsx` checks the easing and duration tokens, the `press` timing and (until it is retired) the spring against Motion's `spring(0.4, 0.15)`, and checks the Ouro theme's text pairs at 4.5:1 in light and dark.

## Workflow

- Use pnpm 10. Run `pnpm run docs --check`, `pnpm registry --check`, `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm test:scripts`, `pnpm test:e2e` and `pnpm build-storybook` before opening a pull request.
- `docs/<Export>.md`, `docs/parts.md` and the catalog in `README.md` (between the `catalog` markers) are generated from the JSDoc and prop types in `registry/` by `pnpm run docs` (always with `run`: bare `pnpm docs` is pnpm's `npm docs`, which opens a browser) (`scripts/gen-docs.mts`, TypeScript compiler API) and committed; CI runs `pnpm run docs --check`. Edit the JSDoc, never the output. Generation fails when an export lacks a purpose or an `@example`, when a component lacks a "use X instead when" sentence, or when an export has no catalog group: each export names its group in its JSDoc (`@group Forms`), one of `groupOrder` in `scripts/catalog-groups.mts` (Actions, Text, Forms, Overlays, Menus, Feedback, Display, Lists, Layout, Navigation, Data, Chat) or `App setup` for `OuroProvider`; the catalog, the README and the site list each group that has exports, in that order, and each group's exports by name. The site's `DocsItem.group` type and tests read the same constant. The documented files and part files (`<folder>/<stem>-parts.tsx`) come from the components' `component.json`. Tag an export that is shared between registry files but not for apps with `@internal`.
- `test/stories.test.tsx` renders every story through `composeStories` and runs axe (zero violations) closed and with each overlay open, light and dark, at 390px and 1280px, in Chromium and WebKit. `test/stories.tsx` finds every `*.stories.tsx` by glob and keys it by its file name in PascalCase, so two story files may not share a name (it throws). A controlled story that opens its overlay from a plain button names it in the story's parameters (`parameters: { plainOpeners: ["Open"] }`), and a story that is a screenshot subject names its baseline there (`parameters: { screenshot: { name: "dialog-open", open: true } }`); the visual test fails when a committed baseline has no such story.
- Screenshot baselines (`test/__screenshots__/**/*-linux.png`, light, dark and reduced motion at 390px and 1280px) come from Linux CI only. To refresh them, run the `visual-baselines.yml` workflow on your branch, download its `visual-baselines` artifact into `test/__screenshots__`, review and commit. CI compares with `pnpm test:visual` in its `visual` job. Both workflows pin `ubuntu-24.04`, the image that rendered the baselines; moving to a new image means regenerating them. Local runs on macOS write `*-darwin.png` files, which git ignores.
- Source rules (`scripts/source-rules.test.mjs`): no registry file has a comment before its first statement, because the shadcn CLI drops it on install; start with the imports, or with an export list (`export { a, b };`) in a file without imports, and put the guidance in JSDoc after it. The install job checks that every installed file kept its source's comments. Write coverage hints as `/* istanbul ignore <next|if|else> @preserve -- reason */`; esbuild strips them without `@preserve`. Every test's full name (describe titles and title) is unique across the suite, so a name filter runs exactly one. Every runtime file under `components/ouro/` and every `lib/ouro/*.tsx` starts with `"use client";` (before the imports) unless it is pure: a component's `<stem>-styles.ts` (by its name) or a file on the pure list (`pureFiles` in `scripts/source-rules.mjs`: `touch-target.tsx`), and so does any other module that calls a hook (including React 19's `use()` and a hook imported from react under another name), calls `createContext` or defines a class component; no other file does, so a Next.js Server Component can render the components and still import plain values; the shadcn CLI keeps the directive in apps with `"rsc": true`, and its removal regex never matches the form with a semicolon, so Vite apps keep it too (the install check fails if an installed file loses it).
- Tests wait on conditions, never on fixed timers: `expect.poll` until a value is reached or a transition has finished (`getAnimations()` empty and two reads agree), `act` to flush React before asserting that something did not happen, and a frame for media query changes. A settle that runs in JavaScript (a spring) is invisible to `getAnimations()`, so it sets `data-ouro-settling` on the element while it runs, and tests wait for the attribute to clear. The projects give every poll 10s, so a loaded runner waits longer instead of failing; don't pass a shorter `timeout`.
- Test with Vitest browser mode. Projects: `ouro-chromium`, `ouro-webkit`, `ouro-touch` (files named `*.touch.test.ts(x)`, Chromium as a 390x844 touch phone), from `ouroTestProjects`, and `visual` (files named `*.visual.test.ts(x)`, only when `CI_VISUAL=1`).
- Tests ship to apps, so they hold under any shadcn theme: compare with the theme's computed variables, never with Ouro's hex values (`themeColor` in `button.test.tsx`), and read compiled CSS with `pageCss()`, never by importing `app.css`. A component's tests, stories and spec import only items their `-tests` item depends on; a `-tests` item may depend on any runtime item.
- End-to-end specs: `pnpm test:e2e` starts Storybook and runs `registry/ouro/e2e/` in Chromium and WebKit.
- Custom browser commands live in `registry/ouro/lib/ouro/testing/commands.ts`: `commands.emulateMedia({ reducedMotion, colorScheme })`, `commands.drag({ from, to, steps, durationMs, hold })` (`hold` keeps the button down so a test can inspect the mid-drag state; release with `pointerPress({ action: "up" })`), `commands.flick`, `commands.tap`, `commands.touchDrag({ from, to, steps, durationMs })` (a one-finger drag with real touch input through CDP, for swipe gestures; Chromium only; pass `durationMs` whenever the result depends on the swipe's speed, as over scroll snap points, because without it the speed is whatever the machine manages), `commands.touchStep({ type, x, y })` (one step of such a gesture, for a finger held still mid-swipe; lift the finger with `touchEnd` in a `finally`, and a finger left down is lifted before the next gesture) `commands.pointerPress({ selector, action })` (holds the real mouse down so `:active` applies) and `commands.restoreTouch()` (turns Chromium's touch emulation back on; the `ouro-touch` setup calls it before every test, because a screenshot taller than the viewport, such as a failure screenshot of a tall page, drops it for the rest of the page's life, so read a burst of coarse-pointer failures in one touch worker on an older kit as one real failure plus fallout). Drag tests run in Chromium only.
- Contributors need Node 22.18 or later (`devEngines`; `.node-version` pins 24) because the scripts run through Node's type stripping.

## Registry

- `registry.json` is generated; never edit it. Run `pnpm registry` after adding, renaming or moving a registry file, changing an import, a theme CSS file, a dependency version or a component's JSDoc purpose, and commit the result. CI fails on a stale file.
- `scripts/registry.mts` derives everything from the layout. Each component is two items. `<name>` ships the runtime source only: `<stem>.tsx`, `<stem>-parts.tsx` and `<stem>-styles.ts` (`registry:ui`), targeted at `@components/ouro/<folder>/`. The opt-in `<name>-tests` ships its tests and type tests (`registry:component`), stories and `e2e/ouro/<stem>.spec.ts` (`registry:file`, to `~/e2e/ouro/`), depends on `<name>` and `ouro-testing`, and carries the Storybook, Vitest and Playwright devDependencies. `ouro-lib-tests` holds `lib/ouro`'s tests, and `ouro-tests` depends on every `-tests` item. A runtime item that needs a devDependency fails the generator. `registryDependencies` come from the `@/registry/...` imports, as full unpinned addresses (`ourostack/ouro-ui/<item>`; release tags pin them, see Pages and releases); npm `dependencies` and `devDependencies` come from the imports, at the range in this repository's `package.json`. The theme items' `cssVars` and `css` come from `registry/ouro/theme/*.css`; a theme file may hold only `:root`, `.dark`, `@theme inline`, `@utility` and `@keyframes`. Descriptions and docs messages come from `docs/<Component>.md`.
- A runtime item's `registryDependencies` are its runtime imports only. Stories and tests count as imports of the `-tests` item (`heading-tests` depends on `button` through its stories), never of the component.
- A component file exports only components and types, so an app's React Fast Refresh lint passes: shared class strings, value lists and dev-message helpers go in `<stem>-styles.ts` (`sheet-styles.ts`, `dialog-styles.ts`, `text-styles.ts`), and hooks in their own module (`use-ouro.ts`).
- A component's docs message gives its import line and every Ouro item installed with it. `ouro-base`, `ouro-lib` and `ouro-testing` start their descriptions with "Installed with every …; you don't need to add it." Theme tokens named `--ouro-*` go to the item's `css` under `:root` and `.dark`, not `cssVars`, so the CLI writes no self-referential `@theme inline` mapping for them; `scripts/install-check.mjs` fails on any `--x: var(--x)`.
- `ouro-theme` is a `registry:theme` (it replaces the app's colors, and the CLI warns before that); `ouro-base` is a `registry:item`, because it only adds variables.
- The `ouro-testing` docs message prints the files an app adds to run the shipped tests and specs (`testingSetup` in the script). `test/install-fixture-tests` holds those files verbatim, and the registry test fails if they drift or if the bare `test/install-fixture` has them.
- The components come from each folder's `component.json` (`scripts/components.mts`): `{ "order": 70, "components": ["text-field", "text-area"] }` lists the folder's component file stems (item name `<stem>`, export name the stem in PascalCase), and `order` places the folder in `registry.json` (equal orders sort by folder name). The manifest ships in no item. A registry file no item ships fails the generator unless it is in `repoOnly`. `pnpm registry` also writes the item list in `site/public/llms.txt` (`## Items`), and `--check` fails when it is stale.
- The shadcn CLI is pinned to `shadcn@4.21.1` in `.github/workflows/ci.yml`, `pages.yml` and `scripts/install-test.sh`.
- The install test (`scripts/install-test.sh <shadcn|ouro|namespace|next|upgrade> <dir>`) runs locally too. It installs the runtime items into the bare fixture first and checks that they added no test, story, spec, test kit or test tooling, and that `npx vitest run` finds no tests; then it copies in `test/install-fixture-tests/`, adds `ouro-tests` and runs the shipped tests and specs. The `ouro` variant fetches `ouro-theme` from GitHub, so push first. Refs are not inherited by `registryDependencies`, so the script installs from a locally built copy of the registry whose dependencies point at the built item files (`--deps <dir>/{name}.json`). The `namespace` variant builds the namespace as Pages does, from the newest release tag (`scripts/namespace.sh`), serves it on localhost, registers `@ouro` in the app's `components.json` and installs `@ouro/dialog`, checking that every dependency came through the namespace, that no test item came with it, that each served item names that release and that every installed file equals the tag's source. The `next` variant creates a Next.js App Router app with `create-next-app` (TypeScript, Tailwind CSS v4, `src/`), runs `shadcn init` (which writes `"rsc": true`), adds every runtime item (the `registry:ui` items in `registry.json`, as every variant installs), renders each component from a Server Component page (ConfirmDialog's `onConfirm` is a server action) and runs `next build`. Each component has its own section, `test/install-fixture-next/src/app/sections/<item>.tsx`, whose `// expect: <pattern>` lines say what the prerendered page must hold; the script writes `sections/index.ts` from the files, and fails when a component has no section. The `upgrade` variant installs `dialog` at `#v0.1.0` from GitHub (which brings `button` and `sheet`) into an app with the v0.1.0 test setup and a test of its own (`test/install-fixture-upgrade/`), then runs the commands in `UPGRADING.md` against this commit's registry, in two layouts. In an `app/` layout with `~/*` aliases on `./app/*`, step 1 on an app with no Ouro component must stop without adding anything, then steps 1 to 3 run. In the `src/` layout, steps 1 and 2 run, and separately steps 1 to 3. Each app must type check, build, run its own test with its own config, keep the same components and have no self-referential token. The note's commands find the app's folders with `npx shadcn info --json` (`resolvedPaths`), never a hard-coded `src/`; `scripts/upgrade-note.test.mjs` also runs them with a stand-in `npx` in bash and zsh. The `github` variant is the ref-less install from `main`; CI runs it (job `install-github`) after each push to main.

## Adding a component

A component touches only its own files, so parallel pull requests do not conflict. Create:

1. `registry/ouro/components/ouro/<folder>/component.json`: `{ "order": <number after the last folder's>, "components": ["<stem>"] }`.
2. `registry/ouro/components/ouro/<folder>/<stem>.tsx` (and `<stem>-parts.tsx`, `<stem>-styles.ts` as needed), with JSDoc on each export including `@example` and `@group <group>`, one of Actions, Text, Forms, Overlays, Menus, Feedback, Display, Lists, Layout, Navigation, Data or Chat (`scripts/catalog-groups.mts`).
3. In the same folder: `<stem>.test.tsx`, `<stem>.test-d.ts` and `<stem>.stories.tsx` (story `parameters` for `plainOpeners` and `screenshot` where they apply), plus `registry/ouro/e2e/ouro/<stem>.spec.ts`.
4. `site/src/docs/demos/<stem>.demo.tsx`: the docs page's live demo, as its default export.
5. `test/install-fixture-next/src/app/sections/<stem>.tsx`: a Server Component section with `// expect: <text>` lines.
6. `scripts/fixtures/agent-types/<stem>.snippets.tsx` and `<stem>.cases.ts`, with snippet ids named after the component.
7. `changes/<stem>.md`: a `- New: ...` line. One top-level `- ` line per change, with no wrapped lines or sub-items: `scripts/changes.mjs check` fails on any other non-blank line, because only those lines reach the release notes.

Then regenerate, never hand-merge: `pnpm run docs` (`docs/`, `README.md`, `site/src/docs/catalog.json`) and `pnpm registry` (`registry.json`, `site/public/llms.txt`), and commit the result. After a rebase, run both again instead of resolving conflicts in those files. Screenshot baselines come from the `visual-baselines.yml` workflow.

## Pages and releases

- `pages.yml` publishes https://ourostack.github.io/ouro-ui/ after CI passes on a push to main (`workflow_run`; also runnable by hand): the site at `/`, Storybook at `/storybook/`, and the `@ouro` namespace registry at `/r/<item>.json` and `/r/registry.json`. The site and Storybook build from main. The namespace builds from the newest release tag, `ouro.latestRelease` in main's package.json (`scripts/namespace.sh`: the tag's own `registry.json`, rewritten by `scripts/registry.mts --from <file> --deps "@ouro/{name}"`, then `shadcn build` over the tag's files), so each item's same-repo dependencies resolve through the namespace and `@ouro` serves released code only. The unpinned GitHub path (`ourostack/ouro-ui/<item>`) still serves main, by nature; public docs use a tag or `@ouro` and call the unpinned path main, for contributors. Pages deploys only when the CI run it follows is for main's current tip, so an older run that finishes late never deploys over a newer one.
- Release by running the Release workflow (`release.yml`) with a `version` such as `0.1.0` (Actions, or `gh workflow run release.yml -f version=0.1.0`). It checks that CI passed on main's head, force-pushes `release/v<version>` from main with every same-repo `registryDependency` in `registry.json` pinned to `#v<version>`, a `version` field, and "Ouro UI v<version>." at the end of each item's `docs` message, so every `add` prints the version it installed (`pnpm registry --release <version>`), and runs CI on that commit (dispatched, because pushes made with `GITHUB_TOKEN` trigger no workflows; it waits on the run for that exact commit). When CI passes, it tags the commit, creates the GitHub release with the items and both install commands, and deletes the branch. There is no pull request.
- Main is never pinned: only the tag points at the release commit. `pnpm registry --check` reads the `version` field, so CI on the release branch checks the pinned file; on main and on pull requests into main it fails on a `version` field or a `#v` dependency.
- Rerunning is safe. If the tag exists and has a release, the workflow exits with a notice. A failed run deletes its branch, so rerun after fixing the cause. Recovery:
  - CI failed on the release branch: fix main, then run Release again.
  - The tag exists without a GitHub release (the run fails and says so): delete the tag with `git push origin :refs/tags/v<version>`, then run Release again.
  - A wrong release was published: delete it with `gh release delete v<version> --cleanup-tag`, then release a new version (prefer a new version over reusing a published tag).
- `ourostack/ouro-ui/<item>#v<version>` installs the item and all its Ouro dependencies at that tag, because the tagged `registry.json` names them with the same tag.
- Install commands in the docs (`README.md`, `site/`, `site/public/llms.txt`, the release notes) use `npx shadcn@latest`, start with the `init` step (`init --base base --preset nova --yes --no-monorepo`) and pin the newest release tag. That tag has one source, `ouro.latestRelease` in `package.json` (`scripts/latest-release.mjs`): `pnpm run docs` writes it into README.md, llms.txt and package.json's description, the site imports it (`site/src/release.ts`), and Pages builds the namespace from it. Never edit a tag by hand: `scripts/latest-release.test.mjs` fails when a `#vX.Y.Z` or `@vX.Y.Z` literal in the docs names another tag. The same test and `site/src/site.test.tsx` fail on an install address with no ref or any ref but a release tag (`#main`, a branch, a commit; `scripts/addresses.mjs`), outside a sentence that says it is for contributors. release.yml sets the new tag on the release branch before it tags (`node scripts/latest-release.mjs set v<x.y.z>`, then `pnpm run docs`), so the tagged commit's README, llms.txt and site name that tag itself (UPGRADING.md keeps its placeholder) (`scripts/latest-release.test.mjs` runs those commands on a copy); its "Prepare main for the next release" PR does the same on main, and when it merges, the docs, the site and `@ouro` move to the release. On the release branch, before the tag exists, `scripts/namespace.sh` builds the namespace from the checkout, whose `registry.json` already is that release. Release advises deleting a tag only when GitHub answers "release not found"; any other error fails with the raw message. `pnpm registry --check` reads only `registry.json`, so a tag in the docs never fails it; `registry.json` on main stays unpinned. The install test and CI keep the exact `shadcn@4.21.1` they verify.
