# The screen-reader lane

Ouro UI's components are read by real screen readers on every commit of main that is released, right after its tag: VoiceOver on macOS and NVDA on Windows, driven through [Guidepup](https://www.guidepup.dev/) in this repository's CI.[^sr-release][^sr-runners] This page lists what the lane checks, how a failure is classified, how to run it, and why it may change a runner's settings.

## What it checks

Each spec opens one story from a static build of this repository's Storybook, waits for the component to render, starts the screen reader, moves it into the page and asserts what it says: the control's name, its role and its state, then the change after a key press.[^sr-stories]

| Spec | Story | What the screen reader must say |
| --- | --- | --- |
| Button | `actions-button--loading` | "Save to cookbook", button; "Loading" from the live region after Enter, while the button keeps focus |
| Checkbox | `forms-checkbox--playground` | "Email me new recipes", checkbox, unchecked; then checked after Space |
| Checklist | `lists-checklist--in-context` | the first item's name, checkbox and its state; then the other state after Space |
| Dialog | `overlays-dialog--playground` | "Edit", button; "Edit recipe", dialog, as it opens; the "Edit" button again after Escape |
| Menu | `menus-menu--playground` | "Actions", button; the menu as it opens on "Edit"; "Duplicate" after ArrowDown; the "Actions" button again after Escape. The Share submenu: "Share" as focus reaches it, "Copy link" as ArrowRight opens it, "Share" again after ArrowLeft |
| MenuBar | `menus-menu--bar` | "File"; "New recipe" as Enter opens it; "Save" after ArrowDown; "File" again after Escape |
| Select | `forms-select--playground` | "Course", combo box, collapsed; the list as it opens; "Main", then "Side"; "Course" with "Side" once chosen, read from the focused control |
| Switch | `forms-switch--playground` | "Cooking timers", switch, off; then on after Space |
| TextField | `forms-textfield--states`, `forms-form--server-errors` | "Email" with its description, and edit text, required, as focus arrives; after a submit, the error "You already have a recipe called Pasta." as focus moves to "Name", which is invalid |
| Toast | `feedback-toast--playground` | "Save recipe", button; "Recipe saved" from the live region after Enter |

The Checklist spec skips, with that reason, until `registry/ouro/components/ouro/checklist/` exists; once it does, a missing story fails the lane. Before either screen reader starts, the `stories` project checks every story id against the built Storybook's `index.json`.[^sr-stories]

VoiceOver reads WebKit on `macos-26`, what current users run, and NVDA reads Chromium on `windows-2025`; those two decide the run.[^sr-runners] VoiceOver on `macos-15` runs beside them nightly, advisory: its failures do not fail the run, but the nightly run opens or comments on one issue for them, so the lane still says what older macOS's users hear.[^sr-runners] It no longer runs on each push to main, where it doubled the lane's macOS demand on a runner pool shared with other repositories and queued releases behind it.[^sr-runners] Each matcher accepts both readers' words (VoiceOver says "unchecked" where NVDA says "not checked", and "checkbox" where NVDA says "check box"), so the specs hold for both, but it must find a control's name and its role in one sentence of one spoken phrase (`inOneSentence` in `registry/ouro/e2e/screen-reader/phrases.ts`).[^sr-one-sentence] Phrases are never joined, VoiceOver's hints ("You are currently on a button…", "To display a list of options…") are cut off first, and the reader's item text, which can run on into the next control, is never counted.[^sr-hints] So "Shakshuka Name edit text" (the dialog's text field) with a hint saying "button" does not pass for the Edit button; NVDA's "clickable, Edit, button, collapsed, opens dialog" does (`scripts/sr-phrases.test.mjs` holds both).

The specs wait for speech, never for a fixed time.[^sr-no-sleep] NVDA's phrases come from Guidepup's capture, which logs everything NVDA says.[^sr-nvda] VoiceOver lets AppleScript read only its last phrase, and Guidepup's capture reads it again only after waiting as long as that phrase takes to say: after a long hint, it missed the short phrase that named the newly focused control ("Edit dialog pop up button") and read the next hint, so the Dialog spec failed at random. On VoiceOver, `heard` instead watches the last phrase every 20 ms from one osascript process, and logs every phrase it read (`watchVoiceOver` in `screen-reader.ts`).[^sr-watch] Before each action the watch waits for VoiceOver to be quiet: no new phrase for 2 s (at most 10 s), as a person listens before pressing the next key (Enter pressed while VoiceOver was still speaking opened the dialog without VoiceOver ever saying its name).[^sr-ready] It then has VoiceOver say "Speech check" (`MARK` in `phrases.ts`) and, after another quiet second with that still its last phrase, runs the action; VoiceOver can drop or talk over MARK, so it is said again, three times in all (`readyForAction`).[^sr-ready] Only phrases after that last MARK count, so nothing said before the action does, and a control VoiceOver was already on still counts when it says it again as focus arrives. Then it checks each new phrase as it is read, for up to 15 s (`speechVerdict` in `phrases.ts`): a phrase that never came is an accessibility failure, and only a watcher that failed before the deadline (osascript could not run, or exited with an error) is infrastructure.[^sr-verdict] The watcher's own limit is longer than a whole test, so no check outlives it.[^sr-outlives]

VoiceOver starts for each test, as @guidepup/playwright's fixture starts it, and each VoiceOver test has a WebKit of its own: with one browser for every test, VoiceOver missed the Dialog's name as it opened once Checklist's test ran before it ([ourostack/ouro-ui#119](https://github.com/ourostack/ouro-ui/issues/119)).[^sr-119] NVDA starts once for each Playwright worker and quits after its last test (`registry/ouro/e2e/screen-reader/nvda.ts`): `nvda.stop()` returns while NVDA is still unloading its helper from the browser, and quitting between tests failed a passing test's context close ("browserContext.close: Test ended.") or took the shared browser down, so the next test could not open a context.[^sr-nvda-worker] Before each test NVDA is moved to the page as Guidepup's `navigateToWebContent` does, and the test fails as **infrastructure** when NVDA still reports another window (once it read "Start, window" and the test hung).[^sr-nvda-window] Each test closes its own browser context, and stopping a screen reader gives up after 30 s; anything that goes wrong there is logged as `[sr] teardown:` and does not fail a test that passed.[^sr-teardown]

VoiceOver's navigation to the page (`startReading`) is bounded at 45 s (`registry/ouro/e2e/screen-reader/navigation.ts`).[^sr-nav-bound] In the six passing lane jobs measured for that bound, a test's start to its first utterance, which includes the navigation, took 13 s to 35 s.[^sr-nav-measured] A navigation that hangs is stopped, waited on until VoiceOver's process has exited, and started again once; the retry is logged as a `[sr] navigation retry:` line.[^sr-nav-retry] So is a navigation that finds VoiceOver had quit between tests (AppleScript's "Application isn't running", -600), or that loses osascript's connection to System Events ("Connection is invalid", -609), or whose key press fails to compile because VoiceOver's scripting terms could not load ("Expected end of line, etc. but found identifier", -2741): VoiceOver is started again and the navigation tried once more.[^sr-nav-gone] The run summary counts those retries against the VoiceOver tests that ran, and says so above 1 in 50.[^sr-nav-rate] A navigation that hangs on both tries fails the test as infrastructure, "VoiceOver stopped answering while it reached the page".[^sr-nav-hung] A navigation that finishes with VoiceOver still outside the page's web area (its first utterance empty, or only how to enter the web area) is run again, without restarting VoiceOver; outside on both tries, the test fails as infrastructure, "VoiceOver never entered the page's web area".[^sr-nav-outside] Only the navigation is retried, never a test's assertions.[^sr-nav-only]

A VoiceOver start that fails because VoiceOver cannot be started, or was not running (Guidepup's message, or AppleScript's -600 anywhere in its cause chain), is retried once: the start is logged as a `[sr] start retry:` line, `registry/ouro/e2e/screen-reader/start-retry.ts`.[^sr-start-retry] Before the retry, the diagnostics are logged as `[sr] start diagnostics:` lines: the VoiceOver and ScreenReader processes that are running, and the newest VoiceOver crash report from the last 10 minutes, its first 15 lines.[^sr-start-diagnostics] VoiceOver is stopped and, if its process is still running after 10 s, killed; the system then gets about 15 s to settle, and the start runs again.[^sr-start-settle] A second failure is thrown as it was: one that cannot start is infrastructure, "VoiceOver did not start". A start that fails any other way is never retried.[^sr-start-second] The run summary counts start retries beside the navigation retries.[^sr-start-summary]

## Known findings

- VoiceOver with WebKit said Select's value without its last three characters, with a comma before it (", Choose a cou, Course, list box pop up" for the placeholder "Choose a course", ", S, Course" for "Side"), while NVDA read it whole ([ourostack/ouro-ui#113](https://github.com/ourostack/ouro-ui/issues/113)).[^sr-113] It is WebKit bug [285047](https://bugs.webkit.org/show_bug.cgi?id=285047), for a `<button>` with `role="combobox"`, and it happened on both of the lane's macOS versions.[^sr-113] Select's trigger is now a `<div role="combobox">`, which VoiceOver reads whole on both, and the spec takes only the whole value.[^sr-113]
- VoiceOver at times does not announce a Checkbox's or a Checklist row's new state after Space: for a Checkbox it says nothing, and for a Checklist row only the checkbox's hint ("You are currently on a checkbox…"), though the box has changed and keeps the focus ([ourostack/ouro-ui#118](https://github.com/ourostack/ouro-ui/issues/118)). That happens on macOS 15 only: in nine runs on macOS 26 VoiceOver read every change, so the specs fall back there only (`olderMacOS`), and macOS 26 must announce it.[^sr-118] It says nothing in the same way for a native `<input type="checkbox">` and a plain `role="checkbox"`, so the miss is VoiceOver's.[^sr-118] On VoiceOver only, and for that step only (`heardOrDescribed`), each spec then asks VoiceOver to describe the focused box (VO-F4), and that one phrase must give its name, the checkbox role and the new state; it logs `[sr] finding: ourostack/ouro-ui#118`.[^sr-118] A miss in which VoiceOver said the old state, a missing or wrong description, and a box whose state did not change in the page are still failures, and NVDA must still announce the change.[^sr-118]
- VoiceOver at times does not say the Dialog's name as it opens: it says only the focused field ("Shakshuka"), then the field's hint ([ourostack/ouro-ui#119](https://github.com/ourostack/ouro-ui/issues/119)).[^sr-119] On VoiceOver only, and for the opening step only, the spec then has VoiceOver stop interacting with the field once (VO-Shift-Up, which the field's hint offers as "exit this group"), moving the VoiceOver cursor, not the focus, to the dialog, and describes the item in the cursor (VO-F3) up to three times: one phrase must give "Edit recipe" and "web dialog".[^sr-119] Describing the focused field (VO-F4) names only the field.[^sr-119] It logs `[sr] finding: ourostack/ouro-ui#119`, still checks that the focus is inside the dialog, and a missing or wrong description is still an accessibility failure.[^sr-119] On macOS 26 it missed once in 25 openings, and focusing the dialog itself or the field a task later did no better than the first field, so Dialog keeps its focus.[^sr-119-probe]
- VoiceOver on macOS 26 now and then says only a control's usage hint, never its name ([ourostack/ouro-ui#2085](https://github.com/ourostack/ouro-ui/issues/2085)).[^sr-2085] So on VoiceOver, any step whose miss holds something and nothing but hints falls back to describing the focus (VO-F4), and that one phrase must pass the step's own matcher; a miss of silence or of a phrase that names something fails as it is, and so does a describe that fails the matcher.[^sr-2085] Each fallback logs `[sr] finding: hint-only`, and the run's summary counts them against its steps, flagging more than 1 in 50.[^sr-2085-count] A nightly strict run after the lane, VoiceOver on `macos-26` with the fallback off (`SR_STRICT=1`), opens or updates one issue when a step misses, so a control VoiceOver only describes, never announces, still shows without failing pull requests or main.[^sr-2085-strict]
- NVDA with Chromium says a Dialog's name twice as it opens ("Edit recipe, dialog. Edit recipe, dialog. Name, edit, Shakshuka") when the focus moves to its first field as it appears ([ourostack/ouro-ui#1778](https://github.com/ourostack/ouro-ui/issues/1778)).[^sr-1778] It is NVDA's [nvaccess/nvda#8971](https://github.com/nvaccess/nvda/issues/8971), which repeats a dialog in browsers, and the spec accepts the name said twice; focusing the field a task later says it once, but keys pressed in that task would go to the trigger, so Dialog does not.[^sr-1778]
- VoiceOver often reads only a field's value when Form moves focus to its error after a submit: no label, no error, no "invalid" ([ourostack/ouro-ui#1720](https://github.com/ourostack/ouro-ui/issues/1720)).[^sr-1720] So Form's alert says a short summary of the errors as the submit's answer arrives ("Couldn't save: 1 problem. Name: …"), and the TextField spec asks both readers for that summary, then describes the focused field (its label, its error and "invalid"); no step falls back to a description.[^sr-1720]
- VoiceOver on macOS 15 says only "You are currently in a menu." when a menu opened from the keyboard moves focus to its first item, and, asked, that the menu has keyboard focus ([ourostack/ouro-ui#1721](https://github.com/ourostack/ouro-ui/issues/1721)).[^sr-1721] On macOS 26.7.2, with the same WebKit 27.2, it reads "Edit menu item" with no workaround, so Menu has none.[^sr-1721] The Menu spec only logs that step on macOS 15 (`[sr] finding (ourostack/ouro-ui#1721)`) and asks for "Edit" everywhere else, NVDA included.[^sr-1721]
- As the Select list opens, VoiceOver can read the first option before it has its name ("selectable (null)"); the spec only logs that moment and checks each move once the list is open.[^sr-select]

- VoiceOver's navigation to the page hung in 13 of the 18 failed lane jobs filed under [#2014](https://github.com/ourostack/ouro-ui/issues/2014) (macOS 26, and the advisory macOS 15 ones), at tests 2 to 23 of their runs; 12 of those 13 hung past the middle of their run.[^sr-2014-cluster] The hung tests ended at the 3-minute test timeout, and the teardown then found VoiceOver not running.[^sr-2014-cluster] Four jobs failed on AppleScript refusing a key press, and one on VoiceOver's start (`Unable to activate application: VoiceOver`).[^sr-2014-cluster]

## When it runs

- Nightly, on main (`.github/workflows/screen-reader.yml`).
- After every release's tag: main's push runs the lane on the commit `release.yml` tagged, which no longer waits for it.[^sr-release] When the lane fails twice on a commit after passing on the one before, `screen-reader-revert.yml` reverts the pull request behind it through a pull request that merges on green, and the next release carries the revert.[^sr-release]
- By hand: `gh workflow run screen-reader.yml --ref <branch> -f source_sha=<the branch's tip SHA>`. The lane refuses any other commit.
- On a pull request only when it changes the lane's own files: a spec, the harness in `registry/ouro/e2e/screen-reader/`, `playwright.screen-reader.config.ts`, the lane's workflows or its `scripts/sr-*` scripts (`laneFiles` in `scripts/sr-impact.mjs`), so a spec is proven on VoiceOver and NVDA before it merges ([ourostack/ouro-ui#666](https://github.com/ourostack/ouro-ui/issues/666)). Every other pull request waits for main's push run, as macOS and Windows runners are scarce, and a red push run is the red-main alarm ([below](#on-a-pull-request)).[^sr-pr-none]

It never runs for a fork's pull request.[^sr-triggers]

## On a pull request

ci.yml's plan runs this on a pull request into main from this repository only when the change touches the lane's own files; then `scripts/sr-impact.mjs pr` selects the specs the change can reach, and every spec when it cannot say.[^sr-pr-none] Any other pull request skips it, and a failure its change causes lands on main, where it blocks the next release.[^sr-pr-none] A pull request that runs the lane gets its failure on the pull request, rather than on main.[^sr-pr-why]

- **Which specs.** `scripts/sr-impact.mjs` finds each spec's story through its `storyIds` entry in `stories.ts`, and every file that story loads at run time, directly or through another file.[^sr-closure] A change to a component selects each spec whose story loads it: a change to TextField selects the TextField spec, which also opens Form's server-errors story, because Form renders TextField.[^sr-each-spec] A change to anything the lane shares runs every spec: the library, the theme, the harness and its story ids, the lane's workflow and scripts, the dependencies and the build.[^sr-shared] So does a change the mapping cannot place.[^sr-unmapped] Prose, change fragments, the site and other workflows select none.[^sr-none]
- **Same repository only.** ci.yml calls this workflow only when the pull request's head repository is this one, and the lane refuses a fork's pull request too.[^sr-fork] A fork's code is not a branch of this repository.
- **Hosted runners only.** Guidepup's VoiceOver and TCC changes die with the ephemeral GitHub-hosted runner, so the lane runs on a pull request only there, as on main: VoiceOver on macos-26 and NVDA on windows-2025 gate it, and the advisory VoiceOver on macos-15 runs only nightly.[^sr-runners]
- **Required when it runs.** Its jobs report under ci.yml's `screen-reader` job, which the `ci` check waits for, so a failed spec fails the check that already gates the merge.[^sr-required] A pull request whose change selects no spec has that job skipped, and the `ci` check counts the skip as a pass.[^sr-skip]
- **Yields to main.** `scripts/sr-yield.mjs` waits before the pull request's jobs start, while a run of this workflow has a macOS job queued or running.[^sr-yield] A push or nightly run of main takes two macOS runners at once and a release's dispatch one, so a pull request's run waits behind them.[^sr-macos] It reads once a minute, starts after 10 minutes at the latest,[^sr-deadline] and fails open: it never fails its step.[^sr-yield-open]
- **Measured apart.** The budget judges the critical path, which leaves the lane out (`offPath` in `scripts/ci-budget.mjs`), since the lane waits on macOS runners that its own cap queues.[^sr-offpath] The wall time and the runner time still count it.[^sr-counts] The CI time summary prints the lane's own critical path on its own line, judged against `laneBudgetMinutes`, which is report-only until the first 10 pull requests on #2017 set it.[^sr-lane-line] `node scripts/sr-lane-timings.mjs <pull request>...` reports, for each pull request, the lane's wall time, the wall time it adds to the run, and its macOS and other runner minutes.[^sr-timings]

## How a failure is classified

`scripts/sr-classify.mjs` reads the log and the exit code of `pnpm test:sr`:

- **accessibility**: an expected utterance was missing or wrong, or a story the lane opens is missing.[^sr-classify] This fails the run and blocks a release.
- **harness**: Playwright refused the lane's own command line or found no test to run (`Project(s) … not found`, `No tests found`, an unknown option), so no test started.[^sr-harness] This fails the run without a retry or an infrastructure issue: fix the command in the workflow.
- **infrastructure**: VoiceOver or NVDA did not start or could not be controlled, a TCC prompt appeared, a test timed out before the screen reader said anything, the Storybook server never became ready, the runner image was broken, or every error in the run is the browser failing to open or close a test's context, which only the fixtures around a test do (a missing utterance, a failed `expect` or any other error in the run makes it **accessibility**).[^sr-classify] A nightly run or a push to main opens, or comments on, one issue labelled `screen-reader-infra` (`scripts/sr-infra-issue.sh`).[^sr-infra-issue] VoiceOver's "not running" is "VoiceOver stopped answering while it reached the page" once a test reached the page, and "VoiceOver did not start" before that.[^sr-not-running] A navigation-retry or start-retry line is no finding, so a test's own failure still decides the class.[^sr-nav-no-finding][^sr-start-no-finding]

On main, red-main's auto-revert (ourostack/.github, `tools/red-main`) reverts the pull request behind a red lane only for an accessibility finding: the classify step annotates any other failed verdict, harness or infrastructure or none at all, `title=infra`, and auto-revert never reverts a job with that annotation.[^sr-auto-revert]

## Running it

On a machine set up for screen reader automation (`npx @guidepup/setup setup`, then `npx @guidepup/setup install` in this repository):

```sh
pnpm test:sr --project voiceover   # macOS
pnpm test:sr --project nvda        # Windows
```

The config (`playwright.screen-reader.config.ts`) builds Storybook into `.tmp/storybook-sr` and serves it on port 6006, runs one test at a time, headed, and never retries.[^sr-config] The main end-to-end run (`pnpm test:e2e`) ignores `*.sr.spec.ts`.

## Security

Guidepup's setup changes the operating system: on macOS it enables VoiceOver's AppleScript control and writes the TCC database so the runner may automate it; on Windows it installs a portable NVDA. So the lane:

- runs only on GitHub-hosted runners, which are thrown away after the job (a step fails on any other runner);
- checks out only the commit it was given, and only when that commit is the tip of the dispatched branch, so it never runs code fetched by SHA from a fork;[^sr-tip]
- runs from every push to main, its nightly schedule or a dispatch, which needs write access to the repository, and from ci.yml for a pull request from this repository, never a fork's;[^sr-triggers]
- holds `contents: read` and no secrets, with every action pinned to a commit; only the job that files the infrastructure issue may write issues, and it runs no Guidepup.[^sr-permissions]
