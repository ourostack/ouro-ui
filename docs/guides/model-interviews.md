# What models build with: interviews

Ouro UI is not yet the models' choice: more than half of the models that answered picked it as their primary in 1 of the 6 listed jobs and scales, and the record needs all 6. In the open arm, 0 of 16 sessions found Ouro UI before the last question named it.

Each frontier model is interviewed as a customer, by the Mom Test: its own practice before any toolkit is named, then three real jobs, each at a product team's scale and a large company's, then what went wrong a year later, and Ouro UI named only in the last question. The questions were [registered before any run](https://github.com/ourostack/ouro-ui-core/blob/bf4539aad126b1d6999883eb84149f86b6acd567/docs/decisions/2026-11-19-model-interviews.md) and don't change between runs; a change starts a new series. This series is kept apart from the [model reviews](model-reviews.md), which ask one question, and its counts never mix with theirs.

Two research arms answer different questions. The **listed arm measures merit**: each job lists the same 20 candidates as the model reviews, by name and link only, in a fresh random order for each session, with Ouro UI never first. The **open arm measures discoverability**: the job lists nothing ("Find the options yourself."), so a loss there says agents don't find Ouro UI, not that it's worse. Every pick, count and answer here is computed from the runs' records by a script.

## What the models asked for, and what we changed

This section is synthesis: each answer split into statements, each statement given a Mom Test signal, and statements about the same thing clustered into a finding. Every quote is verbatim and links the transcript it came from, so it can be checked. A finding is filed as an issue labelled `model-review`, ranked by how many models raised it and how strong the evidence is.

### Disconfirming evidence: not a pain, or a surprise

What could show Ouro UI is solving the wrong problem, or that the models' reasons aren't what we'd assume, first.

#### Writing UI code isn't the hard part for models, and the failures they expect sit outside any UI kit.

Signal: not-a-pain. Raised by 8 models: Claude Opus 5.5, Claude Sonnet 5.5, GPT-6.2 Sol, GPT-6.2 Astra, GPT-6.1 Terra, Gemini 4 Hydrogen, Grok 4.7, MAI Code 2. Status: open. [#2314](https://github.com/ourostack/ouro-ui/issues/2314).

All 32 sessions said building good human interfaces is a problem, but six models said outright that markup, layout, state and components are the easy part; the hard part is knowing the result is good for people. In the pre-mortem every model placed its likeliest failure where no component kit reaches: delivery and unread state, offline sync, notifications, governance. This disconfirms a pitch led by better components for agents: Ouro HX has to be argued through what it handles that models admit missing, and Ouro should say plainly what it doesn't cover.

### What the models asked Ouro UI to change

#### A2UI is the default format for agent cards, and models file Ouro's composed tree as an adapter for it.

Signal: past-behavior. Raised by 8 models: Claude Opus 5.5, Claude Sonnet 5.5, GPT-6.2 Sol, GPT-6.2 Astra, GPT-6.1 Terra, Gemini 4 Hydrogen, Grok 4.7, MAI Code 2. Status: changed. Sixteen of 32 chat decisions used A2UI, and every model used it at least once, for reasons Ouro's composed tree also meets: UI as validated data rather than code, a catalog the app owns, native renderers. All eight models called catalog-validated cards the answer to the chat app's hardest piece, yet none chose Ouro's tree for them. Ouro should present itself as the native A2UI renderer and catalog on every platform, rather than a rival format with an A2UI adapter.
