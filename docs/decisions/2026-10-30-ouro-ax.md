# Decision: what Ouro AX is

Ouro UI's halves are named for who they serve. Ouro HX is for people: an agent builds an interface and a person uses it. Ouro AX is for agents: an agent uses an interface built for it, such as a CLI, an HTTP API or an MCP server. Until now, Ouro AX was a name without a product behind it. This record says what it is, and why, from four competing designs that were each built into a real app's agent interface (a command line plus an HTTP API) and measured with real agents.[^probes] That app is the first adopter. Its records in the evidence folder call its command line `app`.

## The decision

Ouro AX has these parts, and the last decides what goes into the others:

1. **A standard with an X-ray.** The standard is a list of checkable claims about agent-facing surfaces: CLI commands, HTTP routes and MCP tools. The X-ray (`ax-xray`) is a black-box checker. It calls an interface the way an agent would, without importing its code, and reports which claims hold on which command, route and tool, with the exact fix where one does not.[^xray] An interface conforms to Ouro AX when an X-ray report, pinned to a claim-set version and the interface's commit, covers a complete inventory of its agent-facing surfaces and shows every applicable `must` claim holding, with no surface untested or silently exempted.[^xray] The X-ray is the conformance authority, much as the Inspector shows what a page is built from in Ouro HX, though it checks behavior rather than provenance.
2. **A kit.** Copy-in TypeScript source in the shadcn registry format, installed the same way as Ouro HX components. With the kit, one definition of a command gives the parser, the usage line, the help, `help --json`, `--json` output, the exit codes, one-line errors that name the fix, and the same command as an MCP tool.[^kitparts] The kit also has three shapes for what comes back to an agent: an outcome for every action, a typed wait, and an attributed work event.[^shapes] The kit is designed to meet the standard, but the X-ray decides: a tool built without the kit can conform, and one built with it can fail.
3. **The evaluation gate.** A claim becomes `must` in one of two ways: an agent evaluation reproduces agents failing a task because of what the claim forbids, and the fix removes the failure; or the claim protects safety, compatibility or integrity, states the hazard, and has an executable check.[^admission] Anything else stays `should` until evidence arrives.[^admission] Real agents in fresh sessions do real tasks against the interface, and a scorer that calls no model judges the result from the end state.[^method] This mirrors Ouro HX's agent-usability test, which measures whether an agent with no Ouro-specific context builds a correct screen from the installed code alone.[^hx]

## Why: what the probes found

Four probes each built one thesis of Ouro AX into the first adopter, and measured it with the same evaluation: five tasks (triage, a draft handed back to the person, a send other people see, an edit, and waiting for a reply), two runs each, with one model and real agents in fresh sessions against the first adopter's mock, which serves made-up data.[^probes] [^method] Two runs per task is evidence for a first decision, not a benchmark: the same task varied by up to twice the calls between runs.[^variance] The baseline is the first adopter's main branch at `ffdecc01`, before it added `--text` and `--file` in its pull request #440.[^baseline]

**In this evaluation, principle-derived claims didn't predict the failures.** The standard-and-X-ray probe first wrote its claims from the first adopter's fifteen AX principles. Fixing every claim that failed took its X-ray score from 75.6% to 99% of checks and changed no task outcome.[^principles] Those claims matched none of the twelve wrong turns agents made on its main branch.[^principles] Two claims written from the agents' actual failures matched seven of the twelve: "text an action needs can be given as an argument, not only on stdin" and "a wait accepts the reference the agent already holds."[^seven] With those two fixed, the same five tasks went from 5 of 10 runs to 10 of 10.[^seven] This is why the evaluation gate exists. Safety rules still belong in the standard without a failing run: no agent in these runs misspelt a flag or used `--dry-run`, yet refusing an unknown flag and previewing an action other people see are worth requiring.[^flags]

**One definition reduces drift.** At `ffdecc01`, the first adopter's sends and edits failed in every run because the help told agents to pipe text in, and the recommended allow-list refuses a pipe.[^pipe] The kit probe generated the usage line from the same declaration as the parser and the MCP schema, so what an agent reads and what the tool accepts come from one place; handwritten code behind a command can still diverge, which is what the X-ray is for. Its CLI passed 8 of 10 tasks against main's 5 of 10.[^kit] As MCP tools, the same definitions passed every send (4 of 4, in 2.3 calls on average), but cost more tokens on reads and failed on waiting.[^mcp]

**What comes back matters as much as what goes in.** The outcomes probe made every action return its state, who can see it, a postcondition the tool checked itself, a receipt and the next valid commands.[^outcomes] When an edit's outcome said its postcondition was checked and held, neither run read the conversation back to verify it; in both comparison runs without it, the agent did.[^outcomes] Its typed wait took "tell me when someone replies" from 1 of 2 to 2 of 2, with about half the calls and well under half the tokens.[^wait]

**Waiting was the common missing primitive.** Three of the four probes independently added a way to wait on a conversation, and in each the wait task improved.[^three] Main's `watch` accepted only meetings, so agents either streamed every event until stopped or gave up.[^meetings]

**Attributed work events serve the person and the measurement, not the agent's task.** The collaboration probe made the first adopter record every handoff and wait as an attributed work event.[^flow] Agents gave a reason with their drafts only once the help asked for one (0 of 2 runs before, 2 of 2 after).[^flow] The event stream didn't change task success for triage, drafting, sending or editing.[^flow] It let agents answer some questions about where the time went: with a value-stream view over the first adopter's plan, agents named the item that took the most agent time in its lane in 2 of 2 runs, in 4 calls, against 0 of 2 in 20 calls without it.[^q2] The agent time in that view was inferred from session logs, not measured.[^flow]

The full measurements, per probe and per run, are in the [evidence folder](2026-10-30-ouro-ax/evidence/) beside this record.

## What's in the first version

| Part | Registry item | What it gives you |
| --- | --- | --- |
| Command definition | `ax-command` | One declaration of a command: its arguments, flags, effect and examples. The parser, usage, help and MCP schema come from it. |
| Errors | `ax-problem` | One line per refusal, ending `Fix: <exact command>`, the same shape on the CLI, over HTTP and over MCP. |
| Exit codes | `ax-exit-codes` | A stable table of codes, printed in help and `help --json`. |
| Effects | `ax-effects` | Who sees an effect: only you, or other people. Other people's actions take `--why` and `--dry-run`, and preview who will see them. |
| Output | `ax-output` | Text and `--json` from the same result. |
| Outcomes | `ax-outcome` | The typed result of an action: state (done, queued, planned, needs the person, uncertain, refused, failed), audience, a checked postcondition, a receipt and the next commands. |
| Waits | `ax-wait` | A typed wait on a reference the agent holds, with a cursor to resume from and a time limit. |
| Work events | `ax-work-event` | An attributed event per handoff, wait, action and return, and a fold from events to figures. |
| MCP | `ax-mcp` | The same command definitions served as MCP tools. |
| Claims | `ax-claims` | The standard: the claims, with their rules, reasons, evidence and checks. |
| X-ray | `ax-xray` | The checker for a CLI, an HTTP API or an MCP server, with text, JSON, Markdown and HTML reports. |

The claims start in two tiers.[^admission] Each `must` claim cites either the evaluation run in which agents failed without it, or the hazard it prevents and its check.[^admission] `should` claims come from principles and other products' experience and wait for evidence. A claim applies to a surface by a rule the X-ray computes from what the interface says about itself (a CLI command, an HTTP route, an action other people see), not by a hand-written waiver. The X-ray fails on a broken `must` claim and reports a broken `should` claim.[^mustexit]

`ax-mcp` ships as a preview in this version: the probe found two bugs in it by measuring, and its claims cover few behaviors so far.[^mcp]

## How the work-measurement idea fits

The question was whether one theory ties the pieces together. Desk's factory measures work bottom-up from session transcripts: jobs, touch time, human attention, waits, returns. The first adopter's plan tool measures it top-down: issues, dependencies, claims and waits on people. Joining them would show, for a plan item, how much was agent work, how much was waiting on a person, and how much was rework.

The probes place it inside Ouro AX and beside it:

- **Inside Ouro AX: the work event.** The event's shape (identity, who acted and for whom, what it was about, why, its receipt, a correlation id, the time) and the rule that an AX surface emits one for its handoffs, waits and actions other people see are interface contracts, like an error shape. They live in `ax-work-event`, which also counts its own stream (actions, handoffs, waits and how long the finished waits lasted) and nothing beyond it.[^fold] An interface can emit only what it observes, so AX does not measure total touch time, human attention or rework. The emit rule is a `should` claim: the evidence so far shows it serves the person and the measurement, not the agent's task.[^flow]
- **Beside Ouro AX: the value stream.** Joining a plan item to its pull requests, sessions and events needs history and identity across systems that a single interface does not hold. That join belongs in the plan tool (the first adopter's `plan flow`) and in Desk's factory. Today the bottom-up half is missing for the first adopter: the factory records on the machine where this was measured name none of its pull requests, so the agent-time figures in the probe were inferred from session logs.[^factory]

The loop that ties them together is the unifying idea. Agents work through Ouro AX surfaces. The surfaces emit outcomes and work events. The factory and the plan fold those into a value stream per item. The wrong turns and waits that the value stream exposes become evaluation tasks. The evaluations admit claims, and the X-ray holds the surfaces to them. Measured work decides what the standard says, and the standard decides what an agent interface does.

## What Ouro AX is not

- **Not a protocol replacement.** It takes CLIs, HTTP APIs and MCP as they are, and adds a standard and a kit on top.
- **Not an agent identity system.** A person's own agent working through their client, with their access, is a different model from an agent with its own organizational identity. Ouro AX describes the interface either one uses, and its effects and work events say who acted and for whom, but it doesn't grant or govern identity.
- **Not a gate on the person.** Nothing in the kit makes an agent wait for a person's approval. An action other people see needs a reason and shows its audience; it doesn't need a click.

## What comes next

- The first version of Ouro AX ships in the next minor release of this repository, after the Ouro HX release being cut now.
- The first adopter adopts it. Its CLI command inventory comes from its own command registration and its HTTP inventory from its router, and its CI runs the X-ray against its mock daemon and fails on a missing, unknown or untested surface or a broken applicable `must` claim. It also requires its CLI commands to run through their `ax-command` declarations. When that report passes on its main branch, its agent interface is the first to conform to Ouro AX and becomes its reference adopter.
- A new evaluation failure becomes a candidate claim. A claim is reviewed for demotion when repeated evaluations show that it does not change an outcome, unless it guards against a hazard.
