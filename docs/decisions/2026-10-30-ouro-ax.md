# Decision: what Ouro AX is

Ouro UI has two halves, named for who they serve. Ouro HX is for people: an agent builds an interface and a person uses it. Ouro AX is for agents: an agent uses an interface built for it, such as a CLI, an HTTP API or an MCP server. Until now, Ouro AX was a name with no product behind it. This record says what it is, and why, from four competing designs that were each built for real in Tandem's agent interface and measured with real agents.

## The decision

Ouro AX is three things, and the third one is how we decide what goes into the other two:

1. **A standard with an X-ray.** The standard is a list of checkable claims about agent-facing surfaces: CLI commands, HTTP routes and MCP tools. The X-ray (`ax-xray`) is a black-box checker. It calls an interface the way an agent would, never importing its code, and reports which claims hold on each command, route and tool, with the exact fix for each one that doesn't. An interface is Ouro AX when the X-ray says every `must` claim holds on every surface. That's the same rule as Ouro HX, where the Inspector shows that a page is built from Ouro components.
2. **A kit.** Copy-in TypeScript source in the shadcn registry format, installed the same way as Ouro HX components. With the kit, one definition of a command gives the parser, the usage line, the help, `help --json`, `--json` output, the exit codes, one-line errors that name the fix, and the same command as an MCP tool. The kit also has three shapes for what comes back to an agent: an outcome for every action, a typed wait, and an attributed work event. A tool built with the kit passes the standard by default; a tool built without it can still pass, and the X-ray says so.
3. **The evaluation gate.** A claim becomes `must` only when an agent evaluation shows an agent failing a task because of the thing the claim forbids. Real agents in fresh sessions do real tasks against the interface, and a scorer that calls no model judges the result from the end state. This mirrors Ouro HX's agent-usability test, which measures whether an agent with no Ouro-specific context builds a correct screen from the installed code alone.

## Why: what the probes found

Four probes each built one thesis of Ouro AX into Tandem, the first adopter, and measured it with the same evaluation: five tasks (triage, a draft handed back to the person, a send other people see, an edit, and waiting for a reply), two runs each, with real agents against Tandem's mock daemon.

**Principles alone measure the wrong things.** The standard-and-X-ray probe first wrote its claims from Tandem's fifteen AX principles. Fixing every claim that failed took Tandem's X-ray score from 75.6% to 99% of checks and changed no task outcome. Those claims matched none of the twelve wrong turns agents made on Tandem's main branch. Two claims written from the agents' actual failures matched seven of the twelve: "text an action needs can be given as an argument, not only on stdin" and "a wait accepts the reference the agent already holds." Fixing those two took the same tasks from 5 of 10 to 10 of 10. This is why the evaluation gate exists: Ouro AX admits a claim when evidence shows it matters, and leaves it as advice until then.

**One definition prevents drift.** Tandem's sends and edits failed in every run on main because the help told agents to pipe text in, and the recommended allow-list refuses a pipe. The kit probe generated usage from the same definition as the parser and the MCP schema, so what an agent reads and what the tool accepts can't disagree. Its CLI passed 8 of 10 tasks against main's 5 of 10. As MCP tools, the same definitions passed every send (4 of 4, in 2.3 calls on average), but cost more tokens on reads and failed on waiting.

**What comes back matters as much as what goes in.** The outcomes probe made every action return its state, who can see it, a postcondition the tool checked itself, a receipt and the next valid commands. When an edit's outcome said its postcondition was checked and held, no agent read the conversation back to verify it; on main, every agent did. Its typed wait took "tell me when someone replies" from 1 of 2 to 2 of 2, with about half the calls and well under half the tokens.

**Waiting is the one primitive every probe needed.** Three of the four probes independently added a way to wait on a conversation, and in each the wait task improved. Main's `watch` accepted only meetings, so agents either streamed every event until stopped or gave up.

**Attributed work events serve the person and the measurement, not the agent's task.** The collaboration probe made Tandem record every handoff and wait as an attributed work event. Agents gave a reason with their drafts only once the help asked for one (0 of 2 runs before, 2 of 2 after). The event stream didn't change task success for triage, drafting, sending or editing. It did make the work measurable: with a value-stream view over Tandem's plan, agents named the item that took the most agent time in its lane in 2 of 2 runs, in 4 calls, against 0 of 2 in 20 calls without it.

The full measurements, per probe and per run, are in the evidence folder beside this record.

## What's in Ouro AX v1

| Part | Registry item | What it gives you |
| --- | --- | --- |
| Command definition | `ax-command` | One declaration of a command: its arguments, flags, effect and examples. The parser, usage, help and MCP schema all come from it. |
| Errors | `ax-errors` | One line per refusal, ending `Fix: <exact command>`, the same shape on the CLI, over HTTP and over MCP. |
| Exit codes | `ax-exit-codes` | A stable table of codes, printed in help and `help --json`. |
| Effects | `ax-effects` | Two effects: only you see it, or other people see it. Other people's actions take `--why` and `--dry-run`, and preview who will see them. |
| Output | `ax-output` | Text and `--json` from the same result. |
| Outcomes | `ax-outcome` | The typed result of an action: state (done, queued, planned, needs the person, uncertain, refused, failed), audience, a checked postcondition, a receipt and the next commands. |
| Waits | `ax-wait` | A typed wait on any reference the agent holds, with a cursor to resume from and a time limit. |
| Work events | `ax-work-event` | An attributed event for each handoff, wait, action and return, and one fold from events to figures. |
| MCP | `ax-mcp` | The same command definitions served as MCP tools. |
| Claims | `ax-claims` | The standard: every claim with its rule, the reason, its evidence and its check. |
| X-ray | `ax-xray` | The checker for any CLI, HTTP API or MCP server, with text, JSON, Markdown and HTML reports. |

The claims start in two tiers. `must` claims each cite the evaluation run in which an agent failed without them. `should` claims come from principles and other products' experience and wait for evidence. The X-ray fails on a broken `must` claim and reports a broken `should` claim.

## How the work-measurement idea fits

Ari asked for "the grand unifying theory that makes it all make sense". Desk's factory measures work bottom-up from session transcripts: jobs, touch time, human attention, waits, returns. Tandem's plan measures it top-down: issues, dependencies, claims and waits on people. Joining them would show, for each plan item, how much was agent work, how much was waiting on a person, and how much was rework.

The probes put it in two places:

- **Inside Ouro AX: the work event.** The event's shape, the rule that an AX surface emits one for every handoff, wait and action other people see, and the fold from events to figures are interface contracts, like an error shape. They live in `ax-work-event`. The emit rule is a `should` claim: the evidence so far shows it serves the person and the measurement, not the agent's task.
- **Beside Ouro AX: the value stream.** Joining a plan item to its pull requests, sessions and events needs history and identity across systems that no single interface holds. That join belongs in the plan tool (Tandem's `plan flow`) and in Desk's factory. Today the bottom-up half is missing for Tandem: the factory records on the machine where this was measured name no Tandem pull request, so every agent-time figure in the probe was inferred from session logs.

The loop that ties them together is the unifying idea. Agents work through Ouro AX surfaces. The surfaces emit outcomes and work events. The factory and the plan fold those into a value stream per item. The wrong turns and waits that the value stream exposes become evaluation tasks. The evaluations admit claims, and the X-ray holds every surface to them. Measured work decides what the standard says, and the standard decides what every agent interface does.

## What Ouro AX is not

- **Not a protocol replacement.** It works with CLIs, HTTP APIs and MCP as they are, and adds a standard and a kit on top.
- **Not an agent identity system.** A person's own agent working through their client, with their access, is a different model from an agent with its own organizational identity. Ouro AX describes the interface either one uses, and its effects and work events say who acted and for whom, but it doesn't grant or govern identity.
- **Not a gate on the person.** Nothing in the kit makes an agent wait for a person's approval. An action other people see needs a reason and shows its audience; it doesn't need a click.

## What comes next

- Ouro AX v1 ships as release v1.3.0 of this repository, after Ouro HX v1.2.15.
- Tandem adopts it until its X-ray shows every `must` claim holding on every command and agent-port route, every command is declared with `ax-command`, and that check runs in Tandem's CI. Tandem's agent interface is then the first version of Ouro AX.
- Each new evaluation failure becomes a candidate claim. A claim that never changes an outcome is demoted.
