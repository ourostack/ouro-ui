# Ouro Current

Ouro Current is our own Dependabot for Ouro UI. Install the [Ouro Current GitHub App](https://github.com/apps/ouro-current) on a repository, and when Ouro UI, Ouro UI core, Ouro UI for Apple, Ouro UI for Windows or Ouro UI for Android releases, that repository gets one small pull request, "Update to Ouro UI vX", with auto-merge on. Nothing else to set up: it finds the pin files by their names.

## What it does

- **Finds the pins by name** in the repository's default branch:[^find] an Ouro HX install record (`.github/ouro-hx-installed.json`), a file vendored from an ouro-ui-core release (`ouro-ui-core/pin.json`), files vendored from a commit (`upstream-sources.lock.json`), core's `dist-manifest.json` copied beside the files vendored from its release (`tools/ouro-actions/`), SwiftPM (`Package.swift`, `Package.resolved`), XcodeGen (`project.yml`), an Xcode project (`project.pbxproj`), NuGet (`Ouro.UI.Windows` and `Ouro.Actions` in a `PackageReference` or a central `PackageVersion`, in a `.csproj`, `.props` or `.targets` file, or in an MSBuild property one of them reads or named `Ouro…Version`), Gradle (`bot.ouro.ui:*` in a build script or a version catalog, `libs.versions.toml`, through its `version.ref` when only Ouro libraries use it, or in a variable the build script defines or named `ouro…Version`, as in `gradle.properties`), and a workflow's `OURO_UI_TAG`, which it reports but leaves alone.
- **Moves each pin to the newest release** and writes what that release would install.[^versions] An Ouro HX file takes the new tag's source, rewritten to the app's aliases as the shadcn CLI rewrites it, and the install record keeps the source's hash.[^hx] Each file stays where the install record has it while its item installs it there, so an app that keeps Ouro check in `lib/ouro/check/` apart from its components in `src/` is updated in place, and a file an item gains goes beside that item's other files.[^placement] A file whose item now installs it elsewhere moves there and its old copy is deleted, and package.json gets what the move needs: the `#ouro-ax/*` import the moved files resolve through, and the script paths that named the moved file.[^moves] An item an updated item now depends on comes with it, as the CLI follows `registryDependencies`, unless the app already has that file.[^dependencies] A file it adds goes where the app's `components.json` and `tsconfig.json` resolve its alias, and its imports use those aliases, whether they sit at the root or in a package of a monorepo.[^aliases]- **Takes core's files from its release**: core commits no `dist/`, so a lock source or a copied `dist-manifest.json` that follows core reads its files from the release's dist asset.[^core-dist] A copied manifest moves only with the files it lists, since a repository checks them against its hashes: when one of them was edited here, or the release no longer ships it, the manifest and its files stay and that file is named.[^core-manifest] A file the manifest does not list is not touched.[^core-manifest] An update that moves an `ouro-actions.mts` generator runs `generate` with it on the repository's declarations, as its package scripts, workflows, Makefile or a shell script they call (a wrapper like `scripts/ouro-actions.sh generate`) run `generate` or `check`, and commits the projections it changed with the version: a newer generator can write different projections from the same declarations.[^generate][^generate-shell] When it cannot find a step that runs that generator, or the step fails, the pull request says so and names the command to run.[^generate-missing] A repository that holds its oxlint hits to `oxlint.baseline.json`, as spoonjoy does, gets that baseline lowered to the hits left in the files the update changes, counted with the oxlint version and `.oxlintrc.json` it pins; the pull request lists each count it lowered.[^baseline-falls] A count only ever falls: when the update raises one, the baseline stays as it was and the pull request names the file, rule and count that went up, so the repository's lint stays red on the new hit.[^baseline-rises] The rules of the repository's own JavaScript lint plugins are its code, which Ouro Current does not run, so their counts stay as they are, and a repository with no baseline gets none.[^baseline-none] An update that is held back whole opens no pull request, and the run's log says why.[^held] Ouro AX's shared files go where the package's `#ouro-ax/*` import resolves; without one they stay where the install record has them, or, when it has none, go under the lib folder, and the import it adds points there.[^kit] When a file moves, the repository's scripts and tests that name its old path, and a stylesheet's `@source` lines, are pointed at the new one, from the root, from the app's package folder or relative to the file; a workflow line or a line of prose that names it is listed in the pull request with the path to write, and a forwarding file at the old path runs the new file for one release.[^forward] A folder whose installed files all moved is followed as a folder, a path from the app's package folder is followed in that package and at the root but not in another package, and the rest of the app's source and Ouro's install folders are left as they are.[^references] A vendored file that now imports a file beside it brings that file into the lock, as a line like its neighbours.[^vendor-imports] Vendored Ouro AX files that import one another as `#ouro-ax/*` bring what they import into the lock, and the nearest package.json above them, the one Node resolves that import through, gets an `imports` entry that points at the vendored folder; one that points elsewhere is named rather than changed, and with no package.json above them the vendored folder gets one of its own.[^vendor-ax] A push to an update pull request whose auto-merge is on turns auto-merge off first and on again after, so a merge queue cannot take the pull request before its checks start.[^disarm] When an update brings in an Ouro check rule the repository's copy of the check never had, the run after it records the findings the pull request's own checks reported for that rule in `ouro-check.json`'s `known`, and says how many in the pull request: they pass, a new finding of that rule fails, and the record stays while the next commit's checks run.[^known] When those reports came from a run where a failing shard cancelled the others, and the round pushes nothing, it sends an `ouro-current-full-run` repository_dispatch event with the commit, which needs only the Contents write it has. The check's workflow, given `repository_dispatch: types: [ouro-current-full-run]`, runs the whole check on that commit and names its report artifacts `ouro-check…-full-<sha>`, and the next round records them. A workflow without that trigger is named in the result instead.[^full-run]
- **Moves NuGet and Gradle pins in place**: only the version of an Ouro package changes, written where the file writes it, and a floating or ranged version (`0.*`, `[0.11.0]`) is left as it is.[^native] A version kept in a property or variable moves where it is defined, unless a package that is not Ouro's reads it too.[^native] A NuGet `packages.lock.json` beside the project or under a central `Directory.Packages.props`, a `gradle.lockfile` or Gradle's `verification-metadata.xml` that holds the package keeps its hashes of the old version: it is left alone and named in the pull request with the command that writes it again.[^native-locks]
- **Holds Ouro UI for Apple for a package that is not ready**: when an app resolves another ourostack package that takes ouro-ui-apple itself (Ouro MD and its app shell), Ouro UI for Apple waits until that package, at the revision the app resolves, takes the new release, and the pull request says why.[^swift-holds]
- **Brings the app's stylesheet along**: for each theme item the stylesheet holds (`ouro-base`, by its `--ouro-layer`; `ouro-theme`, by its colours), it adds what the item at the new tag puts in the file `components.json` names (`tailwind.css`) and the file lacks, as `shadcn add` would: its `cssVars` in `:root`, `.dark` and `@theme inline`, and its `css` rules, utilities and keyframes, each declaration at the indent of its block.[^stylesheet] A variable the app already has keeps its value, a plain rule the item had at the old tag and the app left out stays out, and an entry it cannot write is named in the pull request instead.[^stylesheet] A `@keyframes` or `@utility` block is added whole whenever the stylesheet has no block of that name, whatever the old tag had; a `@keyframes` of that name the app has is kept as the app wrote it, and a `@utility` the app has gains a line new since the old tag, so a fix to `press` still reaches it.[^stylesheet-named] A record already on the newest release whose stylesheet lacks a variable, keyframes or utility that release's `ouro-base` adds gets the same pull request, "Update the stylesheet to Ouro UI vX", since an update before this one moved the components alone (#1843).[^stylesheet-behind]
- **Moves ouro-base into a file of its own**: a stylesheet that holds `ouro-base`'s rules gets `@import "./ouro/ouro-base.css"` after `@import "tailwindcss"`, and `ouro-base.css` from the new tag in an `ouro/` folder beside it, recorded in the install record by its hash like any installed file. Every declaration and keyframes the stylesheet holds exactly as the old tag's `ouro-base.css` has it is taken out, with any block that leaves empty; the app's own values stay after the import, where they win, and the pull request names them and what the file brings back.[^import] From then on Ouro Current leaves `ouro-base`'s rules out of the stylesheet and replaces the file whole on each release while it is still what was installed; a file the app edited is left and named.[^import] Rules it adds to one block keep `ouro-base`'s order, so the 200rem type step stays after the 150rem one.[^order] A plain-CSS copy (`ouro-base.css`, `ouro-theme.css` or `ouro-plain.css` from `site/public/css/`, for a page with no Tailwind) the install record holds is replaced the same way, and a record already on the release whose copy is an older one's gets a pull request.[^static]
- **Draws squircles in WebKit**: Ouro UI draws squircle corners where the engine has no `corner-shape` only through the `squircleCorners()` PostCSS plugin (`lib-squircle-corners`), so an update for an app that installs a component brings the plugin and adds it to the app's one `vite.config` or `astro.config` (under `vite` in Astro), with its import; another Vite config that builds CSS apart from it is named in the pull request.[^squircles] An app whose PostCSS plugins sit in a `postcss.config` file, or whose config Ouro Current cannot read, gets no pull request: the update is held back whole and says what to add, since an update without the plugin draws plain round corners in Safari.[^squircles-held] An app already on the release whose build lacks the plugin gets that update too, and one that names `squircleCorners` in a build config is left as it is.[^squircles-behind]
- **Names the new Ouro check rules** when the app has Ouro check installed: a rule in the new tag's `registry/ouro/check/new-rules.json` that the old tag's lacks, by name, is listed under "New Ouro check rules" with its summary and the number of the app's findings recorded as known for it, or, before the pull request's checks report them, that they will be.[^check-rules] Without that file, the rules whose findings were recorded are named from the record.[^check-rules] A file that cannot be read leaves the list out and says so.[^check-rules-bad] A check vendored in a package of a monorepo has them recorded in that package's own `ouro-check.json`, the one it reads where it runs.[^check-config]
- **Treats a widened rule as a new one.** A release that widens an existing rule's reach declares it in `new-rules.json`, as an entry with `widened` naming what the rule now also finds: `{ "rule": "off-scale", "widened": "negative lengths", "summary": "…" }`. The rule is then listed with what it now finds, and the app's findings of it are recorded as known in the update pull request, as a new rule's are. A new finding gates from the release on. An existing rule that a release does not declare widened keeps what was recorded, so its new findings gate.[^widened] We rule it so because a widening otherwise holds an app's update until someone fixes old code by hand, as off-scale's negative lengths did. A repository that vendors Ouro check through `upstream-sources.lock.json` reads the rules from `new-rules.json` too, at the lock's commit and the release's.[^widened]
- **Checks an update against the live site** of a repository whose Ouro check runs on its deployed pages, as ourostack/factory's does (`live.mjs`): when the update brings a rule, the release's Ouro check runs against those pages before the update is written, its findings of the new rules are recorded as known and named in the pull request whether or not the app vendors Ouro check, and a finding of any other rule holds the whole update back; the check is not repeated while the update's branch already records the new rules for that release, and a hold-back stands for six hours.[^live-check][^live-held][^live-recorded][^live-again]
- **Keeps one pull request per repository** on the branch `ouro-current/update`, and updates it in place when a newer release comes.[^one-pr] It pushes nothing when the update is already there, and closes its pull request when the repository caught up on its own.[^caught-up]
- **Writes a pull request a claims check accepts**: versions and file names in code spans, no counts, so a repository that runs Ouro UI's claims check on pull requests does not fail the update.[^claims]
- **Keeps a lock file's layout**: in `upstream-sources.lock.json` it changes only the followed source's commit and its files' hashes, and every other byte stays as the repository wrote it.[^lock] The release a source names, as `release` or `tag`, moves with its commit.[^source-tag]
- **Does what the repository asks of a change**, when it declares that in `.github/ouro-current.json`, the way Dependabot reads `.github/dependabot.yml`.[^rules] `version` lists the files that carry the app's version, with a pattern whose first group is the version; when the repository has a published release at or past it, the update moves those files to the next patch.[^rules] `changelog` is a fragment to add, its `path` and `text` taking `{version}` and `{releases}`.[^rules] `{versionSlug}` is the version with dashes for dots, for a fragment name that allows only letters, digits and dashes.[^slug] A prerelease version such as `0.1.0-alpha.1183` moves to the next number, a file can be listed more than once for each place it carries the version, and `"json": "versions"` makes `changelog` a JSON changelog whose `versions` array gets the text under the app's version.[^rules-json] `npm` names the package the app publishes: a version its registry already serves counts as released, so the update starts the next version instead of adding to the published one.[^rules-npm]

  ```json
  {
    "version": [{ "path": "Sources/App/Release.swift", "pattern": "static let version = \"([0-9]+\\.[0-9]+\\.[0-9]+)\"" }],
    "changelog": { "path": "changes/ouro-ui-{version}.md", "text": "Uses {releases}.\n" },
    "ignore": ["scripts/agent-benchmark/vendor/"],
    "review": { "team": "design-system" }
  }
  ```

  `ignore` lists pin files to leave alone, as a path or a folder ending in `/`, such as a copy a benchmark pins on purpose.[^ignore] A repository never follows itself, so Ouro UI's own copy of core's generator follows core alone.[^ignore]

  `review` is for a repository whose governance wants a person to approve each change: with `"review": { "team": "design-system" }` (or `"acme/design-system"`, the organisation that owns the repository), the update pull request is opened with auto-merge off, and that team is asked to review it when the pull request opens and after each push.[^review] A pull request that already had auto-merge on has it turned off, and a team GitHub refuses is named in the run's result while the update still opens, and is asked again on the next run if nobody has reviewed.[^review] An update that stays armed because GitHub would not turn auto-merge off fails that repository's run instead of reporting it off.[^review-armed] A team outside the repository's own organisation, or a `review` with no team, fails that repository's run with the fix.[^review-bad]

- **Brings Ouro UI's bar into AGENTS.md**, so the agents working in the repository read it: the lines in `agents.mjs`, between `<!-- ouro-ui:bar -->` markers, go after the paragraph that points at ourostack's Interfaces follow Ouro UI rule, or at the end, and change in place when those lines do.[^agents] The rest of `AGENTS.md` stays the repository's. An AGENTS.md byte budget in `.github/agents-md-budget.json` moves by the block's bytes alone, a repository that lists `AGENTS.md` under `ignore` is left alone, and one without the file gets none.[^agents-update]
- **Turns on auto-merge**, squash where the repository allows it, else a merge commit,[^auto-merge] unless the repository's rules name a review team. The repository's own checks decide whether it merges.

## What it leaves alone

- It never writes to a default branch, and never merges anything itself.[^one-pr]
- It never overwrites a file that differs from what the install wrote, and names that file in the pull request instead.[^hx]
- It writes nothing for a repository whose update pull request merged or closed while the run read it, because what it read of the default branch is from before that: no branch on the old default branch, and no title on the merged pull request.[^raced] The next run starts from the new default branch.[^raced]
- It never force-pushes over a commit someone else pushed to its pull request's branch, such as a fix the repository's checks needed; it leaves that pull request to them, as Dependabot does.[^edited] Merges of the default branch on top of its own commit, as "Update branch" makes, are not someone's fix: the next update replaces them.[^merges]
- It leaves `.github/workflows/` alone and says so in the pull request, or in the run's log when that is the whole update. GitHub lets an app change a workflow only with the `workflows` permission, which installations would have to approve again, and which would let the app write CI. A workflow that needs the Ouro UI version reads it at run time from a file Ouro Current moves, such as the tag in `.github/ouro-hx-installed.json`.[^workflows]
- It never names a private repository in public: not in the run's log, and not on the page.[^private]

## How it runs

[`.github/workflows/ouro-current.yml`](../../.github/workflows/ouro-current.yml) starts when Release has tagged an Ouro UI release (release.yml starts it with `gh workflow run`, because a release published with the workflow's own token starts no workflow itself),[^release-start] and runs twice an hour for core, Apple, Windows and Android releases. It signs in as the app (a JWT from the private key in `OURO_CURRENT_PRIVATE_KEY`, the app ID in `OURO_CURRENT_APP_ID`), takes a short-lived token for each installation, and keeps every repository that installation can see.[^jwt] A failed GitHub request is tried again.[^retry] A repository that still fails is reported while the others go on, in a dry run too,[^dry-run] and the run opens or comments on one issue, "Ouro Current could not update a repository", which it closes after a clean run.[^failure]

The list of who it keeps current is `current.json` on the `adoption-data` branch. For a repository the app is not installed on yet, `--with-token` opens the same pull request with your own token.[^with-token]

```sh
node --test scripts/current/current.test.mjs                                   # the tests, with GitHub faked
GH_TOKEN=$(gh auth token) node scripts/current/current.mjs --dry-run --only owner/repo   # what it would change; writes nothing
GH_TOKEN=$(gh auth token) node scripts/current/current.mjs --with-token --only owner/repo   # the same pull request, opened with your token
```
