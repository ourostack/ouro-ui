# The adoption ledger

The one place that tracks who uses Ouro UI and who gives back to it. It is published at <https://ui.ouroboros.bot/adoption/>, regenerated hourly, and its cells link the public source they were measured from. Tracking happens in public, in issues labelled [`adoption`](https://github.com/ourostack/ouro-ui/issues?q=is%3Aissue+label%3Aadoption): one for the program, one per work item.

## Run it

```sh
node scripts/adoption/ledger.mjs                     # writes site/src/adoption/ledger.json
node scripts/adoption/ledger.mjs --out /tmp/l.json   # somewhere else
node scripts/adoption/ledger.mjs --only ouro-md,gatefold
node --test scripts/adoption/ledger.test.mjs         # the tests, with `gh` faked
```

It needs a current Node, `unzip` and a signed-in `gh`, and imports only Node's built-in modules. Code search is rate limited, so a run waits on it between searches.[^search-limit] The hourly run passes `--search-cache-in`/`--search-cache-out` so a repository whose commit hasn't moved since the last hour, and whose cached result is under a day old, is read from the cache instead of searched again.[^search-cache]

The hourly run is [`.github/workflows/adoption-ledger.yml`](../../.github/workflows/adoption-ledger.yml). It writes `ledger.json` to the `adoption-data` branch (a bot-written data branch, not a pull request, so the hour's number does not wait for a pull request to merge). It writes the code-search cache to that branch too, in its own file (`search-cache.json`), keeping a search result out of `ledger.json`. Pages builds that branch's ledger into the site, read signed in from the contents API rather than a cached copy,[^api] when it is newer than the copy committed on main (`take-newest.mjs`), so the page opens on the last hourly run, and it still offers the branch's newer one when it opens. Each hourly run dispatches Pages once it has published, so the deployed page opens on that hour's ledger.[^rebuild] Code search waits share one time budget; after it, the cells that needed a search are left "not measured", so a heavily rate-limited hour still publishes the rest.[^search-budget]

## What it reads

- [`ledger.config.json`](ledger.config.json): the hand-kept list of the [surfaces](scripts/adoption/ledger.config.json "verify:count(scripts/adoption/ledger.config.json#surfaces)=23") and the [work items](scripts/adoption/ledger.config.json "verify:count(scripts/adoption/ledger.config.json#cards)=16"), and how a column is measured for a product. Add a product here, with its repository and a tracking issue.
- Live: GitHub releases, repository files and trees, code search, Actions artifacts, merged pull requests, and the issues labelled `adoption`.

An issue is found by a hidden marker in its body: `<!-- adoption:card=<id> -->` for a work item (the ids are in the config), `<!-- adoption:program -->` for the program. The program issue holds a table, `| Step | Depends on | Repo | State | Evidence |`, which becomes `program.steps` in `ledger.json`; the page shows only the products, so read the steps there or in the issue. Edit the issue to change a step's state; the next run records it.

## The columns

A cell is `{ value, note, source, measuredAt }`.[^cell] A value of `null` means "not measured yet" and the note says why. The generator estimates nothing.

| Column | Value | How it is measured |
|---|---|---|
| Ouro UI pin | the pinned tag and how many stable releases came after it | Reads the product's own file (an installed-components record, a `Package.swift`, `Package.resolved` or XcodeGen `project.yml`, a workflow's `OURO_UI_TAG`, a vendoring lock) and counts the stable releases of the repository that pin follows published after the pinned one. A vendored commit counts the releases after the commit's date. A product whose file records a dependency on nothing gets an empty list. A library that keeps a SwiftPM floor (`from:`) low on purpose and commits no resolved file builds against the newest release of that major, so a pin marked `"range": "major"` lacks no release while the newest is in its range.[^floor] |
| HX use | `full`, `partial`, `none` or `n/a` | Web: the installed Ouro components (folders of `components/ouro/*/*.tsx` in the repository tree) and the files that import them (code search). `full` is 20 or more[^web-full] components in use, `partial` is some use, and `none` is the absence of both. Apple: the files using an Ouro HX component (`OuroButton`, `OuroToast`, `OuroBanner`, `OuroSheet`, `OuroEmptyState`) and the files that use `OuroHX` in any way. `full` is 5 or more[^apple-full] component files, `partial` is use of `OuroHX` without that, and `none` is neither. `n/a` is for a CLI, a server or a tool that has only a command line or a server, with the reason. |
| AX kit | `yes`, `no` or `n/a` | `yes` when code search finds `defineCommand`, `bindAx` or `ax-mcp` outside the kit's own copy, tests and fixtures, when the product vendors the kit's files, or (Apple) when a file imports `OuroAX`. |
| Actions on the one-action model | a count | The actions the product declares once and generates with ouro-ui-core's `ouro-actions`: every `actions.json` in its repository whose `generator` is `ouro-actions`, each action counted once per set.[^action-model] Test fixtures and benchmark copies are left out. `0` when there is no such file; `null` when the file list GitHub returned was cut short and held none.[^action-none] It is information; Confirmed counts the census instead. |
| Census | doors declared out of doors found, and the gaps | The product's Ouro AX census (`scripts/ouro-census/`): `census.json` in the `ax-census` artifact of the newest successful push to `main` of the workflow the config names, for the product the config names.[^census-trust] It counts only when the run is a push to `main` in the product's own repository, the report is for `refs/heads/main` at that run's commit, its checker hash is the one in `scripts/ouro-census/dist-manifest.json` at Ouro UI's latest release or at a release that one replaced less than a day ago, it is at most 7 days old, and its counts add up; otherwise the cell is not measured and says why.[^census-trust] The gaps are its weak, undeclared, unwalked and stale doors added up.[^census-gaps] A kind a product's own walker walks counts only once the config's `census.reviewed` maps that walker's name to its module's SHA-256 as the report gives it.[^census-reviewed] |
| X-ray | claims holding, and `must` claims holding | The `ax-xray` reports among the product's CI runs: the latest successful pushes to `main` of the workflows named in the config, in the repository the config names (a pull request, a fork's `main` or another branch doesn't count),[^xray-push] their artifacts, `report.json` at the artifact's root or in a folder of it,[^nested] matched by the app's name. The cell links the run and gives the report's own date. Apple apps' reports come from their App Intents X-ray, Spoonjoy web's from its MCP X-ray (`mcp-xray.yml`). A claim set without `must` claims conforms trivially. An app on the one action model also uploads `ouro-actions check --report` (ouro-ui-core 0.16.0), an artifact named with `xray`: the newest report of each checker counts, and their claims add up, so the action claims' `must` claims count with the X-ray's.[^xray-sum] A product's X-ray reports count once per checker and surface, so a CLI report and an MCP report both count. The config lists the surfaces a product has (`xraySurfaces`: `cli`, `http`, `mcp`, `tools` for in-turn tools, `app-intents`), and a product that runs agents (`runsAgents`) lists `tools`.[^xray-surfaces] |
| Give-back | merged pull requests | Merged pull requests into `ourostack/ouro-ui`, `ouro-ui-core` and `ouro-ui-apple` whose title, text or branch names the product (the terms are in the config; whole words only), leaving out release and "Prepare main" pull requests. It is a text heuristic, and a lower bound: a pull request that came from a product's lane without naming it is not counted, and a mention is not authorship. Ouro UI itself is `n/a`. |
| Tracking issue | the issues for the product's work items | The `adoption` issues whose work item lists the product, with their state. A product that lacks a work item is shown as not having an issue yet. |
| Confirmed | the conditions below, together | The list that follows. |

The target is that no product goes more than a day without an Ouro UI release (web, core or Apple) it lacks.[^late] The summary names each product past it, and adds up every counted product's releases behind; that total is context, since Ouro UI releases several times a day.[^late] While one has, the hourly run keeps one issue open, "Products are more than a day behind Ouro UI", and comments on it at most daily.[^late-issue]

### Confirmed

A product is confirmed when these hold together:

1. **On current Ouro UI**: it has a pin, every pin could be read, and no pin lacks a release that has been out for more than a day.[^current] Ouro UI releases several times a day, so "no release behind" would hold only for the minutes after a product updates; the day is the target below, and the cell still shows how many releases a pin is behind.[^current]
2. **Ouro HX in full**: a product with screens builds them from Ouro HX, so the HX column reads `full`. `partial` or `none` leaves hand-built screens, and the page says how much was counted. A product whose config says HX is `n/a`, with its reason (a CLI, a server, an agent without a screen of its own), holds it as `n/a`.[^hx-full] A private product's HX is read only from the evidence its own CI publishes, so with none the check doesn't hold for it.[^published]
3. **Census at zero**: the census finds doors, none of them is a gap, and it walks every door kind the config lists for the product.[^census-gaps] It counts doors declared, not files installed.
4. **AX `must` claims pass in CI**: a report exists, it has `must` claims, they hold, and the reports check every surface the config lists for the product.[^xray-surfaces] A claim set without `must` claims is vacuous and does not count.[^confirmed] A product whose in-turn tools no report checks fails here, and its cell says which surfaces are missing.[^xray-surfaces] The claim set a report checks must be one an Ouro UI release published in `scripts/ax-claim-sets.json`, read at the latest release; a claim set from a local or branch build fails.[^claim-set-released] An older released claim set says how many claim sets and releases behind it is, and fails only when a newer one adds a claim for a surface the product lists.[^claim-set-behind]
5. **Has given back**: at least one merged pull request in the give-back column. Ouro UI, the upstream, has nothing to give back to, so this holds for it and its `n/a` cell is not counted as unmeasured.[^upstream]

A product whose config says AX is `n/a`, with its reason (a site with no CLI, MCP or other agent interface of its own), has nothing for the X-ray to check, so the must check holds for it as `n/a`, the way give-back holds for the upstream, and that cell is not counted as unmeasured.[^ax-na] The reason alone doesn't hold Census at zero: that check holds as `n/a` only when the product's own census walks its kinds and finds no doors.[^census-na] The page draws them as "does not apply", not as passing.[^ax-na-page] A product with an agent interface still needs both.

Ari then signs the product off; the ledger only says whether the evidence is there. The page counts products "in scope". A product marked `inScope: false` in the config is listed but not counted: Drift Remote, a private repository the public ledger cannot read. Shepherd is read from the harness's census, as its own product there. The Butler is private and counted, so it stays unmeasured, never Confirmed, until its CI publishes a census summary the ledger can read.[^census-rows] A private desktop app publishes its evidence, so its row is read from that.[^published]

## The program section

The steps come from the program issue's table and are recorded in `ledger.json` (`program.steps`), not drawn on the page. Ouro UI's own numbers are: the latest release of the Ouro UI repositories, the number of Ouro HX components in the registry, the merged pull requests across them, the pull requests the give-back column counted, the benchmark, which is each interface's tasks done out of trials run in the agent interface benchmark's published runs on main, counted as its page counts them,[^benchmark-cell] and the model-reviews result, which is the newest review's headline, counted from its runs on main as its page counts them, with whether more than half the models that gave a verdict chose Ouro UI.[^model-reviews-cell]

## What cannot be measured here

- A product in a private repository: it is listed, with its cells "not measured yet", unless its own CI publishes evidence. The config's `published` names a file in a public repository (`ourostack/adoption-evidence`), and the ledger reads the pins, HX and X-ray cells from it: schema 1, for that product, dated in the past, at most 7 days old, with whole-number counts, or the cells stay not measured.[^published] HX is `full` when 20 or more Ouro components are in use across the screens the product's X-ray of its window read and no other control is on them.[^published-full] Its X-ray reports are held to the same released claim sets as any other. Each cell's note says the product published it.[^published]
- A web product's X-ray, other than Spoonjoy web's, which the config names (`ledger.config.json`).
- Code search reads a repository's default branch and can lag a push.
